# 权限模型

两个维度：**作用域**（在哪管）+ **等级**（能管谁）。

设计目标：一个用户在不同群、不同插件里可以拥有完全不同的权限，互不干扰；
上级只能设置下级，不能给自己或同级提权。

---

## 等级：数字越小权限越高

和 Unix 的优先级一个思路，`0` 最高。

| 等级 | 值 | 能授予的下级 | 来源 |
|------|----|-------------|------|
| 主人 | 0 | 1 及以上 | **只能**在 `config/bot.json` 的 `owners` 里配 |
| 管理员 | 1 | 2 及以上 | 命令或面板 |
| 群管 | 2 | 3 及以上 | 命令或面板 |
| 助手 | 3 | 4 及以上 | 命令或面板 |
| 内核预留 | 4 ~ 9 | — | 以后扩展用，现在空着 |
| 插件区 | 10 ~ 998 | — | 主程序按插件 id 自动分配号段 |
| 无权限 | 9999 | — | 默认值 |

### 为什么 `0` 不能通过命令授予

主人等于「能改任何配置、能启停任何插件、能给自己提权」。如果命令能授予 `0`，
一个拿到管理员的人就能自己升到主人，权限体系直接失效。

所以 `0` 只有两个入口：
- 手改 `config/bot.json` 的 `owners`
- 首次启动用认领码 `/claim <码>`（`owners` 为空时才可用）

认领码每次启动随机生成，只打印在控制台和面板日志里——避免群里任何人抢先 `/claim` 变成主人。

## 等级空间是分区管理的

| 区间 | 归属 | 说明 |
|------|------|------|
| 0 – 3 | **内核独占** | 主人 / 管理员 / 群管 / 助手，插件只能读（`ctx.CORE_LEVELS`），不能改语义 |
| 4 – 9 | 内核预留 | 以后加「超管」「审计」不用重排 |
| 10 – 998 | **插件区** | 启动时按插件 id 排序，每个插件分 10 个号位 |
| 9999 | 无权限 | 普通成员 |

号段分配示例（按 id 字典序）：

```
dice       10-19
echo       20-29
hello-py   30-39
```

**为什么按 id 排序而不是按加载顺序**：目录读取顺序不保证稳定，如果按加载顺序分配，
重启后号段会漂移，用户已经配好的权限就对不上了。按 id 排是确定性的，
同一插件永远拿到同一段。

插件在自己的号段内自定义等级，不会和内核对撞：

```js
const L = ctx.defineLevels({
  管理员: 0,   // dice → 10
  玩家: 2,     // dice → 12
});
```

`ctx.defineLevels` 会自动在菜单里加一个「权限等级」分组，用户 `/help dice` 就能看到怎么授权。

用 `/admin levels` 查看当前的号段分配。

## 作用域

| 写法 | 含义 |
|------|------|
| `global` | 全局 |
| `group:<群openid>` | 某个群 |
| `channel:<频道id>` | 某个频道 |
| `user:<用户openid>` | 某人的私聊 |
| `feature:<插件id>` | 某个功能的管理权 |

### 有效等级怎么算

```
有效等级 = min(全局, 当前会话, 本插件)
```

取数字最小的那个，也就是权限最高的那个。

举例：某人在 A 群是群管（2），在 dice 里有插件等级 10，在 echo 里是插件等级 20。

```
/admin whois 8C7419D4...
  openid: 8C7419D4...
  全局: 无
  各作用域：
    group:xxx     群管（2）
    feature:dice  插件等级 10（10）
    feature:echo  插件等级 20（20）
```

- 在 A 群用管理命令 → 2，通过
- 在 dice 里 → `min(9999, 2, 10) = 2`，通过
- 在 echo 里 → `min(9999, 2, 20) = 2`，通过
- 换个群、没被授权 → `min(9999, 9999, 10) = 9999`，拒绝

每个插件只看自己那一段，权限不会串。

---

## 核心规则：只能授予数字更大的等级

也就是**只能给比自己权限低的人授权**。同级和更高权限都改不了。

| 你是 | 能设的范围 |
|------|-----------|
| 主人（0） | 1 及以上 |
| 管理员（1） | 2 及以上 |
| 群管（2） | 3 及以上 |
| 助手（3） | 4 及以上 |
| 插件等级 10 | 11 及以上 |

这条规则同时管住两件事：**不能给自己提权**，**不能动同级或更高的人**。

## 命令

```bash
/admin                        # 当前作用域总览 + 自己的等级
/admin me                     # 查看自己在各作用域的权限
/admin list [作用域]           # 列出某作用域的管理员
/admin set <openid> <等级> [作用域]
/admin del <openid> [作用域]
/admin whois <openid>         # 查某人在各作用域（含各插件）的权限
/admin scopes                 # 列出所有已配置的作用域
/admin levels                 # 等级空间与插件号段分配
```

作用域省略时默认「当前会话」：

```bash
/admin set 8C7419D4... 2              # 设为本群群管
/admin set 8C7419D4... 3 group:xxx    # 指定某个群
/admin set 8C7419D4... 1 global       # 全局管理员
/admin set 8C7419D4... 5 feature:dice # 只管掷骰子，5 级
```

## 群主和邀请人自动拿权限

| 信号 | 授予 |
|------|------|
| `GROUP_ADD_ROBOT` 事件里的 `op_member_openid`（邀请人） | 该群管理员（1） |
| 消息报文里 `author.member_role = owner`（群主） | 该群管理员（1） |

两条都**只影响那一个群**，不会变成全局主人——把最高权限交给一个可能不相干的人是不对的。

**已知局限**：官方没有查询群主/群成员的接口。
- 群主只在**发过言**之后才能被识别（要靠消息报文里的 `member_role`）
- 机器人离线期间被拉进群，`GROUP_ADD_ROBOT` 事件会永久丢失，拿不到邀请人

拿不到时，用 `/admin set <openid> <等级>` 手动授权，或让当事人发 `/whoami` 拿到自己的 openid。

## 插件里怎么用

```js
// 命令级：注册时声明
ctx.command('purge', { desc: '清理本群数据', admin: true }, handler);
ctx.command('shutdown', { desc: '全局停机', admin: true, globalAdmin: true }, handler);
```

| 选项 | 含义 |
|------|------|
| `admin: true` | 需要**当前作用域**管理员（≤1）及以上 |
| `globalAdmin: true` | 需要**全局**管理员（≤1），用于影响全局的操作 |

```js
// 代码级：自己判断
if (!(await ctx.can(msg))) return msg.reply('需要管理员权限');   // 默认要求 1
if (!(await ctx.can(msg, 'manager'))) return;                    // 指定 2
if (!(await ctx.can(msg, L.管理员))) return;                     // 本插件自定义等级

// 拿具体数字做更细的判断（越小权限越高）
const lv = await ctx.levelOf(msg);
if (lv <= 1) { /* 管理员及以上 */ }
if (lv === 9999) { /* 无权限 */ }
```

| 成员 | 说明 |
|------|------|
| `ctx.can(msg, 等级?)` | 是否达到某等级，默认 `admin`（1） |
| `ctx.levelOf(msg, 作用域?)` | 取权限等级数字，自动看全局 + 当前会话 + 本插件 |
| `ctx.scopeOf(msg)` | 当前作用域：`group:xxx` / `channel:xxx` / `user:xxx` |
| `ctx.isOwner(userId)` | 是否机器人主人 |
| `ctx.isGroupAdmin(群openid, userId)` | 该用户是否是这个群的管理者 |
| `ctx.CORE_LEVELS` | 内核等级常量（只读）`{ owner:0, admin:1, manager:2, helper:3 }` |
| `ctx.levelBase` / `ctx.levelRange` | 本插件号段起点 / 范围 |
| `ctx.level(n)` | 号段内第 n 档，`ctx.level(0)` 是最高 |
| `ctx.defineLevels(map)` | 一次性定义并写进菜单 |

## 数据存在哪

`data/bots/<机器人id>/roles.json`，结构是「作用域 → openid → 等级」。

```json
{
  "__version": 2,
  "group:ABC123": { "user-openid-1": 1, "user-openid-2": 2 },
  "feature:dice": { "user-openid-1": 10 },
  "global": { "user-openid-3": 1 }
}
```

`__version` 用于数据迁移。改结构时递增版本号并在 `roles.js` 里写迁移逻辑，
旧存档会自动升级，不用手动改。
