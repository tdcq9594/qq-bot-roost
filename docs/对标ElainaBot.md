## 一、结论先行

**1. 架构层的差距已经平了。**
前两轮补的 Webhook / 流式 / 全局菜单 / Docker / 自更新 / 后台服务，对方有的我们现在都有。
这一轮剩下的差距里，**没有一项是「做不到」，全是「还没做」或「攒得少」**。

**2. 差距性质变了：从「能力」变成「内容」。**
66 vs 4 个插件、10 个图床、DAU 图表渲染、SQLite 七类统计——
这些不是框架能力，是作者投入量。**框架再好也补不出内容。**

**3. 唯一会随时间恶化的技术差距是存储层。**
我们全用 JSON 文件。统计类数据（DAU / 消息流水 / 成员 / 订阅）一旦上量，
JSON 会变成性能瓶颈和损坏风险。这是唯一必须动架构的一项，但**只对「运营多群」才成立**。

## 四、差距清单（按优先级）

| 优先级 | 事项 | 现状 → 目标 | 理由 | 量级 |
|---|---|---|---|---|
| **P0** | SQLite 存储 + 统计 | 0 行 → 基础表 + 3 类统计 | 唯一会随时间恶化的差距。`node:sqlite` 是 Node 22 内置，**不破坏零依赖** | 600~900 行 |
| **P1** | 插件文件变更自动热重载 | 无 → mtime 轮询 | 开发者体验最直接的一项，对方做法已可抄 | ~100 行 |
| **P1** | 插件元数据补 `icon` / `frameworkVersion` / `supportPlatforms` | 部分 → 完整 | 版本不兼容要能**阻止加载并提示**，不能装完才发现跑不了 | ~50 行 + 规范一节 |
| **P2** | 插件注册 Web 页面 | 无 → `ctx.registerPage()` | 让插件自带管理界面，面板才能长大 | ~150 行 |
| **P2** | 素材管理 / 模板消息 / silk 语音 | 无 → 有 | 消息能力补齐最后几个口子 | 中等 |
| **P3** | 图床（走插件层） | 无 → 1~2 个 | 必须走插件，否则破坏零依赖 | 插件级 |
| **P3** | 图片渲染（走插件层） | 无 → 可选 | 同上，PIL/canvas 都是重依赖 | 插件级 |
| **P3** | 插件数量 4 → 20 | 4 → 20 | 不是技术问题，是持续产出 | 长期 |

**不做的**：多平台适配层（对方也没有，做了是过度设计）。

## 五、我们领先的四项（写 README 的依据）

1. **多语言插件** —— 对方只有 Python。我们内建 ESM + 外部子进程 NDJSON，
   Python / Go / 任意语言都能写。**这是唯一对方短期补不上的架构差异**（它是 Python 单语言绑定）。
2. **零运行时依赖** —— 装 Node 22 就跑，`npm install` 都不用。
   对方 `requirements.txt` 拉 FastAPI 一整套。部署成本差一个数量级。
3. **细粒度权限** —— 我们是「5 作用域 × 数字等级 + 号段动态分配」，
   对方是 `_blacklist.py`（2.5 KB）级别的禁用名单。这个模型没有对标。
4. **编辑器集成** —— DSH 插件让 AI 直接管机器人（查状态/看日志/启停插件/发消息）。
   对方没有，整个 QQ 机器人圈也没见第二家。

| 第二轮 | 10-23 | **运行时服务**：5 个后台服务 | v0.5.3 补平 |

（WebUI 重做、修 git 依赖、修插件不生效、加卸载）
**全部是修自己，对标差距一点没缩小**。

这不是浪费时间——0.5.5 那个「装了插件永远不生效」是致命的，
不修的话连 4 个插件都跑不起来。但要说清楚：**修 bug 不等于追差距**。

## 七、下一步建议

技术上的 P0 是存储层，但**真正卡住的不是技术**：

- 仓库 1 star，市场 4 个插件全是示例
- 对方 70 star，但插件仓库也只有 3 star——**它的 66 个插件也是作者一个人攒的**
- 所以「插件数量差距」不是社区差距，是**单人产出量差距**

如果目标是「有人用」，优先级应该是：

1. **先让一个陌生人能跑起来**（安装文档 + 首次启动体验，比存储层重要）
2. **再让第一个外部作者能写出插件**（热重载 + 元数据 + 一份能照抄的插件模板）
3. 然后才是存储层（等真有人运营多群了再做）

如果目标是「自己用得爽」，那 P0 就是存储层 + 热重载，其余可以一直不做。
