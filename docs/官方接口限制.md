# 官方接口限制与应对

用 QQ 官方接口而不是第三方协议（OneBot 那类），换来的是合规和稳定，代价是一堆硬限制。
这份文档说明**哪些限制内核已经替你处理了**、**哪些只能绕**、**哪些根本做不到**。

---

## 一、已被内核兜底的

插件和业务代码都不用关心这些，`msg.reply()` 照常调即可。

| 官方限制 | 数值 | 内核怎么处理 |
|----------|------|--------------|
| 被动回复有效期·**群聊** | **5 分钟**，每条消息最多回复 **5 次**（`msg_seq` 1–5） | 发送前查消息年龄，超过 4 分 45 秒自动降级为主动消息；次数用满同样降级 |
| 被动回复有效期·**单聊** | **60 分钟**，每条消息最多回复 **4 次** | 同上，但窗口和次数按 `kind` 分开取（`outbound.js` 的 `PASSIVE_SAFE_MS` / `PASSIVE_MAX_REPLIES`） |
| 同一会话发送频率 | **每秒 5 条**（⚠️ 待核实：2026-10 版官方文档在发送接口上写的是「接口频率限制 100 QPS」） | 按会话排队，默认压到 4 条/秒留余量 |
| 主动消息额度·**群聊** | 单关系 **20 条/分钟** + **每个群每天 1000 条**；Bot 维度：认证 60/qpm、未认证 30/qpm | 本地记账落盘 `data/bots/<机器人id>/quota.json`，日额度和分钟额度都拦 |
| 主动消息额度·**单聊** | 单关系 **20 条/分钟** + **每个好友每天 1000 条**；Bot 维度：企业/个人身份证认证 **10/qps**，未认证 **5/qps 且 30/qpm** | 同上（⚠️ Bot 维度单聊是 **qps** 不是 qpm，未认证还多一道 30/qpm） |
| 必须 WebSocket 在线才能发 | — | 离线时直接拒发，不浪费一次网络请求 |
| 主动消息需审核 | 返回 `304023` | 识别为 `pending`，**不当失败** |
| 同一条消息被重复投递 | — | 按 `msg.id` 去重，窗口 120 秒 |
| 相同 `msg_id` + `msg_seq` 重复发送 | 返回 `40054005` 消息被去重 | `msg_seq` 是天然幂等键，投递账本必须记 |

> **2026-10-29 修正**：以前「5 分钟 / 5 次」是**群聊口径**，被两个场景共用了。
> 单聊实际是 **60 分钟 / 4 次**，共用会导致单聊 5 分钟后就白白降级成主动消息
> （吃掉每个好友 1000 条/天的额度，而被动回复本来不占额度），
> 且第 5 次回复必然撞 `40034128`。已按 `kind` 拆开。

具体实现在 `src/outbound.js`。发送失败抛 `SendError`，带 `code` 字段：

| `code` | 含义 | 建议处理 |
|--------|------|----------|
| `offline` | 机器人没连上 QQ | 记日志，别重试 |
| `expired` | 超窗且主动额度用完 | 告诉用户「稍后 @ 我一次」 |
| `quota` | 主动额度用完 | 同上 |

```js
import { SendError } from '../../src/outbound.js';

try {
  await ctx.push(groupId, '每日提醒');
} catch (e) {
  if (e instanceof SendError && e.code === 'quota') {
    ctx.logger.warn('今日主动额度已用完，跳过');
  } else throw e;
}
```

## 一·补、发送消息的错误码（2026-10-29 核对官方两个发送接口页）

**QQ 的业务错误码和 HTTP 状态码是两回事**：同样是 400，`40054004`（无好友）
和 `40034006`（内容违规）该做的事完全不同。所以 `api.js` 的 `#request` 会把
`data.code` 拆成 `err.qqCode`，上层按它分支，不靠猜消息文本。

### 和「能不能送达」有关的（会改可达性状态）

| 码 | 含义 | 出现场景 | 处理 |
|---|---|---|---|
| `40054004` | 无好友关系 | 单聊主动消息 | `reach.is_friend = 0` |
| `40054013` | 用户拒收消息 | 单聊主动消息（用户在资料卡关了推送） | `reach.c2c_push = 0` |
| `40054006` | 验证好友关系失败 | 单聊 | **不改状态**，官方自己说「请重试」 |
| `40034101` | 机器人非群成员 | 群聊 | 群档案标失效 |
| `40054003` | 机器人不是群成员 | 群聊 | 同上 |
| `40054002` | 机器人被禁言 | 群聊 | 临时状态，**不是**不可达 |

### 和额度 / 幂等有关的（不改状态，只记日志或退额度）

| 码 | 含义 | 处理 |
|---|---|---|
| `40034100` | 主动消息超频控 | 退额度、记日志；**不能**当成「对方不可达」 |
| `40034122` | 召回消息已达区间上限 | `is_wakeup` 该周期用完了 |
| `40034123` | 不支持召回消息 | 回退普通主动消息 |
| `40034128` | 被动回复时间或次数超限 | 本地已提前拦（群 5 次 / 单聊 4 次） |
| `40054005` | 消息被去重 | 相同 `msg_id` + `msg_seq` 重发；幂等键有效 |
| `304103` / `40034005` | `msg_id` 已过期 | 降级主动消息 |
| `40054016` | 机器人已下线 | 检查连接状态 |

### 另外三个没用上的能力

| 能力 | 接口 | 说明 |
|---|---|---|
| **互动召回** `is_wakeup` | 仅单聊 | 用户主动对话后 30 天内，可分 4 个周期各下发 1 条（当天 / 1-3 天 / 3-7 天 / 7-30 天）。与 `msg_id`、`event_id` 互斥 |
| **事件被动回复** `event_id` | 单聊 + 群聊 | 单聊支持 `INTERACTION_CREATE` / `C2C_MSG_RECEIVE` / `FRIEND_ADD`；群聊支持 `INTERACTION_CREATE` / `GROUP_ADD_ROBOT` / `GROUP_MSG_RECEIVE`。**用户加好友、重新打开推送时可以被动回一条，不消耗主动额度** |
| **输入中状态** `msg_type=6` | 仅单聊 | `input_notify`，最长 60 秒。模型思考时先亮「正在输入…」 |

### 引用回复的 ID 怎么来（以前以为解不出）

`message_reference.message_id` 要填**消息索引**，不是 `msg_id`：

- **非机器人发的消息** → 从消息事件 `message_scene.ext` 的 `msg_idx` 取（形如 `REFIDX_xxx==`）
- **机器人自己发的消息** → 从发送响应的 `ext_info.ref_idx` 取

所以只要把每条消息的 `msg_idx` 存下来、把自己发出去的 `ref_idx` 存下来，引用边就能建。

### 单聊不是「拿到 openid 就能发」：两道门

这是之前最容易想错的地方。**openid 和能不能私聊完全无关**——同一个用户在同一机器人下的 openid
是稳定的，但你拿着它直接发单聊，可能撞 `40054004`。

| 门 | 含义 | 关着的时候 |
|---|---|---|
| **门一：好友关系** | 用户必须把机器人**加为好友**（且机器人后台白名单放行） | `40054004` 无好友关系 |
| **门二：主动推送开关** | 用户在资料卡里可以关掉机器人推送（`C2C_MSG_REJECT`） | `40054013` 用户拒收消息 |

两门都开才能主动发单聊。**但被动回复不受门二限制**——用户刚给你发过消息，你在 60 分钟窗口内回，
他关着推送也收得到。所以判断逻辑不是「不可达就不发」，而是：

- **有被动窗口** → 直接回，不查可达性
- **没被动窗口（要主动推）** → 查可达性：`yes` 发、`no` 跳过、`unknown` 放行并靠失败回写补状态

`unknown` 必须放行。因为好友关系只能靠 `FRIEND_ADD` / `FRIEND_DEL` 事件学到，而这些事件
**在机器人上线前发生的历史关系是补不回来的**——一个从没触发过事件的老好友，状态永远是 `unknown`。
把 `unknown` 当 `no` 会把所有老用户全静音。

实现见 `src/reach.js`，状态落盘 `data/bots/<id>/reach.json`。面板「数据 → 可达性」页可以看，
也能**人工标注**（`POST /api/reach`）——老关系永远拿不到事件，没有这个口子就只能去改 JSON。

## 二、官方没开放、只能绕的

| 能力 | 现实情况 | 应对 |
|------|----------|------|
| **群列表** | 确实没有「查询机器人所在群」的接口（21 个群接口里没有这个） | 靠 `GROUP_ADD_ROBOT` 和消息事件被动发现，内核自动登记到「群组」页 |
| **用户 QQ 号** | openid 不可读。**同一个机器人下，同一用户在群聊和单聊拿到的是同一个 openid**；换成另一个机器人就变了 | 用 `msg.userName` 显示昵称，openid 只在单机器人内做人物档案的键 |
| **必须 @ 才能触发** | 官方已全量开放免@唤醒，但受群设置和机器人权限影响 | 内核做「免@粘性」兜底，见下 |

> 群管理（禁言 / 踢人 / 群成员）**不是没开放**，而是分批开放。详见下一节，
> 这份文档早期写的「踢人 / 禁言 / 撤回他人消息明确未开放」已经过时。

## 二·补、群管理接口现状（2026-10-23 核对）

官方群聊管理接口一共 21 个，分三档状态。**别再说「官方没给」**——
被内邀卡住的只是群成员那几个，禁言和撤回早就能用了。

### 已开放，可以直接用

| 接口 | 方法 | 路径 | 频率限制 |
|------|------|------|----------|
| 获取群基本信息 | GET | `/v2/groups/{group_openid}/info` | 30 QPM |
| 获取机器人群内状态 | GET | `/v2/groups/{group_openid}/bot_state` | — |
| 查询群禁言状态 | GET | `/v2/groups/{group_openid}/restrict_chat_setting` | — |
| **设置群成员禁言** | POST | `/v2/groups/{group_openid}/restrict_chat_setting` | 60 QPM |
| **撤回群聊消息** | DELETE | `/v2/groups/{group_openid}/messages/{message_id}` | 10 QPS |
| 入群申请列表拉取 | GET | `/v2/groups/{group_openid}/join_request_list` | — |
| 入群申请审批 | POST | `/v2/groups/{group_openid}/approval_join_request/{member_openid}` | — |
| 入群自动审批策略（增删改查 / 执行 / 白名单） | 多个 | `/v2/groups/join_approval_strategy...` | — |

**禁言的硬约束**（`restrict_chat_setting`）：

- 机器人**必须拥有群管理员身份**，否则 `40062003 无操作权限`
- 最长禁言 **30 天**；到期时间用 RFC3339，如 `2026-08-05T11:23:05+08:00`
- 单次最多 **20 个**成员，通过 `op` 控制：`add` 增加 / `update` 改到期时间 / `del` 解除
- **只能操作普通成员**，群主、管理员、机器人都不能动

```json
POST /v2/groups/{group_openid}/restrict_chat_setting
{
  "members": [
    { "op": "add", "member_openid": "EC58...", "mute_expire_at": "2026-08-05T11:23:05+08:00" }
  ]
}
```

**撤回的硬约束**：

- 发送超过 **2 分钟**的消息不可撤回（`40064004`）
- 机器人是**群管理员**时，可以撤回自己的消息**和普通群成员的消息**；
  是普通成员时只能撤回自己发的
- 群成员的消息 ID 从 `GROUP_AT_MESSAGE_CREATE` / `GROUP_MESSAGE_CREATE` 事件的 `d.id` 取
  自己发的消息 ID 从发送接口的响应里取

> 撤回这条内核封装了（`retractGroupMessage`），但**只做了裸请求，没有预检**——
> 2 分钟时限和群管理员身份都是服务端判，失败了看错误码：`40064004` 超时、
> `40062003` 无权限。

### 内邀中，普通机器人调不通

页面明确标注「该能力正在内邀接入中，敬请期待」，调了会返回 `11253 应用无接口访问权限`：

| 接口 | 方法 | 路径 |
|------|------|------|
| 获取群成员列表 | GET | `/v2/groups/{group_openid}/members` |
| 获取群成员信息 | GET | `/v2/groups/{group_openid}/members/{member_openid}` |
| 群成员批量移除（踢人） | POST | `/v2/groups/{group_openid}/batch_remove_members` |
| 群黑名单查询 / 操作 | GET / POST | `/v2/groups/{group_openid}/member_blacklist` |

群成员列表每次最多返回 30 条、支持分页；批量移除单次最多 20 个、可同时加入黑名单。
要这些能力得找平台运营申请白名单。

**所以「群成员列表」的应对仍然有效**：只能记录发过言的人，主动授权用 `/admin set <openid>`。

`src/api.js` 提供了这些方法，插件通过 `ctx.api` 调用：

> 但它们同样要求机器人是群管理员：申请列表和审批直接要求，
> 自动审批策略则是「只有当机器人是该群管理员时才会生效运行」。
>
> 两个容易踩的点：
> - `executeJoinStrategy` 是**异步**的，约 10 分钟才跑完，别当同步接口等结果
> - 白名单填的是 **QQ 号码**，不是 openid；单次最多 10000 个、总上限 10 万

### 机器人是不是群管理员，能查

`GET /v2/groups/{group_openid}/bot_state` 返回 `member_role`：
`member` 普通成员 / `owner` 群主 / `admin` 管理员。禁言、踢人、入群审批
都要求 admin 或 owner，所以调用前可以先查它，省得撞 `40062003`。

框架封装成了 `canManageGroup()`：

```js
const st = await ctx.api.canManageGroup(msg.groupId);
// { ok: true, role: 'admin', reason: '机器人是群管理员' }
// { ok: false, role: 'member', reason: '机器人只是普通成员，没有群管权限' }
// { ok: false, role: null, reason: '查不到机器人角色：...' }
```

**禁言、踢人、入群审批默认会自动预检**——确认不是管理员就直接抛
`机器人在这个群没有管理权限：…`，不用插件自己 try/catch。
想跳过传 `{ precheck: false }`。

两个限制要知道：

1. **`bot_state` 本身是内邀接口**（`11253`）。没申请白名单的机器人查不了，
   此时 `canManageGroup()` 返回 `role: null`，框架**不拦截**，照样发请求让服务端判。
2. 它有 **30 QPM** 限制，框架带 60 秒缓存。批量操作不会每次都查。

## 三、免@粘性怎么工作

用户 @ 过一次后，该会话在 `session.stickySec`（默认 180 秒）内，
即使不 @ 也算「在跟机器人说话」。

> **2026-10-26 更正**：这条结论**是错的**。官方文档明确有
> `GROUP_MESSAGE_CREATE`「群消息（全量模式）」事件——
> *「当机器人开启了"接收所有消息"功能后，群里的每一条消息（不限于@机器人）都会推送此事件」*。
> 之前测不到不是平台不给，是**没在开放平台开启「接收所有消息」**。
> 全量模式下粘性窗口才有意义；在此之前它确实是「备而不用」。

```
用户 A: @机器人 开始游戏     ← mentioned=true，开启本会话 180 秒免@窗口
用户 A: 攻击                ← 没 @，但窗口内 → sticky=true, addressed=true
用户 B: 今天吃啥             ← 也在窗口内 → addressed=true（同样会传给插件）
```

**粘性按会话算，不是按人算**。最后一行是关键：同一个群里别人说话也会被标记成 `addressed`。

所以做「主动搭话」类玩法时，除了 `msg.addressed`，最好再确认是不是同一个人：

```js
const lastPlayer = await ctx.storage.get('global:lastPlayer');
if (!msg.addressed) return;
if (msg.userId !== lastPlayer) return;   // 不是正在玩的人，别接话
```

想关掉粘性：`config/bot.json` 里 `session.stickySec = 0`。

## 四、事件名的一个坑

官方文档写的是 `GROUP_AT_MESSAGE_CREATE`，但平台实际下发的还有 **`GROUP_MESSAGE_CREATE`**
（**2026-10-26 更正**：官方文档**明确列了这个事件**，叫「群消息（全量模式）」，
不是"未列出的事件名"）。两者载荷结构一致，代码里都认。

`GROUP_MESSAGE_CREATE` 是**群里所有消息**（需开启「接收所有消息」），不只是 @ 机器人的。
内核的处理方式是「**先给插件机会，没人理才丢弃**」：

1. 群消息一律先登记群档案
2. 命令（带前缀）走命令路由
3. 其余消息全部交给插件的 `message` 监听
4. 有插件回应了（发了消息，或 `return true`）→ 这条消息就算被消费
5. 没有任何插件回应 → 判定为噪音，静默丢弃，不产生任何输出

这样既能让「掷骰子」「打卡」这类关键词玩法在不 @ 的情况下生效，
也不会让机器人对群里每句话都插话。

> 插件想表达「这条我管了」有两种方式：调用 `msg.reply()` 等发送方法，
> 或者处理函数 `return true`。

## 五、实现要点（对照官方文档）

| 环节 | 实现 |
|------|------|
| 获取凭证 | `POST /app/getAppAccessToken`，`{appId, clientSecret}` |
| 鉴权头 | `Authorization: QQBot {access_token}` |
| 提前刷新 | 有效期 7200s，提前 120s 刷新；401 强制刷新重试一次 |
| 网关 | `GET /gateway/bot` → `wss://...` |
| 握手 | `op10 Hello` → `op2 Identify`（`token: "QQBot xxx"`） |
| 心跳 | 按 `heartbeat_interval` 发 `op1`，带最新 `s` |
| 断线 | 指数退避，有 session 走 `op6 Resume` 补事件 |
| 发群消息 | `POST /v2/groups/{group_openid}/messages` |
| 发私聊 | `POST /v2/users/{openid}/messages` |

## 六、其他已知限制

- **群主识别**：消息报文里 `author.member_role` 为 `owner` 的就是群主（只授予该群管理员），
  机器人收到该人消息时会自动记下来，比「谁邀请机器人」更准。没发过言的群主识别不到。
- **单进程**：插件与内核同进程，插件里写死循环会拖垮整个机器人。后续可换 `worker_threads`。
- **频道消息只收不发**：`guild` 场景没接 v2 发送接口，主要面向群聊/私聊。
- **未做分片**：单连接够用；进几千个群再考虑 `shard`。

### 富媒体上传的两层限制（2026-10-30 核对，踩过）

这是两个**完全不同**的限制，混为一谈会做出无效修复：

| 限制 | 数值 | 维度 | 超了会怎样 |
|---|---|---|---|
| 业务软限制 | 图 20MB / 视频 30MB / 语音 20MB / 文件 200MB | `file_type` | **降级为文件**（`file_type=4`），官方语义 |
| 二进制直传上限 | **5MB**（`file_data`） | 单次 HTTP 请求体 | 网关回 **413**（stgw 的 HTML，无业务错误码） |
| 硬限制 | 200MB | 文件本身 | 官方报 `850031`，分片也救不了 |

**关键教训**：一张 24.4MB 的图「降级为文件」后仍是同一个 `/files` 端点、同样整包 base64
（≈32.5MB body），照样 413——因为撞的是**请求体上限**，不是 `file_type`。
大文件唯一出路是分片上传。

- 分片大小由 `upload_prepare` 的 `block_size` 下发（默认 5MB），别自己定。
- `md5_10m` 取**前 10002432 字节**（官方写死的数字，不是 10MB）。
- 错误码：`40093001` 分片转存通道异常**可重试**（按 `retry_timeout`）；
  `40093002` 日发送容量上限**不可重试**，只能告诉用户明天再试。
- 单聊 / 群聊的上传与分片端点**互不通用**，必须同场景。
- `file_info` 有 `ttl`，过期要重传。
- **存储是 JSON**：适合中小规模。大型游戏存档建议插件里直接接 SQLite。
- **面板无登录态**：只有访问密钥校验，没有会话。别直接暴露到公网。
