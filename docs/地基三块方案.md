## 0. 能力边界：哪些抄不了

对标 `wangyufengsky/qq-agents`（跑在 NapCat/OneBot 上）与
`NoMindSama/qq-dsh-bridge`（跑在 SnowLuma/OneBot 上）。我们是**QQ 官方 API**，
这不是实现差异，是能力边界差异。

| 能力 | OneBot 系 | 我们（官方 API） | 应对 |
|---|---|---|---|
| 群标识 | 真实群号 | `chatId`（openid） | 全链路用 chatId，不假装有群号 |
| 同一个人跨群识别 | QQ 号全局唯一 | **字段名两套但值相同**：群读 `author.member_openid`、私聊读 `author.user_openid`（`message.js` 的 `buildMessage`） | 可以做跨群人物档案，主键 `(bot_id, openid)` |
| 跨 bot 关联 | QQ 号 | `User.union_openid`，**可能为空**（官方原文） | 有就用，没有不猜；建索引，不做主键 |
| 主动发消息 | 随时发 | 单关系 20/分 + 每群 1000/天，超了硬拒 | 预算按官方配额算 |
| 回合边界 | 自由 | 被动窗口：群 5 分钟 / 单聊 60 分钟；`msg_seq` 群 1–5 / 单聊 1–4 | 账本必须记 `msg_seq`，否则幂等无从谈起 |
| **拉历史消息** | 可拉 | **没有任何历史消息接口**（`endpoints.js` 的 17 个 GET 里没有） | 事件账本是**唯一**历史来源 |
| 引用回复 | `reply` 段可反查 | 引用原文能直接拿到（`message.js` 的 `quoted`）；索引从 `message_scene.ext` 的 `msg_idx` / `ref_msg_idx` 取 | 能建边，见 §1 |
| **能不能私聊** | 随时 | **两道门**：好友关系 + 资料卡里的主动推送开关。**都没有查询接口**，只能靠 6 个事件维护 | 见 §4 |

**结论：对方把账本当「更好的记忆」；我们把账本当「唯一的历史」。**

## 1. 事件账本（阶段 1）✅

### 1.1 为什么必须有

官方没有历史消息接口。`stats` 存的是聚合（不存正文），`journal` 存的是「她记得的事」。
**原始消息一条都没有**。后果：

- 检索原料是模型当时抽出的二手摘要——**记忆的上限被原料决定**
- 没有 `msg_seq` 上下文，幂等和场景片段都做不了
- 暂停期间的消息永久消失

### 1.2 表

```sql
CREATE TABLE events (
  seq          INTEGER PRIMARY KEY AUTOINCREMENT,  -- 账本序，稳定、不可重排
  id           TEXT NOT NULL UNIQUE,               -- uuid，对外引用用
  bot_id       TEXT NOT NULL,
  kind         TEXT NOT NULL,                      -- group / c2c
  chat_id      TEXT NOT NULL,
  msg_id       TEXT,
  user_id      TEXT,                               -- openid
  user_name    TEXT,                               -- 当时昵称（会变，故带 observed_at）
  content      TEXT NOT NULL DEFAULT '',           -- 正文（独立成列，见下）
  at           INTEGER NOT NULL,                   -- 消息时间
  observed_at  INTEGER NOT NULL,                   -- 本地收到时间
  time_basis   TEXT NOT NULL,                      -- message / observation / unknown
  dedupe       TEXT NOT NULL UNIQUE,               -- `${botId}:${msgId}`；无 msgId 时退化为 chatId+at+hash
  msg_idx      TEXT,                               -- 官方 message_scene.ext 的 msg_idx
  ref_msg_idx  TEXT,                               -- 引用别人的索引（可能是 REFIDX_ 或 TMP_）
  union_openid TEXT,                               -- 跨应用统一标识，可能为空
  quoted       TEXT,                               -- 引用原文
  payload      TEXT NOT NULL                       -- 原始 JSON（**已剔除 auth_token**）
);
-- 邻文查询要排除 unknown，把 time_basis 放进索引，避免回表过滤
CREATE INDEX events_timeline ON events(bot_id, chat_id, at, seq) WHERE time_basis != 'unknown';
CREATE INDEX events_user     ON events(bot_id, user_id, at);

CREATE TABLE event_refs (
  from_id   TEXT NOT NULL,   -- events.id
  to_id     TEXT,            -- 解析成功才有
  to_msg_id TEXT,
  kind      TEXT NOT NULL,   -- reply / quote
  resolved  INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX refs_from ON event_refs(from_id);
CREATE INDEX refs_to   ON event_refs(to_id) WHERE resolved = 1;
```

**库位置**：`data/bots/<id>/events.db`，每鸟一份，和 `stats.db` 同目录同生命周期。
于是 `seq` 是 **per-bot** 的，跨鸟不可比——面板跨鸟列表按各自 `seq` 展示，不能排序对比。

**为什么单独一个库**：保留策略不同（stats 90 天聚合 / events 7 天全文），隐私承诺相反
（`schema.js` 开头那句「只存聚合结果，不存消息正文」是对用户的承诺，不是技术选择）。
混一个库的话「这个库会不会被拷走」说不清。分库之后「想清掉聊天记录」变成删一个文件。

**`content` 为什么独立成列**：`payload` 有 256 KB 上限（防畸形报文撑爆库），
而截断 payload 就等于截掉正文。正文是账本最要紧的东西，不能跟 payload 共命运。
独立成列还有个好处：将来上 FTS/LIKE 必须有独立列，藏在 JSON 里查不了。

### 1.3 三个非显然的设计

**① `time_basis` 三分，不是可选项**

- `message`：官方给了 timestamp
- `observation`：官方没给 / 不可信，用本地收到时间
- `unknown`：导入、补录、迁移来的

`resolveTime()` 永远产生不了 `unknown`——判不准时它退回 `observation`，这是对的
（「不知道官方时间，但我知道我什么时候收到的」比「不知道」有用）。
`unknown` 的真实场景是**导入**：批量灌几年前的老聊天记录时，`Date.now()` 是导入时间。
所以有 `append(msg, { timeBasis })` 这个显式入口。

**`unknown` 的事件不参与时间邻文**。拿不可靠的时间拼上下文，拼出来的是
「看起来合理但错误」的对话，比没有更糟。

**② `seq` 与 `at` 分离**

分页用 `seq`（稳定），邻文用 `at`（语义）。历史补录只动 `at`，不动 `seq`——否则所有游标失效。
QQ 时间只精确到秒，同一秒内按 `seq` 排，保持到达顺序。

已实测：`node:sqlite`（Node 22.22.2）支持 `AUTOINCREMENT` 且删行后**不复用 seq**。

**③ 保留策略：events 一律 7 天滚动删，证据由 B 侧自己留**

| 数据 | 位置 | 保留 |
|---|---|---|
| 全部事件（含原文） | A 侧 `events` 表 | 7 天（`ledger.retentionDays`），滚动删 |
| 记忆的证据快照 | B 侧 `journal.evidence` 列 | 永久 |
| 命令类消息 | A 侧原 `messages` 表 | 按 `stats.retentionDays`（90 天） |

早期设想是「被 `journal.event_ids` 引用的事件永久保留」——**不可实现**：events 在 A 侧、
journal 在 B 侧，A 侧根本不知道 B 侧引用了哪些事件。要么加一条反向同步，要么换思路。
改成快照之后：events 可以无脑滚动删，跨进程依赖从「双向」降为「单向」，
代价是原文两边各存一份（200 字 × 记忆条数，可接受）。

**写入开销（实测）**：2000 条 233 ms，单条约 117 μs，折算 **8500 条/秒**。
QQ 单会话限频 5 条/秒、接口 100 QPS，同步写完全不是瓶颈——**不需要攒批**。
攒批的唯一好处是吞吐，代价是进程被 kill 时丢最后一批，而官方补不回来。

### 1.4 接口与插件视图

| 接口 | 说明 |
|---|---|
| `GET /api/ledger?chatId=&limit=` | 某会话最近 N 条（正序） |
| `GET /api/ledger/stats` | 总量、时间范围、未解析引用数、保留天数 |
| `GET /api/ledger/context?chatId=&seq=&before=&after=` | 以某条为锚点的前后邻文 |

`payload`（原始报文）**一律不返回**：前端只要正文和元信息，整包给出去只会把面板变成数据外泄面。

`ctx.ledger` 给插件的是**只读视图**（`recent` / `timeline` / `get` / `stats`）。
只读是防误用不是防恶意（插件同进程，拦不住真想绕的）。但 `append()` 一暴露，
插件就能往账本里塞「用户没说过的话」，而账本的全部价值就在于是原始事实。

### 1.5 欠

**面板页面没做**（等场景片段一起做）。现在只能通过 API 看。

## 2. 发送出口（阶段 2）✅

### 2.1 前提：发送有 4 个出口，不是 1 个

`Outbound.send()` 曾经不是唯一出口，这是本方案最重要的一处修正：

| # | 出口 | 位置 | 过 outbound？ |
|---|---|---|---|
| 1 | `msg.reply()` / `msg.send()` | `message.js` 的 `send()` | ✅ |
| 2 | `!outbound` 兜底 | 同上，`if (!outbound)` 分支 | ❌（线上不可达） |
| 3 | 面板 `/api/send` | `web/server.js` 的 `'/api/send'` 路由 | ✅ 已收编 |
| 4 | ai-chat `POST /r/send` | `ai-chat/index.js` 的 `registerRoute('POST','/send')` | ✅ 已收编 |

**出口 4 曾是最严重的缺陷**：`outbound.js` 的「2b) 主动消息额度」那段有完整的
额度记账（20/分、1000/天），但 dsh-roost 的主动消息走 `channel.js` → `/r/send` →
`api.sendGroup` **直发**，额度记账完全没参与。ai-chat 的注释当时写着
「限频的责任在调用方」，实际只有 dsh-roost 自己的 `maxPerDay: 3` 在兜。

**出口 2 保持原样**：`bot.js` 的 `init()` 里无条件 `new Outbound`，线上走不到这条分支；
留它是为了不打断单测和早期调用方。

### 2.2 收编后

**出口 3（面板）**：改调 `rt.outbound.send()`，`SendError` 按 code 分状态码——
`quota` / `rate` 回 429（等会儿能好），其余回 400（重试也不会好）。响应多一个 `pending`。

**出口 4（ai-chat）**：改调 `ctx.push(target, text, { kind })`，错误多带 `code`，
响应多 `pending`。老框架没有 `ctx.push` 时退回 `ctx.api` 但**打 warn**——静默退回等于账本又变回半真。

### 2.3 `quota` 必须拆成 `quota` + `rate`

同一个 `quota` 背后是两种现实：

| code | 含义 | 多久能好 |
|---|---|---|
| `quota` | 这个会话今天的主动额度用完了 | 等跨天 |
| `rate` | 这一分钟发得太密（20/分） | 等一分钟 |

混成一个 code，调用方只能按最坏情况处理——dsh-roost 的主动搭话会把一次「发得太密」
当成「今天说满了」，白白放弃一整天。反过来按最好情况处理，就是每分钟空撞一次到跨天。

`stats.rateBlocked` 单独计数。dsh-roost 侧按 code 分三路排期（`quota`→明天、
`rate`→1 分钟、其余→随机间隔）。

### 2.4 `pending`（304023 审核中）只透传，不落记忆

主动消息进审核时，ai-chat 返回 `ok: true, pending: true`。**既不是失败也不是送达。**

dsh-roost 那边**还没**据此决定要不要写「我说过」——那需要投递账本的状态机（§6）。
在这里顺手做等于把「她坚称自己说过一句话」押在一个 HTTP 响应字段上。

### 2.5 为什么 e2e 要读额度文件而不是只看 200

面板这条路由收编前**同样返回 200**，但额度账本里一条记录都没有。面板随手点几下
就能把官方额度打满，而账本上看不出任何事——**半真的账本比没有账本更糟，因为你会相信它。**

所以 e2e 的断言是读落盘的 `data/bots/main/quota.json`：发一条后该会话计数 +1。
这是这条链路唯一不可伪造的痕迹。

## 3. 暂停闸（阶段 3）✅

### 3.1 是什么

一句话：**任何一只鸟、任何一个会话，都能在不改配置、不重启的前提下闭嘴，
而且面板说得出「为什么不能说」。**

在这之前 `grep -rn "paused" src/` 零命中。人格写飞、模型抽风、群选错了，
重启之后立刻对几个群开口，**没有刹车**——唯一能止住的办法是关进程，那连别的鸟一起停了。

三级闸取「与」，任一道关着就不说话：

```
global（进程级）  →  bot（每只鸟）  →  chat（每个会话）
                                    ↘ silence（静默：带 until，到期自动解除）
```

| 级别 | 谁改 | 语义 |
|---|---|---|
| global | 面板 / `--paused` 启动参数 | 全停 |
| bot | 面板 | 这只鸟停 |
| chat | 面板 / 插件 API | 这个会话停 |
| silence | 模型（`<<silence:2h>>`）/ 插件 | 到期自动解除 |

**存储**：`data/gate/<botId>.json` + `data/gate/global.json`（`DIRS.gate`）。
按鸟拆文件——共用一个 `gate.json` 时 `.tmp` + `rename` 只能保证「不会写坏」，
**不能保证不丢更新**（两只鸟同时改，后写覆盖前写）。

**静默存绝对时间戳不存剩余毫秒**：`{ chatId: untilMs }`。剩余时间在进程重启后要重算，
而「到几点解除」是事实，重启也成立。

### 3.2 接入点

```
bot.js:  ledger.append（记账，永远不拦）
     →   pipeline.run: gate → dedup → whitelist → ratelimit → cooldown → plugin
```

**顺序是关键：先入账，再过闸。** 账本不在 pipeline 里，它是 `pipeline.run()` 之前的一次同步写。
所以闸排在 pipeline 最前面也挡不住入账——暂停期间的消息照样进账本，恢复后能补看
「你不在的时候群里聊了什么」。

如果闸放在账本之前，暂停就等于丢消息，而官方没有历史消息接口，丢了补不回来。
e2e 专门去账本里查暂停期间那条消息来守这个顺序。

闸拦下时**不回任何话**：静默才是目的，回一句「我暂停了」等于没闭嘴。

### 3.3 「不能说话的原因」

`BotRuntime.canSpeak(chatId, { kind }) → { ok, reasons[] }`：

```js
['gate:global', 'gate:bot', 'gate:chat', 'gate:silence',
 'reach:not-friend', 'reach:push-off',      // 只查主动消息，见 §4
 'gateway:offline', 'quota:daily', 'quota:permin']
```

**没放在 `Outbound` 里**：outbound 是发送执行器，只知道额度和离线，不知道闸；
而这个方法要回答的是「这只鸟现在能不能开口」，是**运行时诊断**，不是发送动作。
放在 bot 上还能省掉 `botId` 参数——outbound 本来就是每鸟一个实例。

**`kind` 决定要不要查可达性**：`c2c` 查好友关系 + 推送开关，`group` 查群推送开关。
**不传就不查**——不知道是群还是私聊就查不了，而「不知道」不该变成「不能」。

面板每只鸟的卡片直接列 `reasons`，文案是中文。**故障排查从「猜」变成「读」**。

### 3.4 三个不显然的决策

**① 多鸟各缓存一份全局闸，光写文件不够。**

每只鸟各有一个 gate 实例，各自在内存里缓存一份 `global.json`。面板点「全局暂停」
只写了一个文件，其他鸟的实例还拿着旧值——表现是「点了暂停，另一只鸟照常说话」。
补了 `reloadGlobal()`，`POST /api/gate` 写完之后逐个通知。

这是「进程内缓存 + 文件共享状态」的通病：**有两份副本就要想清楚谁通知谁**。

**② `pauseOnStart` 不需要安装向导。**

原设计问的是「首次配置由谁生成」，其实需要的是**判断「这是不是第一次」**：
`gate.open()` 返回 `botExisted`（闸文件在不在），`bot.js` 拿它决定要不要自动暂停。

默认 `false`，且只在首次运行生效。**每次启动都暂停会让人以为坏了**——重启之后不说话，
第一反应是「出故障」，不是「等我确认」。

**③ `--paused` 只改内存不写盘。**

`setGlobal(..., { persist: false })`。这个参数表达的是一次性意图「这次先别说话」；
写进 `global.json` 的话，下次不带参数启动却发现还在暂停，人会以为程序坏了。

### 3.5 不做什么

- 不做「按插件暂停」（插件启停已有自己的机制，别叠两层）
- 不做审批流（那是权限模块的事，不是闸的事）
- 不做「暂停时回一句『我暂停了』」——静默才是目的
- `plugin:disabled` 不列进 `canSpeak`：「某插件被停用」不等于「这只鸟不能对这个会话说话」，
  它只是少了一个可能回应的人

### 3.6 `<<silence:2h>>` 的三个坑

**① 必须先提取、再摘标记。**

ai-chat 的 `parseActions` 和 dsh-roost 的 `fire()` / `parseVerdict()` 都会
`raw.replace(/<<[^>]*>>/g, '')` 把标记一把抹平。抹掉之后再想拿「要安静多久」就没处找了。

这个错**极隐蔽**：标记被正常摘掉、正文正常发出，只是静默悄悄没了——没有报错，没有现象。

**② 静默要两边都记。**

框架的闸拦的是 pipeline（收到的消息），而主动搭话走 outbound、**不经过 pipeline**。
只记框架那边的话，她说完「让我静静」，私聊里照样被主动搭话叫醒。
所以 `speakup` 另记一份 `silenceUntil`，`shouldFire()` 里挡一道。

**③ 只有静默、没有正文是合法的。**

`<<silence:2h>>` 单独出现就是「我要安静，没什么要说的」——既不该发一条空消息，
也不该当成错误拒掉。`/r/send` 为此返回 `silentOnly: true`。

时长上限 30 天：`<<silence:9999h>>` 那种等于永久静默，恢复只能靠面板。

## 4. 可达性（阶段 3.5）✅

### 4.1 官方给的是两层开关，不是一层

| 层 | 事件 | 官方原话 |
|---|---|---|
| 好友关系 | `FRIEND_ADD` / `FRIEND_DEL` | 用户添加/删除机器人 |
| **单聊主动推送** | `C2C_MSG_REJECT` / `C2C_MSG_RECEIVE` | 「用户在机器人资料卡手动关闭主动消息推送时触发。**关闭后机器人无法向该用户发送主动消息**」 |
| 群主动推送 | `GROUP_MSG_REJECT` / `GROUP_MSG_RECEIVE` | 群管理员关闭/开启主动消息推送 |

**有好友 ≠ 能主动发。** 用户可以在资料卡里单独关掉主动推送，关了之后即使好友也发不出去。

### 4.2 没有查询接口，但有事件

官方 sitemap 里 `friend` 只有两个**事件页**，**没有任何好友查询 API**——
`endpoints.js` 的 17 个 GET 里也没有。

所以状态只能这样维护：接入之前就存在的关系**未知**（事件是增量，不补发历史）；
接入之后的变化**精确**（订阅 6 个事件，落地即更新）。

**存储**：`data/bots/<id>/reach.json`（500ms 延迟合并写 + `timer.unref()`）。
数据量小（每 bot 几百条），为它单独开一张表要拉进 sqlite 连接和迁移，不值。JSON 还能人工直接改。

```js
// 每个 openid 一条
{ is_friend: 1|0|null, c2c_push: 1|0|null, group_push: { [groupOpenid]: 1|0 },
  evidence: 'friend_add' | 'c2c_msg_reject' | 'observed_c2c' | 'send_failed' | 'manual',
  updated_at }
```

### 4.3 判定顺序与 `NULL`

```
canC2C(bot, openid):
  is_friend === 0                     → 不可（reach:not-friend）
  c2c_push  === 0                     → 不可（reach:push-off）   ← 有好友也不行
  is_friend === 1 && c2c_push !== 0   → 可
  其余（NULL）                        → 未知，不拦，但发送失败要记 evidence
```

**`NULL` 不能当 `0` 用。** 未知不等于不可达——群里聊过的人，可能已经加了好友只是没私聊过。
把未知当不可，会让主动搭话永远开不了口。

### 4.4 错误码

| 码 | 含义 | 对 reach 的影响 |
|---|---|---|
| `40054004` | 无好友关系 | `is_friend = 0` |
| `40054013` | 用户拒收消息 | `c2c_push = 0` |
| `40054006` | 验证好友关系失败 | **不改**——官方要求「重试」，不是终态 |
| `40034101` / `40054003` | 机器人非群成员 | 群档案标失效 |
| `40054002` | 机器人被禁言 | 临时，**不是**不可达 |
| `40034100` | 主动消息超频控 | **不是**不可达，别误标 |

**`40054006` 不改状态这一条最关键。** 它是「验证失败」不是「验证不通过」，
一次网络抖动就会把它打出来；如果照 `40054004` 一样标 `is_friend=0`，
抖一下就把一个真好友永久静音，而且没有事件能把他救回来（除非他再发消息）。

### 4.5 人工标注的语义陷阱

字段传 `undefined` 是「这项不动」，传 `null` 是「重置为未知」。
用 `??` 或真值判断会把这两者混掉——用户在面板上改「好友」时，「推送」会被悄悄清空，
界面上没有任何提示。

### 4.6 接进 `canSpeak`

`bot.canSpeak(chatId, { kind })` 里查，`verdict === 'no'` 时映射成
`reach:not-friend` / `reach:push-off`。`unknown` 一律放行。

`kind` 不给就不查（见 §3.3）。

## 5. 场景片段（阶段 4）✅

### 5.1 做什么

`journal` 加两列：`event_ids TEXT`（JSON 数组，这条记忆从哪几条消息来）和
`evidence TEXT`（原文快照）。检索命中后：

```
journal 命中 → event_ids → 取原文
             → 以命中事件为锚点，取前后各 2 条（时间窗 ≤10 分钟）
             → 按 (at, seq) 排序返回
```

返回时每条标记 `hit` / `neighbor` / `quoted`。**相邻不等于同一话题**——这点要写进提示词，
不能因为挨着就当因果。

`journal.evidence` 存 `[{eventId, at, sender, excerpt}]`，`excerpt` 是原文前 200 字。
写 journal 时**复制**进来，不是引用（理由见 §1.3 ③）。

### 5.2 已读水位：**这个设计在我们的架构下不需要**

原方案要求每个 `(bot_id, chat_id)` 记一条 `read_through_seq`，目的是
「不越过未见间隙」——防止模型以为自己看过中间的对话。

**但那是「把最近原文流注入上下文」的架构才需要的东西。** 我们的注入是
`journal` 的**记忆摘要**，不是原文流；原文只在 `memory_search` 时按需拉，
而拉的时候 `around` 已经是完整的前后文（`timeline` 带 `hit` / `neighbor`），
不存在「中间有没看过的空隙」。

所以这条**不做**。记在这里是因为：将来如果改成「注入最近 N 条原文」，
这个设计立刻就需要，到时候照抄 §5.2 原来的写法即可。

> 唯一保留的前提：`seq` 在跨进程语义上稳定。已实测 `AUTOINCREMENT` 不复用 seq。

### 5.3 落点

| 环节 | 做法 |
|---|---|
| `journal` 加列 | `event_ids` / `evidence`，**老库靠 `ALTER TABLE` 补**——`CREATE TABLE IF NOT EXISTS` 对已存在的表什么都不做，不补的话 insert 报 `no such column`，而新装的人是好的，这种只影响升级用户的错最难查 |
| 桥 1（A→B） | 入账返回值挂到 `msg.eventId`，ai-chat 转发时带 `eventIds`（合并批就是多条） |
| 桥 2（B→A） | ai-chat 新增 `GET /r/context?aroundId=&before=&after=`，返回带 `role: hit/neighbor` 的邻文 |
| 写记忆 | `journalAdd` 带上 `eventIds` + `evidence`（整段快照，不逐条——合并批拆不回去） |
| 消费 | `memory_search` 命中后**前 2 条**补邻文，其余只给摘要 |

**为什么只补前 2 条**：5 条 × 5 段邻文 = 25 段，会把这个工具的返回撑得比它要回答的问题还大。

**为什么 `evidence` 存整段而不是逐条**：合并窗口已经把正文拼成一段，拆不回原来那几条。
快照的用途是「events 7 天后删了还能看到当时说了什么」，整段正好满足；
要逐条回看原文，用 `eventIds` 调 `/r/context`。

**`/r/context` 找不到时返回 `gone: true` 而不是空数组**：events 只留 7 天，
更早的记忆里 `evidence` 还有快照。「查不到」和「没人说过」是两件事，
返回空数组会让宿主以为这条消息不存在。

### 5.3 验收

检索命中时带出前后文；`unknown` 时间不参与；events 删了之后旧记忆的证据仍在。

## 6. 投递账本（阶段 5）❌ 未开始

### 6.1 目标

**发出的每一条消息都有据可查，且永远不会因为「不确定」而被重发。**

现状：发送链路上 `grep outbox` 零命中，`requestId` 只有 `dsh-roost/src/update.js`
里那个更新安装用的。现在靠**顺序**绕——「『我说过』必须挂在发送成功之后」。
这在 `msg_seq` 群 1–5 / 单聊 1–4 的约束下很脆：一次超时重发就撞上限流，
还会把「我说过」写进记忆，形成自洽幻觉。

### 6.2 状态机

```
                    ┌──────────── 304023 ──────────→ audited（等审核事件）
                    │
created → pending ──┼──────────── 有 msg_id ─────→ sent
                    │
                    ├── 超窗 / 配额 / 离线 / 限流 → failed（可重试）
                    │
                    └── 超时 / 5xx / ECONNRESET ──→ unknown（**永不自动重发**）
```

三个非显然的点：

1. **`audited` 不是成功也不是失败。** `outbound.js` 的 `CODE_AUDIT = 304023`，
   官方说「识别为 pending，不当失败」。**术语要统一**：官方文档里的 `pending` 指
   「结果未确定」，账本里的 `pending` 指「尚未发出」。方案采用 `audited` 作独立状态，
   避免两个 `pending` 打架。审核期间**不能回写「我说过」**。
2. **`unknown` 必须存在。** 网络超时后我们**无法知道**服务端是否收到。
   原则是「未知结果必须人工核对，绝不自动重发」，因为官方配额下重发的代价更高。
3. **`pending` 会在崩溃后残留。** 启动时扫一遍，全部转 `unknown`。
   不做这一步，重启后这些记录永远卡住。

### 6.3 表

```sql
CREATE TABLE deliveries (
  request_id  TEXT PRIMARY KEY,   -- 幂等键，由调用方给
  bot_id      TEXT NOT NULL,
  kind        TEXT NOT NULL,      -- group / c2c
  chat_id     TEXT NOT NULL,
  reply_to    TEXT,               -- 被动回复时的 msg_id
  msg_seq     INTEGER,            -- 群 1..5 / 单聊 1..4，官方硬限制
  digest      TEXT NOT NULL,      -- 前 120 字 + 总长 + sha1 前 8 位
  state       TEXT NOT NULL,      -- pending/sent/audited/failed/unknown
  msg_id      TEXT,
  code        TEXT,
  attempts    INTEGER NOT NULL DEFAULT 0,
  created_at  INTEGER NOT NULL,
  settled_at  INTEGER
);
CREATE INDEX deliveries_chat ON deliveries(bot_id, chat_id, created_at);
CREATE INDEX deliveries_open ON deliveries(state) WHERE state IN ('pending','unknown');
```

**`digest` 不存全文**——沿用 `schema.js` 的原则「只存聚合结果，不存消息正文」。
全文只在事件账本里（且受保留策略约束）。

**库位置**：并进每鸟的 `stats.db`（同为 bot 侧、同生命周期，且都不含正文）。

### 6.4 `request_id` 谁来生成

**dsh-roost 的 `qq_send` 生成**，不是框架。理由：`qq-tools.js` 写明
「`qq_send` 每调一次是一段独立消息」，只有它知道「一段话」的语义边界。

**跨进程要传**（见 §7）：`qq_send` → `channel.js` 的 POST body 加 `requestId`
→ ai-chat `/r/send` 透传 → `outbound.send({ requestId })`。
现在 `channel.js` 的 body 里还没有这个字段。

同 `request_id` 再调一次的语义：

| 当前状态 | 行为 |
|---|---|
| `sent` / `audited` | 直接返回上次结果，**不重发** |
| `unknown` | 返回 `unknown`，不重发，提示「请到面板核对」 |
| `failed` | 允许重试（复用同一行，`attempts += 1`） |
| `pending` | 返回「正在发送」，拒绝并发 |

### 6.5 `classify(e)` 的映射

`SendError.code` 有五种：

- `offline`、`expired`、`quota`、`rate` → **确定 `failed`**（消息一定没发出去）
- `api` → 看具体错误码：明确的 4xx → `failed`；超时、5xx、连接重置 → `unknown`

### 6.6 与记忆的耦合（这才是收益）

`dsh-roost` 写日记前查账本：只有 `sent` 才允许写入「我说过 X」。
这条现在靠调用顺序，改造后靠**状态查询**——顺序会被并发打乱，状态不会。

### 6.7 验收

同一 `request_id` 连调两次只发一条；kill 进程后 `pending` 变 `unknown`；
`audited` 能被审核事件结算。

## 7. 跨进程数据边界

bot 框架和 dsh-roost 是**两个进程、两套数据目录**，账本和记忆不在同一侧。

```
进程 A：bot 框架        DIRS.data = <HOME>/data
                        收消息、发消息、outbound、gate、events
                        ← events.db 在这里

进程 B：dsh-roost        dataDir() = <DSH>/data/roost
                        记忆、情绪、日记、图谱
                        ← journal.sqlite / graph.sqlite 在这里

桥：ai-chat 插件（跑在 A 里）
    A → B：转发消息（带 eventId）
    B → A：POST /api/plugins/ai-chat/r/send（主动发消息）
```

**三条硬约束：**

1. **events 只能在 A 侧**。收消息发生在 A，B 停了 A 还在收。若把账本放 B，dsh-roost 一重启就断档。
2. **journal 只能在 B 侧**。记忆的抽取/摘要/评分都要调模型，那是 B 的职责。
3. **跨进程的桥必须列全。**

| # | 方向 | 用途 | 形态 | 状态 |
|---|---|---|---|---|
| 1 | A → B | 转发消息时带 `eventId` | 现有转发通道加字段 | ✅ 已建 |
| 2 | B → A | 取邻文 `GET /r/context?aroundId=&before=&after=` | 新增只读路由 | ✅ 已建 |
| 3 | B → A | 查投递终态 `GET /r/delivery/:requestId` | 新增只读路由 | 未建（阶段 5 需要） |

**桥 3 为什么需要**：`audited`（304023）时 B 拿到的是「待审核」，不知道最终结果。
B 不能靠「等推送」——`MESSAGE_AUDIT_PASS` / `MESSAGE_AUDIT_REJECT` 事件到的是 A 侧。
最省事的做法是 **A 收到审核事件时更新账本，B 下次写记忆前拉一次终态**，不搞推送。

**路由现状**：ai-chat 只注册了 `POST /send` 和 `POST /reply`，**没有 `/status`**。
`channel.js` 的 `ping()` 调 `/r/status` 会 404，但 `ping()` 全仓没有调用点，是死代码。
新增路由时一并补 `/status` 或删掉 `ping()`。

**退化方案**（不想加跨进程路由时）：把 events 也放 B 侧，由 ai-chat 把每条消息 POST 给 B。
代价是每条消息一次 HTTP，且 **B 停摆期间丢档**——而官方没有任何历史接口可以补。
所以倾向保留桥方案：桥是只读路由（B 挂了不影响 A 收消息），退化方案是写路由（丢数据）。

## 8. 待办与已知问题

### 8.1 方案内的待办

| 项 | 归属 | 说明 |
|---|---|---|
| 事件账本的面板页面 | 阶段 1 欠 | 等场景片段一起做 |

| 投递账本本体 | 阶段 5 | 见 §6 |

### 8.2 已知问题（不属于三块，但记在这里）

**① 群主动的 skip 会无限烧钱。**

`awake.wakeGroups` 每 5 分钟一轮，每个候选群一次 `compose()`（= 一次模型调用）。
`!v.speak` 时**什么状态都不改**，而候选条件（冷场 45 分钟）一旦满足就一直满足。

清醒时段 15 小时 = **180 轮/天 × 群数**，全部返回 skip 也照烧。
`count` 只在发送成功时 +1，所以模型一直 skip 就无限问下去。

对照：`speakup`（私聊）skip 后 `state.nextAt = scheduleNext(cfg)` 退避 3–8 小时，没这个问题。

**修法（未实施）**：指数退避——连续 skip 1 次等 15 分钟、2 次 30 分钟、3 次 60 分钟、
4 次起封顶 2 小时。`noteUser`（有人说话）、发送成功、跨天三个条件清零。
`compose` 抛错也计入（模型挂了同样是每 5 分钟白重试一次）。

**注意退避只拦「主动插话」**：@她 / 回复她走的是被动回复（pipeline → ai-chat → DSH），
完全不经过 awake，不受影响。

**② 上下文压缩的阈值可能偏低。**

`compact.js` 的阈值是 60%（群）/ 40%（单聊），压缩方式是**开新会话 + 摘要开场**。
而每次换会话都会让 prompt cache 整段失效——注释里已经认识到这一点，所以从 25% 提到了 40–60%。

但对照 `qq-dsh-bridge` 的实测（阈值 0.15 → 0.95，单步 45–55 秒 → 3–4 秒），
40% 仍然偏低。他们的做法是「对话中 0.95 永不压缩 + 闲置 30 分钟才做边界压缩」，
把全量重算的代价挪到没人在等的时候。

我们暂时做不到他们的「原地 `/compact`」（`dsh-roost` 里 `grep slash` 零命中，
没有 DSH 的 slash RPC 通道），但**提高阈值 + 挪到闲置边界**是可以做的。

**前置条件**：先能观测 cache 命中率。没有观测就改，改完也不知道有没有用。

**③ `decide: 'mention'` 和 `awake.groups` 同时开着会打架。**

`decide: 'mention'` 模式下普通群消息不转发给 DSH，`awake.noteUser` 不会被调用，
`lastUserAt` 不更新。结果是「只在 @ 时回复」的群，反而在**实际有人聊天**的时候
被判定成冷场，然后主动插话。

不是 bug，是配置冲突。文档要写一句：要「只在 @ 时回复」，就别把这个群加进 `awake.groups`。

**④ 人格成长（selfNote）未做。**

`qq-dsh-bridge` 的记忆是四层 + 一层：L0 原文 / L1 会话摘要 / L2 长期事实 / L3 产物索引
+ **L4 `selfNote`（它对自己的叙述）**。前三层记的是「你」，第四层记的是「它」。

设计上最讲究的一点：**只在新会话第一次唤醒时读一次**，因为「每轮灌进去就变成
别人每隔十秒告诉你你是谁，那不是成长，是洗脑」。

我们的 `journal` 有 mood、persona、事实，但没有「它对自己的叙述」。
这是 P1（人格成长）的一部分，本方案明确不做（见 §9.3）。

**⑤ 群聊的 preset 物理隔离可以考虑。**

`qq-dsh-bridge` 的 owner / 只读 / 仅聊天是**三个独立 preset**，工具面在 preset 层
就不一样——群里那个 agent 的进程里根本没有本地工具，越权在物理上不可能。

我们是运行时检查（`permissions.js` 的 bucket + `can()`）。差别是：他们靠「没有」，
我们靠「拦住」。一处检查漏了就是缺口。

值得评估：群聊场景要不要改成「根本不注册本地工具」。

### 8.3 发布相关

`sums:verify` 现在会红——指纹对应 v0.8.14 tag 的 tarball，不跟工作区走。
下次 bump 时一起重跑。CI 的 `sums:check` 只查「当前版本有没有指纹条目」，不受影响。

## 9. 决策日志

这一节保留**为什么变成现在这样**。只记结论和踩过的坑，不记过程。

### 9.1 能力核实（v2–v6）

| 问题 | 结论 |
|---|---|
| 引用回复能否建边 | 官方给了完整机制：非机器人消息取 `message_scene.ext.msg_idx`，机器人自己发的取发送响应的 `ext_info.ref_idx`。不需要实测 |
| 群和私聊的 openid 是否同一个 | **是**（字段名两套 `member_openid`/`user_openid`，值一套）。跨群人物档案可做，主键 `(bot_id, openid)` |
| 跨 bot 能否关联 | `union_openid` 可能为空，存但不当主键 |
| 同一条消息会不会重复推送 | **会**（官方原文「相同 msg_id 可能重复推送」）。`dedupe` 必需且 `msg_id` 可用 |
| 304023 有没有对应事件 | 有。`MESSAGE_AUDIT_PASS` / `MESSAGE_AUDIT_REJECT`（intent 27） |
| 非好友 / 关了推送分别返回什么码 | `40054004` / `40054013`；另 `40054006` 要求重试，**不改状态** |
| 有没有历史消息接口 | **没有**，17 个 GET 里没有 |
| `ref_msg_idx` 的 `TMP_` 前缀与 `REFIDX_` 是否同命名空间 | 只能实测。不影响建表——两列都是 `TEXT`，对不上时退化成「只存边不建链」 |

### 9.2 实现时的四处「和设计不一样」

**① 事件账本单独一个库，不并进 `stats.db`。** 保留策略和隐私承诺都相反（见 §1.2）。

**② 同步写，不攒批。** 实测 117 μs/条，攒批只省吞吐，代价是 kill 时丢最后一批。

**③ `canSpeak` 从 `Outbound` 挪到 `BotRuntime`。** outbound 不知道闸，也不知道插件启停。

**④ 多鸟各缓存一份全局闸，需要 `reloadGlobal()`。** 这是「进程内缓存 + 文件共享状态」的通病。

### 9.3 明确不做

- **不替换现有检索栈**。`journal` 的 BM25 + 向量 RRF（k=60）+ 图谱三路召回，设计上强于对方。
  但向量默认是关的（`memory.embedding` 没填就不启用），默认配置下实际只有 BM25 + 图谱两路。
- **不重写 `journal`**。`journal` 是「她记得的」，`events` 是「发生过的」，生命周期不同。
  本轮只给 journal 加两列（`event_ids` / `evidence`），不改它现有的检索与衰减逻辑。
- **不做多后端抽象**（DSH/Codex/OpenAI 三选）。插件体系已经解耦了后端。
- **不做 self 版本化**（人格成长）。它是独立议题，别和账本一起做——账本是地基层面的改动，
  混进产品功能会失控。
- **不做 `is_wakeup` 互动召回**。它是「主动找谁」的策略层，得先有投递账本才知道哪条发过。
  **没有账本就上召回 = 重复骚扰**。
- **不做 `msg_type=6` 输入中状态**。仅单聊、最长 60 秒，属体验项。
