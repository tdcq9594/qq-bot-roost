## 0. 先说清楚：哪些抄不了

对方跑在 NapCat/OneBot 上，我们跑在 QQ 官方 API 上。这不是实现差异，是**能力边界差异**，方案必须按我们的边界重画。

| 能力 | 对方（OneBot） | 我们（官方 API） | 方案应对 |
|---|---|---|---|
| 群标识 | 真实群号 | `chatId`（openid） | 全链路用 chatId，不假装有群号 |
| 同一个人跨群识别 | QQ 号全局唯一，`people` 表可合并 | **字段名两套但值相同**：群读 `author.member_openid`、私聊读 `author.user_openid`（`src/message.js:220-228`），官方 `User` 对象还有 `id`（「用户唯一标识（OpenID 格式）」）。**官方文档示例里三者在群/私聊场景下是同一个值**（`group_at_message_create.html` 与 `c2c_message_create.html` 的示例均为 `A1B2C3D4…`） | **可以做跨群人物档案**，主键 `(bot_id, openid)` |
| 跨 bot 关联 | QQ 号 | `User.union_openid`：**跨应用统一用户 OpenID，但「可能为空」**（官方原文）。示例里有时有值、有时是 `""`，群消息示例里干脆没这个字段 | 有就用，没有不猜；`union_openid` 建单独索引，不做主键 |
| 主动发消息 | 随时发 | 单关系 20/分 + 每群 1000/天，超了硬拒（`docs/官方接口限制.md:16`） | 预算按官方配额算，不用自建预算 |
| 回合边界 | 自由 | 被动窗口：群聊 5 分钟 / 单聊 **60 分钟**；`msg_seq` 群 1–5 / 单聊 **1–4**（`官方接口限制.md:14-15`） | 账本必须记 `msg_seq`，否则幂等无从谈起 |
| **拉历史消息** | 可拉 | **没有任何历史消息接口**。`src/endpoints.js` 的 17 个 GET 里没有；`dsh-roost/src/channel.js` 头注释明确写「QQ 没有…没有历史消息接口」 | 事件账本是**唯一**的历史来源 |
| 引用回复 | `reply` 段可反查 | 引用原文能直接拿到（`src/message.js:344` 的 `quoted`）；被引用消息的索引从 `message_scene.ext.msg_idx` / `ref_msg_idx` 取 | **能建边**，见 §4 #1 |
| **能不能私聊** | 随时 | **两道门**：好友关系（加好友受平台白名单限制）+ 用户资料卡的主动推送开关。**都没有查询接口**，只能靠 6 个事件维护 | 见 §1.5 可达性 |

**结论：对方把账本当作「更好的记忆」；我们把账本当作「唯一的历史」。** 优先级比他们更高，不是可选项。

## 1. 暂停闸（最小、最独立）

### 目标
一句话：**任何一只鸟、任何一个会话，都能在不改配置、不重启的前提下闭嘴；并且面板说得出「为什么不能说」。**

现状（v9 之前）：`grep -rn "paused\|isolated" bot/src` 零命中——一只鸟配错了，重启后立刻对几个群开口，没有刹车。**已落地，见下方「落点（v9）」。**

### 三级闸 + 一个派生状态

```
global（进程级）  →  bot（每只鸟）  →  chat（每个会话）
                                    ↘ silence（静默：带 until，自动解除）
```

四者取**与**：任一道关着就不说话。

| 级别 | 谁改 | 语义 |
|---|---|---|
| global | 面板 / `--paused` 启动参数 | 全停 |
| bot | 面板 | 这只鸟停 |
| chat | 面板 / 插件 API | 这个群停 |
| silence | 模型（**新增** `<<silence:2h>>` 动作标记）/ 插件 | 到期自动解除 |

> **v10 补：`<<silence:2h>>` 已实现。** 解析在 ai-chat 的 `parseActions`（`decide.js`），执行在 `ctx.gate.silence()`。
> 注意 ai-chat 的动作标记清单已经变过一轮，现在认识的是 `<<remember:>>` / `<<remember-here:>>` / `<<forget:>>` / `<<clear>>` / `<<image:>>` / `<<voice:>>` / `<<button:>>` / `<<say:>>` / `<<close:>>` / `<<mood:>>` / `<<silence:>>`，而 `skip` 用的是**单尖括号** `<skip>`（`decide.js` 的 `SKIP_MARK`）。
> 记忆和人设类标记的执行已经整体挪到 dsh-roost，ai-chat 只负责「认识并摘掉」。

**存储位置**：`DIRS.gate` = `data/gate/`，**按鸟拆文件**：`<botId>.json` + `global.json`（`src/paths.js` 的 `DIRS.gate`）。用现成的原子写（`.tmp` + `rename`），和 dsh-roost 的 `memory.json` / `mood.json` / `closing.json` 同一套做法。

> 为什么在 bot 侧而不是 dsh-roost：闸拦在 pipeline 里，dsh-roost 停了 bot 还在收消息，闸必须比 dsh-roost 活得久。

> **并发写（v4 补）**：多鸟共用一个 `gate.json`，`.tmp` + `rename` 只能保证「不会写坏」，**不能保证不丢更新**（两个鸟同时改，后写覆盖前写）。两个选择：
> - 简单：进程内串行化（一个 Promise 队列），写前重读、只改自己的 key；
> - 干净：按鸟拆文件 `gate/<botId>.json` + 一个 `gate/global.json`，只有全局闸需要跨鸟串行。
>
> 倾向后者，因为全局暂停本来就是低频写。

### 接入点

`src/pipeline.js` 已经是洋葱模型，加一个中间件即可，**不动分发逻辑**：

```
bot.js: ledger.append（记账，永远不拦）
     → pipeline.run: gate → dedup → whitelist → ratelimit → cooldown → plugin
```

账本**不在 pipeline 里**——它是 `pipeline.run()` 之前的一次同步写。所以闸排在 pipeline 最前面也挡不住入账。

**顺序是关键：先入账，再过闸。** 暂停期间的消息仍然落进事件账本，恢复后 AI 能看见「你不在的时候群里聊了什么」。

> **依赖关系**：这一步只有在 §3 事件账本存在时才有意义。若先上暂停闸，则暂停＝丢弃消息，需在文档和面板明说。**建议与 §3 同批上线，或本节先只做「不发」不做「不丢」。**

### 「不能说话的原因」
`BotRuntime.canSpeak(chatId, { kind }) → { ok, reasons[] }`（v9 起在 bot 上，不在 outbound）：

```js
['gate:global', 'gate:bot', 'gate:chat', 'gate:silence',
 'reach:not-friend', 'reach:push-off',        // v10 补：只查主动消息
 'gateway:offline', 'quota:daily', 'quota:permin']
```

`kind` 决定要不要查可达性（`c2c` 查好友关系 + 推送开关，`group` 查群推送开关）；
**不传就不查**——不知道是群还是私聊，而「不知道」不该变成「不能」。
```

面板每只鸟的卡片直接列出来，文案用中文。**故障排查从「猜」变成「读」**——这是对方做得最好的细节。

### 不抄的默认值

对方**每次启动自动全局暂停**。我们不抄这个默认值：

- 他们是「先隔离检查再放开」的探索型产品，我们是长期挂机的生产型框架；
- 重启后不说话，用户第一反应是「坏了」，不是「等我确认」。

**折中**：`gate.pauseOnStart` 默认 `false`，且**只在首次运行**（闸文件还不存在）时生效，并在面板概览页显示「已暂停」。首次安装要确认，日常重启不添堵。

> **v9 落地**：不需要安装向导。`gate.open()` 返回 `botExisted`（闸文件在不在），`bot.js` 拿它决定要不要自动暂停——原设计问的是「首次配置由谁生成」，其实需要的是「判断这是不是第一次」。
>
> 另有 `--paused` 启动参数：**只改内存不写盘**（`setGlobal(..., {persist:false})`）。它表达的是一次性意图「这次先别说话」；写进文件的话，下次不带参数启动却发现还在暂停，人会以为程序坏了。

### 落点（v9：已落地）

| 原设计 | 实际做法 | 差异原因 |
|---|---|---|
| `Outbound.canSpeak(botId, chatId)` | **`BotRuntime.canSpeak(chatId, {kind})`** | outbound 是发送执行器，只知道额度和离线，不知道闸；这个方法要回答「这只鸟现在能不能开口」，是运行时诊断。另外 botId 是多余参数——outbound 本来就是每鸟一个实例 |
| 原因列表 8 项，含 `plugin:disabled` | 只做 4 类：`gate:global/bot/chat/silence` + `gateway:offline` + `quota:daily/permin` | 「按插件暂停」明确不做（插件启停已有自己的机制），而「某插件被停用」不等于「这只鸟不能对这个会话说话」——它只是少了一个可能回应的人 |
| `gate.pauseOnStart` 由安装向导写 `true` | 默认 `false`，且**只在首次运行**（闸文件还不存在）时生效 | 落点问题解决了：不需要安装向导，`gate.open()` 返回 `botExisted`，`bot.js` 据此判断。**每次启动都暂停会让人以为坏了**——重启后不说话，第一反应是「出故障」，不是「等我确认」 |
| 多鸟共用一个 `gate.json` | 按鸟拆：`data/gate/<botId>.json` + `data/gate/global.json` | 方案倾向的选项，采纳。但多了一层方案没考虑到的问题：**每只鸟各有一个 gate 实例，各缓存一份全局闸**，面板改完只写了文件，别的鸟内存里还是旧值 → 必须 `reloadGlobal()` 逐个通知，否则「全局暂停」要等重启才对其他鸟生效 |

**中间件的顺序**：`gate → dedup → whitelist → ratelimit → cooldown`。闸在最前面，连去重表都不写；账本不在 pipeline 里（`bot.js` 的 `ledger.append()` 在 `pipeline.run()` 之前），所以**暂停期间的消息照样入账**。这条顺序是「暂停不等于丢消息」的唯一保证，e2e 专门去账本里查那条消息来守它。

**静默存绝对时间戳不存剩余毫秒**：`{ chatId: untilMs }`。剩余时间在进程重启后要重算，而「到几点解除」是事实，重启也成立。

**`gated` 单独计数**：`metrics.counters.gated`，和 dedup/limited/rejected 并列。面板的「错误 / 拦截」卡片把它算进去——否则暂停一天之后，用户看到「拦截 0」会以为闸没生效。

### 不做什么
- 不做「按插件暂停」（插件启停已有自己的机制，别叠两层）
- 不做审批流（那是权限模块的事，不是闸的事）
- 不做「暂停时回一句『我暂停了』」——静默才是目的，回话等于没闭嘴

## 1.5 可达性：能不能私聊（v5 重写，v6 已落地）

这一节独立出来，因为它不只是闸的问题——它决定「主动找谁」能不能成立。

### 官方给的是两层开关，不是一层

v4 只想到「好友」，**漏了一层**。官方文档原文：

| 层 | 事件 | 官方原话 |
|---|---|---|
| 好友关系 | `FRIEND_ADD` / `FRIEND_DEL` | 用户添加/删除机器人 |
| **单聊主动推送** | `C2C_MSG_REJECT` / `C2C_MSG_RECEIVE` | 「用户在机器人资料卡手动关闭主动消息推送时触发。**关闭后机器人无法向该用户发送主动消息**」 |
| 群主动推送 | `GROUP_MSG_REJECT` / `GROUP_MSG_RECEIVE` | 群管理员关闭/开启主动消息推送 |

**有好友 ≠ 能主动发。** 用户可以在机器人资料卡里单独关掉主动推送，关了之后即使好友也发不出去。这一层是 v4 完全没想到的。

### 没有查询接口，但有事件

官方 sitemap 里 `friend` 只有两个**事件页**（`friend_add.html` / `friend_del.html`），**没有任何好友查询 API**——`endpoints.js` 的 17 个 GET 里也没有。

所以状态只能这样维护：

- **接入之前就存在的关系：未知**（事件是增量，不会补发历史）；
- **接入之后的变化：精确**（订阅这 6 个事件，落地即更新）。

### 表

```sql
CREATE TABLE reach (
  bot_id      TEXT NOT NULL,
  openid      TEXT NOT NULL,
  is_friend   INTEGER,        -- 1 好友 / 0 已删 / NULL 未知
  c2c_push    INTEGER,        -- 1 开着 / 0 用户关了 / NULL 未知
  group_push  TEXT,           -- JSON: {"<group_openid>": 1|0}，群维度
  evidence    TEXT NOT NULL,  -- friend_add / c2c_msg_reject / observed_c2c / send_failed / manual
  updated_at  INTEGER NOT NULL,
  PRIMARY KEY (bot_id, openid)
);
```

### 判定顺序

```
canC2C(bot, openid):
  is_friend === 0                     → 不可（reach:not-friend）
  c2c_push  === 0                     → 不可（reach:push-off）   ← 有好友也不行
  is_friend === 1 && c2c_push !== 0   → 可
  其余（NULL）                        → 未知，不拦，但发送失败要记 evidence
```

**`NULL` 不能当 `0` 用。** 未知不等于不可达——群里聊过的人，可能已经加了好友只是没私聊过。

### 落点（v6：已落地，与本文档原设计有出入的地方标出）

| 原设计 | 实际做法 | 差异原因 |
|---|---|---|
| 表存 SQLite `reach` | **JSON 落盘 `data/bots/<id>/reach.json`**，500ms 延迟合并写 + `timer.unref()` | 可达性数据量小（每 bot 几百条），为它单独开一张表要拉进 sqlite 连接和迁移，不值。JSON 还能人工直接改 |
| `canSpeak()` 加两个原因 | 独立的 `reach.canC2C()` / `reach.canGroupPush()`，返回 `{verdict:'yes'\|'no'\|'unknown', reason}` | 暂停闸 v9 落地后补的：**v10 已接进 `bot.canSpeak(chatId, {kind})`**，映射成 `reach:not-friend` / `reach:push-off`。`kind` 不给就不查——不知道是群还是私聊，而「不知道」不该变成「不能」 |
| 6 个事件内置消费 | `bot.js` 的 `#noteReach()`，在插件监听器**之前**调用 | 与设计一致 |
| `noteSendError` 弱证据 | 按 `qqCode` 分支：`40054004`→`is_friend=0`、`40054013`→`c2c_push=0`、`40054006`→**不改** | 错误码已核实，不用再猜 |
| 面板翻译原因 | 面板「数据 → 可达性」页：三态下拉（是/否/未知）、依据中文翻译、结论徽章 | 已落地 |

实现清单：

1. `src/reach.js`（新增）：`canC2C` / `canGroupPush` / `noteFriendAdd` / `noteFriendDel` / `noteC2cPush` / `noteGroupPush` / `noteC2cObserved` / `noteSendOk` / `noteSendError` / `noteManual` / `noteGroupManual` / `flush`
2. `src/bot.js`：`this.reach = createReach({ file: this.paths.reach })`，`#noteReach()` 消费 6 个事件，`stop()` 里 `await this.reach.flush()`
3. `src/plugin/loader.js` + `context.js`：插件侧拿 `ctx.reach`
4. `src/web/server.js`：`GET /api/reach`（读）+ `POST /api/reach`（人工标注）
5. `web/index.html` + `web/app.js`：「数据 → 可达性」页，行内三态下拉即标注
6. `qq-bot-roost-plugins/plugins/ai-chat/index.js`：`/r/send` 发送前查 `canC2C`，`unknown` 放行；成功/失败回写
7. 测试：`test/selftest.mjs` 的 `testReach()` 21 条、`test/e2e.mjs` 的 `testReach()` 14 条

**人工标注的语义陷阱**（最容易写错的地方）：字段传 `undefined` 是「这项不动」，传 `null` 是「重置为未知」。
用 `??` 或真值判断会把这两者混掉——用户在面板上改「好友」时，「推送」会被悄悄清空，界面上没有任何提示。

### 错误码（2026-10-29 核实，v5 的「还剩一个未知」已消）

| 码 | 含义 | 对 `reach` 的影响 |
|---|---|---|
| `40054004` | 无好友关系 | `is_friend = 0` |
| `40054013` | 用户拒收消息 | `c2c_push = 0` |
| `40054006` | 验证好友关系失败 | **不改**——官方要求「重试」，不是终态 |
| `40034101` / `40054003` | 机器人非群成员 | 群档案标失效 |
| `40054002` | 机器人被禁言 | 临时，**不是**不可达 |
| `40034100` | 主动消息超频控 | **不是**不可达，别误标 |

**`40054006` 不改状态这一条最关键。** 它是「验证失败」不是「验证不通过」，一次网络抖动就会把它打出来；
如果照 `40054004` 一样标 `is_friend=0`，抖一下就把一个真好友永久静音，而且没有事件能把他救回来
（除非他再发消息触发 `noteC2cObserved`）。

## 2. 投递账本

### 目标
**发出的每一条消息都有据可查，且永远不会因为「不确定」而被重发。**

现状：发送链路上 grep 不到 `outbox` / `requestId`。唯一的 `requestId` 在 `dsh-roost/src/update.js:314`，是更新安装用的，与消息无关。我们现在靠**顺序**绕——「『我说过』必须挂在发送成功之后」。这在 `msg_seq` 群 1–5 / 单聊 1–4 的约束下很脆：一次超时重发就撞上限流，还会把「我说过」写进记忆，形成自洽幻觉。

### 关键前提：发送有 4 个出口，不是 1 个

复核发现 `Outbound.send()` **不是唯一出口**，这是本方案最重要的一处修正：

| # | 出口 | 位置 | 过 outbound？ | 后果 |
|---|---|---|---|---|
| 1 | `msg.reply()` / `msg.send()` | `src/message.js` 的 `send()` | ✅ | 正常链路 |
| 2 | `!outbound` 兜底 | 同上，`if (!outbound)` 分支 | ❌ | 早期调用方，实际不走 |
| 3 | 面板 `/api/send` | `src/web/server.js` 的 `'/api/send'` 路由 | ❌ → ✅ **已收编** | 调试用，原来无额度、无账本 |
| 4 | **ai-chat `POST /r/send`** | `plugins/ai-chat/index.js` 的 `registerRoute('POST','/send')` | ❌ → ✅ **已收编** | **dsh-roost 的主动消息全走这里** |

**出口 4 曾是现存缺陷，不只是方案问题**：`outbound.js` 的「2b) 主动消息额度」那段有完整的主动额度记账（20/分、1000/天），但 dsh-roost 的 `speakup.js` / `awake.js` 发消息走 `channel.js` 的 `/r/send` → `api.sendGroup` **直发**，额度记账完全没参与。ai-chat 那边的注释当时写着「限频的责任在调用方」，实际限频只靠 dsh-roost 自己的 `maxPerDay: 3` 这类应用层配置。

→ **账本必须包在最外层，或者把 3、4 两个出口收编进 outbound。** 建议后者：给 `/r/send` 的 body 加 `requestId`，内部改调 `outbound.send()`。

#### 落点（v8：出口 3、4 已收编）

| 出口 | 改法 | 验证 |
|---|---|---|
| 3 面板 `/api/send` | 改调 `rt.outbound.send()`；`SendError` 按 code 分状态码（`quota`→429，其余→400）；响应多一个 `pending`（进审核） | e2e 断言**额度账本落盘**：发一条后 `data/bots/main/quota.json` 里该会话 +1 |
| 4 ai-chat `/r/send` | 改调 `ctx.push(target, text, { kind })`；错误多带 `code`（`offline`/`expired`/`quota`/`rate`/`api`）；响应多一个 `pending` | 插件仓 `test/ai-chat-send.mjs` 30 条，核心断言「push 被调用、直连 api 一次都没调」 |

**为什么 e2e 要读额度文件而不是只看 200**：这条路由以前直连 `api.sendGroup`，**同样返回 200**，但账本里一条记录都没有。面板随手点几下就能把官方额度打满而账本上看不出任何事——半真的账本比没有账本更糟，因为你会相信它。

**出口 2 保持原样**：`!outbound` 分支只在自造 Bot 实例（不建调度器）时可达，`bot.js` 的 `init()` 里无条件 `new Outbound`，所以线上走不到。留它是为了不打断单测和早期调用方。

**`pending`（304023 审核中）为什么不能当成功**：见下面状态机第 1 点。目前 ai-chat 只是**把 `pending` 透出去**，dsh-roost 那边还没据此决定要不要写「我说过」——那属于阶段 5（投递账本），不是阶段 2 能收的尾。

### 状态机（按官方 API 的现实设计）

```
                    ┌──────────── 304023 ──────────→ audited（等审核事件）
                    │
created → pending ──┼──────────── 有 msg_id ─────→ sent
                    │
                    ├── 40034128 超窗 / 配额 / 离线 → failed（可重试）
                    │
                    └── 超时 / 5xx / ECONNRESET ──→ unknown（**永不自动重发**）
```

三个非显然的点：

1. **`audited` 不是成功也不是失败。** `outbound.js` 的 `CODE_AUDIT = 304023`，`docs/官方接口限制.md:18` 说「识别为 pending，不当失败」。**术语要统一**：官方文档里的 `pending` 指「结果未确定」，账本里的 `pending` 指「尚未发出」。方案采用 `audited` 作独立状态，避免两个 `pending` 打架。审核期间**不能回写「我说过」**——否则审核不通过就变成她坚称自己说过一句没人看见的话。
2. **`unknown` 必须存在。** 网络超时后我们**无法知道**服务端是否收到。对方的原则是「未知结果必须人工核对，绝不自动重发」，我们要照抄，因为官方配额下重发的代价更高。
3. **`pending` 会在崩溃后残留。** 启动时扫一遍，全部转 `unknown`。不做这一步，重启后这些记录永远卡住。

### 表

```sql
CREATE TABLE deliveries (
  request_id  TEXT PRIMARY KEY,   -- 幂等键，由调用方给
  bot_id      TEXT NOT NULL,
  kind        TEXT NOT NULL,      -- group / c2c
  chat_id     TEXT NOT NULL,
  reply_to    TEXT,               -- 被动回复时的 msg_id
  msg_seq     INTEGER,            -- 群 1..5 / 单聊 1..4，官方硬限制
  digest      TEXT NOT NULL,      -- 摘要：前 120 字 + 总长 + sha1 前 8 位
  state       TEXT NOT NULL,      -- pending/sent/audited/failed/unknown
  msg_id      TEXT,
  code        TEXT,
  attempts    INTEGER NOT NULL DEFAULT 0,
  created_at  INTEGER NOT NULL,
  settled_at  INTEGER
);
CREATE INDEX deliveries_chat ON deliveries(bot_id, chat_id, created_at);
CREATE INDEX deliveries_open ON deliveries(state) WHERE state IN ('pending','unknown');
```

**`digest` 不存全文**——沿用 `src/storage/schema.js:9` 的既有原则「只存聚合结果，不存消息正文」。全文只在事件账本里（且受保留策略约束）。

**库位置**：沿用每鸟一份库（`src/bot.js` 里 `new StatsStore({ file: this.paths.stats })`，即 `data/bots/<id>/stats.db`）。投递账本可以并进同一个库（同为 bot 侧、同生命周期），跨鸟查询在面板层合并。

### request_id 谁来生成

**`dsh-roost` 的 `qq_send` 生成**，不是框架。理由：`qq-tools.js:73` 写明「`qq_send` 每调一次是一段独立消息」，只有它知道「一段话」的语义边界。

**跨进程要传**（见 §3.5）：`qq_send` → `channel.js` 的 POST body 加 `requestId` → ai-chat `/r/send` 透传 → `outbound.send({ requestId })`。现在 `channel.js` 的 `createQqChannel` 里 body 还没有这个字段，需要加。

同 `request_id` 再调一次的语义：

| 当前状态 | 行为 |
|---|---|
| `sent` / `audited` | 直接返回上次结果，**不重发** |
| `unknown` | 返回 `unknown`，不重发，提示「请到面板核对」 |
| `failed` | 允许重试（复用同一行，`attempts += 1`） |
| `pending` | 返回「正在发送」，拒绝并发 |

### classify(e) 的映射

`SendError.code` 有五种：`offline` / `expired` / `quota` / `rate` / `api`。

- `offline`、`expired`、`quota`、`rate` → **确定 `failed`**（消息一定没发出去）
- `api` → 看具体错误码：明确的 4xx → `failed`；超时、5xx、连接重置 → `unknown`

**`quota` 和 `rate` 必须分开（v8 修正）**：两者原本都是 `quota`，但「多久能好」差三个数量级——
日额度用完要等跨天，分钟限流等一分钟。混成一个 code，调用方只能按最坏情况处理：
dsh-roost 的主动搭话会把一次「发得太密」当成「今天说满了」，白白放弃一整天。
反过来按最好情况处理，就是每分钟空撞一次到跨天。现在 `rate` 单独一个 code，
`stats.rateBlocked` 也单独计数。

### 与记忆的耦合（这才是收益）

`dsh-roost` 写日记前查账本：只有 `sent` 才允许写入「我说过 X」。这条现在靠调用顺序，改造后靠**状态查询**——顺序会被并发打乱，状态不会。

## 3. 事件账本（v7：已落地）

### 目标
**把「发生过什么」和「她记得什么」分开存。**

现状：`src/storage/schema.js` 只有 `messages`（时间/会话/用户/**不含正文**）、`daily`、`members`、`commands`；`dsh-roost` 的 `journal` 存的是「她记得的事」。**没有原始消息**。后果：

- 检索原料是模型当时抽出的二手摘要，不是原文——**记忆的上限被原料决定**
- 没有 `msg_seq` 上下文，幂等和「场景片段」都做不了
- 暂停期间的消息永久消失
- **官方没有任何历史消息接口**，账本是唯一退路

### 落点（v7：与本文档原设计的差异）

| 原设计 | 实际做法 | 差异原因 |
|---|---|---|
| 表并入 `stats.db` | **单独一个 `events.db`** | 两个理由：保留策略不同（90 天聚合 vs 7 天全文），隐私承诺相反（stats 说「不存正文」，ledger 存）。混一个库的话「这个库会不会被拷走」说不清。用户想清聊天记录，删一个文件就够 |
| 写入攒批 + 定时刷 | **同步 INSERT**（`node:sqlite` 本来就是同步 API） | WAL 下单条 INSERT 是微秒级。攒批的唯一好处是吞吐，代价是进程被 kill 时丢最后一批——账本不能丢，因为官方补不回来 |
| `append(msg)` 自动判时间 | 加 `append(msg, {timeBasis})` 显式入口 | **`resolveTime()` 永远产生不了 `unknown`**：判不准时它退回 `observation`（本地收到时间），这是对的。`unknown` 的真实场景是「连本地收到时间都不可信」——批量导入几年前的老聊天记录，那时候的 `Date.now()` 是导入时间。没这个入口，`unknown` 这条分支就是死代码 |
| 插件不碰账本 | `ctx.ledger` 给**只读视图**（`recent` / `timeline` / `get` / `stats`） | 只读是防误用不是防恶意（插件同进程，拦不住真想绕的）。但 `append()` 一暴露，插件就能往账本里塞「用户没说过的话」，而账本的全部价值就在于是原始事实 |
| — | `GET /api/ledger`、`/api/ledger/stats`、`/api/ledger/context` | `payload`（原始报文）**一律不返回**。前端只要正文和元信息，整包给出去只会把面板变成数据外泄面 |

文件：`src/ledger.js`（`EventLedger` / `resolveTime`）、`src/storage/events-schema.js`。

测试：`selftest.mjs` 的 `testLedger()` **29 条**、`e2e.mjs` 的 `testLedger()` **12 条**。

### 表

```sql
CREATE TABLE events (
  seq         INTEGER PRIMARY KEY AUTOINCREMENT,  -- 账本序，稳定、不可重排
  id          TEXT NOT NULL UNIQUE,               -- uuid，对外引用用
  bot_id      TEXT NOT NULL,
  kind        TEXT NOT NULL,                      -- group / c2c
  chat_id     TEXT NOT NULL,
  msg_id      TEXT,
  user_id     TEXT,                               -- openid
  user_name   TEXT,                               -- 当时昵称（会变，故带 observed_at）
  content     TEXT NOT NULL DEFAULT '',           -- 正文（v7 新增，见下）
  at          INTEGER NOT NULL,                   -- 消息时间
  observed_at INTEGER NOT NULL,                   -- 本地收到时间
  time_basis  TEXT NOT NULL,                      -- message / observation / unknown
  dedupe      TEXT NOT NULL UNIQUE,               -- `${botId}:${msgId}`；无 msgId 时退化为 `${botId}:${chatId}:${at}:${hash}`
  msg_idx     TEXT,                               -- 本条消息自己的索引（官方 `message_scene.ext` 的 `msg_idx`，形如 `REFIDX_…==`）
  ref_msg_idx TEXT,                               -- 引用别人的索引（`ref_msg_idx`，可能是 `REFIDX_…` 也可能是 `TMP_…`）
  union_openid TEXT,                              -- 跨应用统一标识，可能为空（官方原文）
  quoted      TEXT,                               -- 引用原文（message.js:344 已解析）
  payload     TEXT NOT NULL                       -- 原始 JSON（**必须剔除 `auth_token`**，见下）
);
-- 邻文查询要排除 unknown，把 time_basis 放进索引，避免回表过滤
CREATE INDEX events_timeline ON events(bot_id, chat_id, at, seq) WHERE time_basis != 'unknown';
CREATE INDEX events_user     ON events(bot_id, user_id, at);

CREATE TABLE event_refs (
  from_id   TEXT NOT NULL,      -- events.id
  to_id     TEXT,               -- 解析成功才有
  to_msg_id TEXT,
  kind      TEXT NOT NULL,      -- reply / quote
  resolved  INTEGER NOT NULL DEFAULT 0
);
-- 双向都要能查：从消息找它引了谁，也要能查「谁引用了这条」
CREATE INDEX refs_from ON event_refs(from_id);
CREATE INDEX refs_to   ON event_refs(to_id) WHERE resolved = 1;
```

**`content` 为什么单独一列（v7 补）**：原设计只有 `payload`，正文藏在里面。
实现时加了 payload 大小上限（256 KB，防畸形报文把库撑爆），才发现一个问题——
截断 payload 就等于把正文截掉了。正文是账本最要紧的东西，不能跟 payload 共命运。
独立成列还有个副作用是好的：将来上全文检索（FTS/LIKE）必须有独立列，藏在 JSON 里查不了。

**库位置（v4 补）**：`data/bots/<id>/events.db`，**每鸟一份**，和 `stats.db` 同目录同生命周期。于是 `seq` 是 **per-bot** 的，跨鸟不可比——水位键必须带 `bot_id`（已带），面板跨鸟列表按各自 `seq` 展示，不能排序对比。

> 为什么不分全局一份：pipeline 本来就是每鸟一个 Bot 实例，共享一个库会多一层跨实例锁竞争，而收益（全局可比 seq）我们不需要。

**不另建 `people` 表（v4 补）**：既然 openid 在同一 bot 下跨群一致，人物维度直接从 `events` 聚合即可（`GROUP BY user_id`，走 `events_user` 索引）。对方单独建 `people` 表是为了存「历次名字」——我们用 `events.user_name` + `observed_at` 也能还原，等真需要「稳定人物档案」时再加，现在加是空表。唯一例外是 §1.5 的 `reach` 表，那是状态不是档案。

### 三个非显然的设计

**① `time_basis` 三分，不是可选项**

- `message`：官方给了 timestamp（群消息有）
- `observation`：官方没给 / 不可信，用本地收到时间
- `unknown`：导入、补录、迁移来的

**`unknown` 的事件不参与时间邻文。** 对方为这个专门加了 `event_timeline`（schema 5），把「缓存观察时间与未知时间」排除在索引外。原因很实在：拿不可靠的时间拼上下文，拼出来的是**看起来合理但错误**的对话，比没有更糟。

**② `seq` 与 `at` 分离**

分页用 `seq`（稳定），邻文用 `at`（语义）。历史补录只动 `at`，不动 `seq`——否则所有游标失效。QQ 时间只精确到秒，同一秒内按 `seq` 排，保持到达顺序。

**③ 保留策略（v3 改过，原设计不可实现）**

全量存正文是隐私问题，`schema.js:9` 那条原则是有道理的。但做场景片段必须有原文。

**v2 的原设计是错的**：原写「被 `journal.event_ids` 引用的事件永久保留」。但 events 在 A 侧、journal 在 B 侧，**A 侧根本不知道 B 侧引用了哪些事件**，滚动删除时无法判断该留哪条。要么加一条反向同步（B 定期把引用集合推给 A），要么换思路。

**改为：events 一律 7 天滚动删，证据由 B 侧自己留。**

| 数据 | 位置 | 保留 |
|---|---|---|
| 全部事件（含原文） | A 侧 `events` 表 | **7 天**（可配 `ledger.retentionDays`），滚动删 |
| 记忆的证据快照 | B 侧 `journal.evidence` 列 | **永久** |
| 命令类消息 | A 侧原 `messages` 表 | 按原 `stats.retentionDays`（90 天） |

`journal.evidence` 存 `[{eventId, at, sender, excerpt}]`，`excerpt` 是原文前 200 字。写 journal 时**复制**进来，不是引用。这样：

- events 可以无脑滚动删，不需要知道谁引用了它；
- journal 的证据不依赖 events 存活，跨进程依赖从「双向」降为「单向」；
- 代价是原文在两边各存一份（200 字 × 记忆条数，可接受）。

> 对方是靠 events 永久保留来实现证据的；我们靠快照。差异原因是他们在**单进程单库**里，引用和原文同库。

滚动删除按 `seq` 分批，每次 ≤5000 行，避免长事务锁库。**已实测**：`node:sqlite`（Node 22.22.2）支持 `AUTOINCREMENT` 且删行后**不复用 seq**，账本序稳定这条前提成立。

**写入开销（v7 实测）**：2000 条 233 ms，单条约 **117 μs**，折算 **8500 条/秒**。
QQ 单会话限频 5 条/秒、接口 100 QPS，所以同步写完全不会成为瓶颈——不需要攒批。
（这也是决定「不攒批」的依据，不是拍脑袋。）

### 场景片段（这一步才是收益）

`journal` 加两列：`event_ids TEXT`（JSON 数组，记录这条记忆从哪几条消息来）和 `evidence TEXT`（原文快照，见上）。检索命中后：

```
journal 命中 → event_ids → 取原文
             → 以命中事件为锚点，取前后各 2 条（时间窗 ≤10 分钟）
             → 按 (at, seq) 排序返回
```

返回时每条标记 `hit` / `neighbor` / `quoted`。**相邻不等于同一话题**——这点要写进提示词，不能因为挨着就当因果。对方对此极谨慎（「时间邻居不等于同一话题，片段发言者不等于群成员名单」），这是对的。

### 已读水位（v3 改过，位置原设计是错的）

每个 `(bot_id, chat_id)` 一条 `read_through_seq`：

- **只有「真正展示给模型」的消息才推进水位**，零散检索不推进；
- 目的是「不越过未见间隙」——否则模型会以为自己看过中间的对话。

**v2 把水位放在 A 侧的 events 库里，这是错的**：决定「什么被展示了」的是 B 侧（模型在 B），A 侧只能被动接收。放 A 侧就变成「B 每展示一批就要通知 A 一次」，多一条写桥。

**改为：水位表放 B 侧**（和 journal 同库），只记 `(botId, chatId) → lastShownSeq`。A 侧不存水位，也不需要知道。

这样 A 侧完全无状态（只入账），B 侧自己管「我读到哪了」。和「暂停期间入账」配合：暂停恢复后 B 的水位还停在暂停前，一醒来就知道有积压。

> 前提：`seq` 必须在跨进程语义上稳定。已实测 `AUTOINCREMENT` 不复用 seq，成立。

## 3.5 跨进程数据边界（v2 新增，原方案漏项）

这是原方案最大的缺口：**bot 框架和 dsh-roost 是两个进程、两套数据目录**，账本和记忆不在同一侧。

```
进程 A：bot 框架        DIRS.data = <HOME>/data          （src/paths.js:51）
                        收消息、发消息、outbound、gate
                        ← events.db 应该在这里

进程 B：dsh-roost        dataDir() = <DSH>/data/roost     （host.js 的 dataDir()）
                        记忆、情绪、日记、图谱
                        ← journal.sqlite / graph.sqlite 在这里

桥：ai-chat 插件（跑在 A 里）
    A → B：转发消息（带 eventId）
    B → A：POST /api/plugins/ai-chat/r/send（主动发消息）
```

**由此推出三条硬约束：**

1. **events 只能在 A 侧**。收消息发生在 A，B 停了 A 还在收。若把账本放 B，dsh-roost 一重启就断档。
2. **journal 只能在 B 侧**。记忆的抽取/摘要/评分都要调模型，那是 B 的职责（`memory.js` 头注释已论证）。
3. **跨进程的桥必须列全。** v2 只写了 2 条，实际需要 3 条（已把「保留策略」和「已读水位」两条依赖就地消除）：

| # | 方向 | 用途 | 形态 | 状态 |
|---|---|---|---|---|
| 1 | A → B | 转发消息时带 `eventId` | 现有转发通道加字段 | 改动小 |
| 2 | B → A | 取邻文 `GET /r/context?aroundId=&before=&after=` | 新增只读路由 | 需鉴权 |
| 3 | B → A | 查投递终态 `GET /r/delivery/:requestId` | 新增只读路由 | 需鉴权 |

**桥 3 为什么需要**：`audited`（304023）时 B 拿到的是「待审核」，不知道最终结果。B 不能靠「等推送」——`MESSAGE_AUDIT_PASS` / `MESSAGE_AUDIT_REJECT` 事件到的是 A 侧（`events.js:151-152`）。最省事的做法是 **A 收到审核事件时更新账本，B 下次写记忆前拉一次终态**，不搞推送。

**路由现状（v2 写错了）**：ai-chat 现在只注册了 `POST /send` 和 `POST /reply` 两条（`registerRoute`），**没有 `/status`**。`channel.js` 的 `ping()` 调 `/r/status` 会 404，但 `ping()` 全仓**没有任何调用点**，是死代码，不构成运行时问题。新增的两条路由要一并补 `/status` 或删掉 `ping()`。

新增路由需要鉴权和 `Host/Origin` 校验——对方在这点上很谨慎（「后台管理页和代理工具使用不同入口；都有本机 Host/Origin 校验」）。

> **退化方案**（不想加三条跨进程路由时）：把 events 也放 B 侧，由 ai-chat 把每条消息 POST 给 B。代价是每条消息一次 HTTP，且 **B 停摆期间丢档**——而官方没有任何历史接口可以补。
>
> 权衡：桥是 3 条**只读**路由（简单、可测、B 挂了不影响 A 收消息）；退化方案是 1 条**写**路由（简单但丢数据）。v3 倾向保留桥方案，因为丢档在官方 API 下是不可恢复的。

## 6. 明确不做

- **不替换现有检索栈**。`journal.js:685` 的 BM25 + 向量 RRF（k=60）+ 图谱三路召回，设计上强于对方（对方明确不引向量库）。但**向量默认是关的**（`embed.js:7`：「默认关着，`memory.embedding` 没填就 `enabled() === false`」），默认配置下实际只有 BM25 + 图谱两路。补检索不是本轮的事，别顺手改。
- **不重写 `journal`**。`journal` 是「她记得的」，`events` 是「发生过的」，两者生命周期不同（和 `closing.js` 头注释那段论证同理），混表早晚互相污染。**本轮只给 journal 加两列（`event_ids` / `evidence`），不改它现有的检索与衰减逻辑。**
- **不做多后端抽象**（DSH/Codex/OpenAI 三选）。插件体系已经把后端解耦了，这件事优先级在 P2。
- **不做 self 版本化**。人格成长是 P1，但它是独立议题，别和账本一起做——账本是地基层面的改动，混进产品功能会失控。
- **不做 `is_wakeup` 互动召回**。官方给了（单聊 30 天内 4 个周期各 1 条），但它是「主动找谁」的策略层，得先有投递账本才知道哪条发过。**没有账本就上召回 = 重复骚扰**。P1。
- **不做 `msg_type=6` 输入中状态**。仅单聊、最长 60 秒，属体验项，等 ai-chat 流式改造一起做。
- **例外：`event_id` 被动回复要尽早接**。`FRIEND_ADD` / `C2C_MSG_RECEIVE` / `GROUP_ADD_ROBOT` 三个场景能被动回一条、**不消耗主动额度**，还正好是可达性状态的实时正反馈。这不是新功能，是把已有的 6 个事件再榨一层。

## 7. 修订记录

### v10（2026-10-29：补三个「文档写了、代码没做」的缺口）

对着文档逐条核对代码时翻出来三个洞，都是**方案里写了、实现时漏了**：

**一、`--paused` 启动参数。**
§1 的表格里写着「global | 面板 / `--paused` 启动参数」，实际只有面板和 API。
补的时候定了条规矩：**只改内存不写盘**（`setGlobal(..., {persist:false})`）。
这个参数表达的是一次性意图「这次先别说话」；写进 `global.json` 的话，
下次不带参数启动却发现还在暂停，人会以为程序坏了。

**二、`<<silence:2h>>` 动作标记。**
§1 写着「silence | 模型（新增 `<<silence:2h>>` 动作标记）」，实际只有 API。

实现时踩到一个**两边都在犯的错**：ai-chat 的 `parseActions` 和 dsh-roost 的
`fire()` / `parseVerdict()` 都会 `raw.replace(/<<[^>]*>>/g, '')` 把标记一把抹平。
抹掉之后再想拿时长就没处找了。所以三处都改成**先提取、再摘掉**。
这条如果不做，「她要求安静」永远不会生效，而且**看不出哪里错了**——
标记被正常摘掉，正文正常发出，只是静默悄悄没了。

第二个坑：静默必须**两边都记**。
框架的闸拦的是「收到的消息」（pipeline），而主动搭话走 outbound、不经过 pipeline。
只记框架那边的话，她说「让我静静」之后私聊里照样被主动搭话叫醒。
所以 speakup 也记一份 `silenceUntil`，`shouldFire()` 里挡一道。

第三个细节：**只有静默、没有正文是合法的**。
`<<silence:2h>>` 单独出现就是「我要安静，没什么要说的」——
这时候既不该发一条空消息，也不该当成错误拒掉。`/r/send` 为此多了一个
`silentOnly: true` 的返回。

**三、可达性没接进 `canSpeak`。**
§1.5 的落点表当时写「暂停闸还没做，先不硬塞进 `canSpeak`，等 §1 落地后再映射」。
§1 在 v9 落地了，这条就悬着——面板说「能说话」，实际对方根本没加好友。

补的时候加了个 `kind` 参数：`canSpeak(chatId, {kind})`。
**不给 `kind` 就不查可达性**——不知道是群还是私聊就查不了，
而「不知道」不该变成「不能」。e2e 专门有一条守这个。

### v9（2026-10-29：暂停闸落地）

四处和原设计不一样，都记在 §1 的「落点」表里。其中两条是**方案没预见到的**：

**一、多鸟共用一个闸状态，光写文件不够。**
方案已经想到「按鸟拆文件避免丢更新」，但没想到另一半：每只鸟各有一个 gate 实例，
**各自在内存里缓存一份全局闸**。面板点「全局暂停」只写了一个文件，
其他鸟的实例还拿着旧值——表现是「点了暂停，另一只鸟照常说话」。
补了 `reloadGlobal()`，`POST /api/gate` 写完之后逐个通知。
这个坑很典型：**进程内缓存 + 文件共享状态**，只要有两份副本就要想清楚谁通知谁。

**二、`pauseOnStart` 不需要安装向导。**
方案里那条「落点待定：首次配置由谁生成」其实问错了方向——不需要谁来生成配置，
需要的是**判断「这是不是第一次」**。`gate.open()` 顺手返回 `botExisted`
（闸文件在不在），`bot.js` 拿它决定要不要自动暂停。方案里那个「退化成只在文档里教」
的退路用不上了。

**三、`canSpeak` 从 `Outbound` 挪到了 `BotRuntime`。**
方案写的是 `Outbound.canSpeak(botId, chatId)`，但 outbound 是发送执行器，
只知道额度和离线，不知道闸；而 `plugin:disabled` 它更是完全无从判断。
这个方法要回答的是「这只鸟现在能不能开口」，是运行时诊断，不是发送动作。
放在 bot 上还能省掉 `botId` 参数——outbound 本来就是每鸟一个实例。

**四、`plugin:disabled` 这个原因没做。**
「按插件暂停」是方案自己明确不做的（插件启停已有机制，别叠两层），
而「某个插件被停用了」不等于「这只鸟不能对这个会话说话」——它只是少了一个
可能回应的人，别的插件还能回。列进 `canSpeak` 会把两件事混成一件。

**顺带修正一处旧口径**：`metrics.counters` 新增 `gated`，面板的「错误 / 拦截」
把它算进去。否则暂停一整天之后用户看到「拦截 0」，会以为闸根本没生效——
**一个不留下痕迹的拦截，在面板上和不存在的拦截长得一模一样。**

### v8（2026-10-29：出口 3、4 收编完成）

改动本身很小（两处调用换成 outbound / `ctx.push`），但有两处判断值得记下来。

**一、测试不能只看 HTTP 200。**
面板 `/api/send` 改之前也返回 200，账本里却一条记录都没有——「接口能通」和「记账生效」是两件事。
所以 e2e 断言改成读**落盘的额度文件** `data/bots/main/quota.json`：发一条，该会话计数 +1。
这是唯一不可伪造的痕迹。同理，ai-chat 那边的断言是「`ctx.push` 被调用、`ctx.api.sendGroup` 一次都没被调用」，
而不是「返回 ok」。两条都做了**变异验证**（临时改回直连，确认断言会红）。

**二、`pending` 只能透出去，不能就地收尾。**
`304023` 进审核既不是失败也不是送达。ai-chat 现在把 `pending` 放进响应，
但**没有替调用方决定要不要写「我说过」**——那需要投递账本的状态机（阶段 5），
在这里顺手做等于把「她说自己说过一句话」押在一个 HTTP 响应字段上。
宁可留一个明确的缺口，也不做一个看起来完整、实际上会自洽幻觉的判定。

**出口 2（`!outbound` 兜底）没动。** 它只在自造 Bot 实例时可达，
`bot.js:153` 无条件构造 `Outbound`，线上走不到；删掉反而会打断单测和早期调用方。

**三、`quota` 必须拆成 `quota` + `rate`，否则「失败后怎么排期」没法写。**
收编完发现 dsh-roost 拿到 `ok:false` 后一律用随机间隔（3–8 小时）重排。
问题是同一个 `quota` 背后有两种现实：日额度用完要等跨天、分钟限流等一分钟。
按随机间隔处理，前者一天空撞好几次；按「推到明天」处理，后者白白少说一整天。
两个都不对，因为**信息在框架这层就被压掉了**。所以拆成两个 code，
dsh-roost 按 code 分三路排期。群主动那边同理，加了 `blockedUntil`——
但没有用「把 count 填满」来变相封禁，那是往状态里写假数据，
面板会显示「今天已经说了 3 次」而实际一次没说。

### v7（2026-10-29：事件账本落地）

实现时改了四处设计，都记在 §3 的「落点」表里。三处是**原设计根本没考虑到的现实**：

**一、`unknown` 那条分支原来是死代码。**
`resolveTime()` 判不准时退回 `observation`（本地收到时间），这个行为是对的——
「不知道官方时间，但我知道我什么时候收到的」比「不知道」有用。
但这样一来 `unknown` 永远产生不出来，而它在索引里还要被排除。
想清楚才发现 `unknown` 的真实场景是**导入**：批量灌几年前的老聊天记录时，
`Date.now()` 是导入时间不是说话时间，这时候只能标 `unknown`。
于是加了 `append(msg, {timeBasis})` 显式入口，并把「导入的数据 `at` 用导入时间」
这个副作用写进注释——宁可多留一个保留期，也不能让刚导进来的数据立刻被滚动删掉。

**二、`stats` 和 `ledger` 必须分库，不是分表。**
原设计写「投递账本可以并进同一个库」（§2），账本这块没明说。
实现时发现合库会让 `schema.js` 开头那句「**只存聚合结果，不存消息正文**」
直接变成假话——那是一条对用户的隐私承诺，不是技术选择。
分库之后「用户想清掉聊天记录」也变成删一个文件的事。

**三、同步写比攒批写更合适。**
统计用「内存缓冲 + 1 秒批量刷」是为了不拖慢收消息，但账本丢不起：
进程被 kill 时缓冲里那批就永久没了，而官方没有历史消息接口，补不回来。
`node:sqlite` 本来就是同步 API，WAL 下单条 INSERT 是微秒级，直接写就行。

**四、插件只能读。**
`ctx.ledger` 是 `Object.freeze` 的只读视图。这不是安全边界（插件同进程，拦不住），
是**语义边界**：账本的价值在于「它是原始事实」，`append()` 一暴露就能伪造历史。

顺带确认的两件事：

- `ref_msg_idx` 解析：`resolveRefs()` 用 `msg_idx` 反查，能对上就把边标 `resolved=1`。
  对不上（`TMP_` 前缀那种）就保持 `0`，退化成「知道引用了谁、不知道是哪条」，
  不抛错也不丢数据——这就是 §4 #6 说的退路。
- `AUTOINCREMENT` 删行后不复用 `seq`，已在测试里钉死（`账本: 清理后新 seq 只增不减`）。
  这条是水位和分页游标的全部前提。

### v6（2026-10-29：官方两个发送接口页核实 + 可达性落地）

核对了 `v2_users_user_openid_messages.post.html` 和 `v2_groups_group_openid_messages.post.html` 两个发送接口页。

**一、§4 的 #1 #5 两个待核实项全部解决**，方案结构不用再改。

**二、发现一个已上线的真 bug：单聊被动窗口写错了。**

| | 群聊 | 单聊 |
|---|---|---|
| 被动窗口 | 5 分钟 | **60 分钟** |
| 最多回复次数 | 5 次（`msg_seq` 1–5） | **4 次（1–4）** |

`outbound.js` 原来是一套常量两个场景共用（群聊口径）。后果：

- 单聊第 6 分钟就判「超窗」，**白白降级成主动消息**，吃掉好友每天 1000 条的额度（被动回复本来不占额度）；
- 单聊第 5 次回复必然撞 `40034128`（单聊只允许 4 次），本地却以为还有余量。

已改成按 `kind` 取：`PASSIVE_WINDOW_MS` / `PASSIVE_SAFE_MS` / `PASSIVE_MAX_REPLIES` 三个都是对象。

**三、`msg_seq` 是天然幂等键（影响 §2 投递账本的设计）。**

官方明确：相同 `msg_id` + `msg_seq` 重复发送返回 `40054005 消息被去重`。
所以投递账本的幂等键**不需要自己造**，直接用 `(msg_id, msg_seq)`；`request_id` 只用于跨进程追踪，不用于去重。
这比原设计更省事，也更可靠——本地账本挂了，服务端还有一道去重。

**四、三个「官方给了但我们没用」的能力，记进 §6 不做清单的理由里。**

| 能力 | 用在哪 | 为什么本轮不做 |
|---|---|---|
| 互动召回 `is_wakeup` | 单聊，30 天内 4 个周期各 1 条（当天 / 1-3 天 / 3-7 天 / 7-30 天） | 是「主动找人」的策略层，得先有投递账本才知道哪条发过。放 P1 |
| 事件被动回复 `event_id` | `FRIEND_ADD` / `C2C_MSG_RECEIVE` / `GROUP_ADD_ROBOT` 等 | **这个该早点做**：用户加好友、重开推送时能被动回一条，不消耗主动额度，还正好是可达性的正反馈 |
| 输入中状态 `msg_type=6` | 仅单聊，`input_notify`，最长 60 秒 | 体验项，等 ai-chat 流式改造一起做 |

**五、引用回复的 ID 来源确定了（§4 #1 的答案）。**

- 非机器人消息 → `message_scene.ext.msg_idx`（`REFIDX_…==`）
- 机器人自己发的 → 发送响应 `ext_info.ref_idx`
- 填的位置是 `message_reference.message_id`（**填索引，不是 `msg_id`**）

### 两轮复核的教训

第一轮查的是「我说的和代码是否一致」，第二轮查的是「方案自己是否自洽」。**第二轮发现的更严重**——两处设计在单进程里看没问题，一放到 A/B 双进程就不可实现。

以后写跨进程方案，先画数据归属表（谁产生、谁消费、谁持久化），再写表结构。顺序反了就会写出「A 侧删除时要知道 B 侧引用了什么」这种没法落地的条款。

### 附带发现的现存缺陷（不在本方案范围，建议单独立项）

**主动消息额度记账形同虚设。** `outbound.js:303/341` 有完整的 20/分 + 1000/天 记账，但 dsh-roost 的主动消息走 `channel.js:124` → ai-chat `/r/send` → `api.sendGroup` 直发，**完全绕过 outbound**。ai-chat 注释把限频责任推给调用方（`index.js:441`），实际只有 dsh-roost 自己的 `maxPerDay: 3` 这类应用层配置在兜。

后果：如果 dsh-roost 的配置调大，或换了别的调用方，官方额度会在没有任何本地保护的情况下被打满。**这是阶段 2「收编发送出口」要解决的，但它本身是已存在的风险，不该等方案落地。**

**→ 已解决（v8）**：出口 3、4 都改走 outbound，两处都补了断言。上面这段保留作为「当时为什么急着做」的记录。
