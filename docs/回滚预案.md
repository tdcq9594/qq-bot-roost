# 回滚预案

> 目标：发错了能快速退回去，且用户侧不被卡死。
> 适用：框架（qq-bot-roost）与插件（qq-bot-roost-plugins）。

---

## 1. 框架回滚

框架是用户自己 clone / 下载运行的，回滚分「发版侧」和「用户侧」两段。

**发版侧（维护者）**
1. 定位上一个好版本 tag：`git tag --list | sort -V | tail`
2. 基于旧 tag 重新打一个补丁版本（**不要删旧 tag 再复用同名**，用户端 semver 会乱）：
   ```bash
   git checkout <good-tag>
   # 只 cherry-pick 需要保留的修复
   git switch -c hotfix/rollback-<ver>
   # 改 package.json version 为新的补丁号（如 0.6.15）
   git commit -am "rollback: 回到 <good-tag> 行为"
   git tag v0.6.15 && git push origin v0.6.15
   ```
3. 双仓同步：`gitee-sync` workflow 会在 tag 推送时自动跑；也可手动 `workflow_dispatch` 触发。
4. 在 `RELEASE_NOTES.md` 写清「本次回滚了什么、为什么」。

**用户侧**
- 面板「检查更新」只会提示更高版本 → 重新发一个更高补丁号即可让用户「更新回去」。
- 急用可手动：下载旧 tag 的 tar.gz 覆盖 `src/`，重启。

---

## 2. 插件回滚（关键约束）

**市场只认「更高版本」**（`market.js` 里 `compareVersion(cur, latest) < 0` 才提示更新），
所以**不能直接把 index.json 的版本改低**——用户端不会降级。

正确的回滚方式：**把旧版代码拿出来，发一个更高版本号**。
```bash
cd qq-bot-roost-plugins
git checkout <good-commit> -- plugins/<id>
# 把 plugins/<id> 里的 version 改成比坏版本更高的号（如 2.1.0 坏了 → 发 2.1.1）
node scripts/build-index.mjs        # 重算 sha256 + 版本
node scripts/build-index.mjs --check
git commit -am "<id>: 回滚到 <good> 的行为（2.1.1）"
git push origin main
```
> 若插件带存档（如 kun），回滚版本必须能读**新版本写下的数据**（向前兼容），
> 否则老用户升级到坏版本后回滚会读不动存档。发布前务必验证。

---

## 3. index.json 坏掉

索引坏了会让**所有用户安装失败**（sha256 对不上）。
1. `git log -- index.json` 找到上一个好提交
2. `git checkout <good-commit> -- index.json`
3. `node scripts/build-index.mjs --check` 确认一致
4. 推送（`gitee-sync` 会跟着同步）

---

## 4. 双仓不一致（Gitee 滞后）

- 现象：用户 `auto` 模式切到 Gitee 后装到旧版。
- 处理：到 GitHub Actions 手动跑 `Gitee 镜像同步`（`workflow_dispatch`），
  它会推镜像并校验 Gitee 分支 sha 是否已跟上。
- 若 `secrets.GITEE_TOKEN` 过期：换新令牌后重跑。

---

## 5. 灰度 / Canary（尚未实现，属产品决策）

当前是「一发布全量到达」。要做得更稳，需要：
- index.json 增加 `versions[]`（保留历史版本 + 各自的 sha256），市场支持「钉版本/降级」；
- 面板增加「灰度比例」或「canary 标记」，只让小部分用户先升；
- 插件连续崩溃 N 次自动禁用（熔断）。

这些需要改索引 schema 与市场安装逻辑，属较大改动，建议单独排期。
