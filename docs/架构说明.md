# 架构说明

这份文档讲**当前**的结构：一个进程怎么跑起多个机器人，数据为什么必须隔离。

---

## 一、进程模型

**单进程，多实例。**

```
main()
 ├── 全局：logger / Web 面板 / 实例锁
 └── for each config/bots/*.json (enabled=true)
      └── BotRuntime
           ├── TokenManager     访问凭证，各自刷新
           ├── QQApi            HTTP 接口
           ├── Gateway          WebSocket 长连接
           ├── Registry         命令表 / 监听表
           ├── RoleStore        权限（data/bots/<id>/roles.json）
           ├── GroupStore       群档案
           ├── Outbound         出站调度 + 额度账本
           ├── SessionManager   多轮对话
           ├── Pipeline         中间件链
           └── PluginManager    插件加载（共享 plugins/ 代码目录）
```

代码在 `src/bot.js` 的 `BotRuntime` 类，一个实例就是一个机器人。

### 为什么不是多进程

| | 单进程多实例 | 多进程 |
|---|---|---|
| 插件代码 | 只加载一次 | 每个进程各加载一份 |
| 面板 | 一个端口管全部 | 要聚合多个端口 |
| 内存 | 省 | 每进程一份 Node 运行时 |
| 故障隔离 | 内建插件死循环会拖垮全部 | 彻底隔离 |

选了单进程。代价是内建插件（`index.js`，跑在主进程）没有隔离——这一点在
[插件开发规范](插件开发规范.md) 里明确写了。真要隔离就写成外部插件（子进程）。

---

## 二、数据为什么必须按机器人隔离

不是设计偏好，是**官方接口的硬约束**：

> **openid 是每个机器人独立的。** 同一个用户在不同机器人下的 openid 完全不同。

所以这些**绝对不能跨机器人共享**：

| 数据 | 为什么 |
|------|--------|
| `roles.json` | 存的是 openid，换机器人全对不上 |
| `groups.json` | 群 openid 也是 per-bot 的 |
| `quota.json` | 主动消息额度按机器人算 |
| 插件存档 | 游戏进度绑的是 openid |

反过来，这些**必须共享**：

| 数据 | 为什么 |
|------|--------|
| 插件代码 `plugins/` | 一份代码，所有机器人按需加载 |
| 全局配置 | 面板端口、日志级别这类是进程级的 |

## 三、目录布局

```
config/
  bot.json                全局配置
  bots/<id>.json          机器人配置
  bots/<id>/plugins/      该机器人的插件配置
data/bots/<id>/           groups / roles / quota / plugins 状态 / 插件存档
logs/bots/<id>/           bot.log + plugins/*.log
plugins/                  插件代码，全局共享
```

路径统一由 `src/paths.js` 的 `botPaths(id)` 生成，**所有模块都从这里取，不自己拼字符串**。
这是多机器人能互不干扰的前提。

### `ROOST_HOME`：把运行数据整体挪走

上面三行（`config/` `data/` `logs/`）默认在仓库根，但可以由环境变量改根：

```bash
ROOST_HOME=/tmp/roost-test node src/main.js --mock --serve
```

`plugins/` **不跟着走**——它是代码不是数据，挪走了就找不到插件了。
代码根（`src/` `web/` `package.json`）永远跟着仓库。

这个变量只为一件事存在：**让测试不去写开发者自己的配置**。
e2e 跑在 `os.tmpdir()` 下的临时目录里，跑完就删。以前它直接读写仓库根的
`config/`，跑一次测试真实机器人的权限表、群档案、插件配置全被改了。

### 日志分流

`src/logger.js` 的 `sinkKeyOf(tag)` 按 tag 决定写哪个文件：

| tag | 写到哪 |
|-----|--------|
| `plugin:<botId>:<pluginId>` | `logs/bots/<botId>/plugins/<pluginId>.log` |
| `bot:<botId>` | `logs/bots/<botId>/bot.log` |
| 其他（`core` / `gateway` / `api` …） | 只进全局 `logs/bot.log` |

全局日志永远是**全量**，单机器人日志是该机器人的子集。排查单个机器人的问题看子集，
排查进程级问题看全局。

## 四、事件流

```
WebSocket
  └─ gateway.js  处理 op 0/1/2/6/7/9/10/11，READY/RESUMED 在网关内部消化
       └─ BotRuntime.dispatch(eventName, d)
            ├─ 非消息事件 → 直接转交插件 (原始 d, { event, intent, desc, api, bot })
            └─ 消息事件   → message.js 规范化成 Message → pipeline → 命令 / 监听器
```

**43 个官方事件全部登记在 `src/events.js`**，`message` 字段标了哪些要规范化成 Message。
内核不认识的事件**也照样转发**，只打一条 WARN 提示补登记——官方新增事件时插件能立刻用上。

详见 [事件与接口清单](事件与接口清单.md)。

## 五、插件加载

每个机器人各有一个 `PluginManager` 实例，但**扫描的是同一个 `plugins/` 目录**。

```
PluginManager.scan({ filter })
  ├─ allocateLevels(全部插件)      等级号段按全量算，保证各机器人看到的一致
  └─ for id of 通过 filter 的插件
       ├─ 内建（index.js）  → 主进程 import
       └─ 外部（plugin.json）→ 子进程 + NDJSON 管道
```

`filter` 来自该机器人的 `plugins.mode`（`all` / `include` / `exclude`）。
**号段分配必须基于全部插件**，否则不同机器人看到的等级号段会错位。

## 六、实例互斥

同一个 AppID 不能有两个进程同时连网关——服务端会判定冲突，两边互相踢（关闭码 4902），
表现是机器人反复掉线、消息时有时无，而且你很难意识到自己开了两个窗口。

`src/instance.js` 用 `data/instances.json` 记录 `{ appId: { pid, at } }`：

- 同 AppID 有活实例 → 拒绝启动，给出 PID 和处理命令
- 不同 AppID → 允许（跑多个机器人是合法需求）
- 死进程记录自动剪枝，不会把人锁在外面
- `--force` 强行启动

锁的粒度是 **AppID 不是进程**，所以一个进程内多个 BotRuntime 互不冲突。

## 七、面板怎么支持多机器人

`startWebServer({ globalCfg, runtimes, ... })` 收的是运行时数组。

每个请求按 `?bot=<id>` 选目标，没传就用第一个：

```js
const rt = pickRuntime(url);
const cfg = rt.cfg;          // 下面用同名局部变量遮住外层聚合对象，
const plugins = rt.plugins;  // 这样所有 handler 的主体逻辑都不用改
const roles = rt.roles;
```

前端 `api()` 自动给每个请求加 `?bot=`，切换机器人 = 换这个值 + 重拉当前页签。

SSE 用 `Map<res, botId>` 记录每个连接在看哪个机器人，各自推各自的状态。

## 八、设计取舍记录

| 决定 | 理由 |
|------|------|
| 单进程多实例，不是多进程 | 插件代码只加载一次，面板一个端口管全部 |
| 插件代码共享，状态隔离 | 改一次代码所有机器人生效；但 openid 不通用，状态必须分开 |
| 插件启用默认 `include` | 新机器人不该莫名其妙跑起一堆插件 |
| 迁移后不保留旧文件 | 避免"两份配置哪个生效"的困惑；迁移前逐字节校验才删 |
| 锁按 AppID 不按进程 | 多机器人是合法需求，真正有害的是同 AppID 双开 |

## 九、全部文件作用

受控文件共 67 个（`git ls-files`，不含 `data/` `logs/`）。按目录分组，
每个文件一句话说清它管什么。

| `LICENSE` | 非商业许可（禁止收费、禁止商用） |

| `.gitattributes` | 换行符规则 |
| `.github/` | Issue 模板（bug / feature）、PR 模板 |

### `config/`

| 文件 | 作用 |
|------|------|
| `bot.example.json` | **全局**配置模板（复制成 `bot.json`）：日志、面板、插件全局项 |
| `bots.example.json` | **机器人**配置模板（复制成 `bots/<id>.json`） |

> 真实配置文件 `config/bot.json` 和 `config/bots/*.json` **不入库**，
> 里面是 AppSecret。分清这两级很关键：`webui` / `logLevel` 是全局的，
> 所有机器人共用一份；其余按机器人分开。
