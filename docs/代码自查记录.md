# 代码自查记录

对全部源码（`src/` 15 个文件、`web/` 3 个文件、`plugins/` 2 个插件）做了一遍通读，
按「安全 → 正确性 → 健壮性 → 性能」的顺序排查。下面是发现的问题与处理结果。

---

## 一、安全

### 1. 事件报文里的 `auth_token` 会被暴露（已修）

群消息报文长这样：

```json
"message_scene": { "ext": ["msg_idx=REFIDX_xxx", "auth_token=laoT7IKvYcoc2yLgruyZ-..."] }
```

原来 `runtime.lastRaw` 直接存原始 JSON，而 `/api/status` 会把它返回给面板。
虽然面板默认只听 `127.0.0.1`，但这属于凭证泄露面。

**修复**：新增 `sanitizePayload()`，递归脱敏：
- `auth_token` / `token` / `secret` / `cookie` 等键名 → `***`
- `ext` 字段整体隐藏
- 字符串里的 `auth_token=xxx`、`msg_idx=xxx` 用正则抹掉

日志里打印未知事件时也走同一个函数。

### 2. 静态文件路径校验可被前缀绕过（已修）

```js
const abs = path.join(WEB_ROOT, filePath);
if (!abs.startsWith(WEB_ROOT)) 403;   // ← 问题在这
```

`startsWith` 是按字符串比较的：如果存在 `web-evil/` 这种同前缀的兄弟目录，
`/../web-evil/x` 解析后仍以 `web` 开头，检查会通过。

**修复**：改用 `path.relative()`，结果以 `..` 开头或为绝对路径就拒绝。

> 补充：WHATWG `URL` 本身会规范化 `..`，所以裸 `..` 走不到这里；
> 真正有风险的是 `%2f` 编码变体，实测已返回 403。

### 3. 面板写接口存在 CSRF 风险（已修）

`/api/config` 这类接口只看访问密钥，不看请求来源。如果没设 `accessKey`，
恶意网页可以用简单表单 POST 打到本地面板端口改配置。

**修复**：所有非 GET 请求强制要求 `Content-Type: application/json`。
跨站表单设不了这个头（设了会触发预检并被拦），实测返回 415。

### 4. 面板输出未转义（已修）

`renderGroups` / `renderRoles` / `renderPlugins` 用模板字符串直接拼服务端数据，
`adminOpenid` 是用户在面板里手填的，理论上可以注入 `<img onerror=...>`。

**修复**：统一用 `escapeHtml()` 包一层。

## 二、正确性

### 5. `gateway.restart()` 完全无效（已修）★

```js
async restart() {
  this.stop();          // ← 这里把 stopped 置成 true
  this.stopped = false; // ← 立刻改回来了
  ...
  await this.#connect(); // ← #connect 第一行 if (this.stopped) return
}
```

面板上点「重连网关」没有任何效果。更糟的是：`stop()` 关闭旧连接后，
close 事件在 300ms 内触发，此时 `stopped` 已经是 `false`，
于是 close 回调又安排了一次重连 → **两条连接同时存在**。

两条连接共用同一个 `sessionId`，后连上的那条发 Resume 会被服务端拒绝：

```
WebSocket 关闭 code=4902 reason=reset by resume
```

然后各自重连、互相踢，形成重连风暴（实测 20 秒内重连 5 次）。

**修复**：
1. `restart()` 里等旧连接真正 `close` 之后再放开 `stopped`
2. `#connect()` 增加守卫：已有 `readyState` 为 0/1 的连接时直接返回
3. 收到 `4902` 时清空 `sessionId`，下次走全新 Identify 而不是 Resume

实测修复后手动重连一次，连接保持在线，`reconnectCount` 不再增长。

### 6. 权限迁移会误伤插件等级（已修）★

旧格式用 `100/80/60/40`，新格式用 `0/1/2/3`，读取时做迁移：

```js
if (lv >= 40 && LEGACY_MAP[lv] !== undefined) { ... }
```

问题：插件号段从 10 开始、每插件 10 个号位，第 4 个插件的等级就是 **40**，
第 6 个是 **60**，第 8 个是 **80**。这些合法值会被当成旧数据转成 3/2/1，
权限直接错乱。

**修复**：加 `__version` 标记，迁移只做一次；并且**跳过 `feature:` 开头的
作用域**——旧版本根本没有插件权限，出现在 feature 作用域的一定是新数据。

实测：`global:80 → 1`、`group:60 → 2` 正确迁移，`feature:60` 和 `feature:40` 原样保留。

### 7. `level: 0` 被当成「缺少参数」（已修）

```js
if (!scope || !openid || !level)   // 0 是 falsy
```

**修复**：改用 `!Number.isInteger(level)`。

### 8. `Math.min` 混入 Promise 得 NaN（已修）

```js
const chat = roles.effective(...);      // 漏了 await
const feature = roles.effective(...);
return Math.min(chat, feature);         // NaN，且不报错
```

后果是所有插件级权限判定静默失败。

**修复**：补 `await`，并改成 `Promise.all` 并行。

## 三、健壮性

### 9. 所有 HTTP 请求没有超时（已修）

`fetch` 默认无限等待。网络卡住时命令会一直挂着，用户看到的是「机器人没反应」。

**修复**：`AbortSignal.timeout(15000)`，凭证接口和开放平台接口都加了。

### 10. 退出时权限数据会丢（已修）

`roles` 的写入有 300ms 防抖，但 `shutdown` 只 flush 了 `groups`，漏了 `roles`。
Ctrl+C 前 300ms 内改的权限会消失。

**修复**：退出、mock 结束时都 `await roles.flush()`。

### 11. 配置文件可能写坏（已修）

`fs.writeFile` 直接覆盖，写到一半断电会留下半个 JSON，下次启动直接崩。

**修复**：写临时文件再 `rename`（原子操作）。

### 12. 心跳假死检测（已加）

原来只发心跳、不检查回执。连接假死（TCP 还在但没有数据）时会一直挂着。

**修复**：记录 `lastAckAt`，连续 2.5 个周期没有 ACK 就主动断开触发重连。

## 四、性能

### 13. 权限查询重复计算（已优化）

每条消息可能查 3~4 次权限，每次都要遍历作用域取 min。

**优化**：
- `RoleStore.effective` 加结果缓存（key = `scope\0openid`），写操作时清空
- `ctx.levelOf` 按消息缓存（`msg.__lvl_<pluginId>`）
- 两个作用域查询改 `Promise.all` 并行
- 命令鉴权合并成一次计算

实测 3 次鉴权 = 1 次未命中 + 2 次命中（67%），`/stats` 里能看到命中率。

> 主人判断放在缓存**之前**——`owners` 会在 `/claim` 时变化，不能缓存。

### 14. 限流表无界增长（已修）

`rate` 按会话存，群多了会一直涨。加了「超过 500 条时清理过期窗口」。

### 15. `lastRaw` 深拷贝开销（已优化）

每条消息都 `JSON.stringify` 整个报文（脱敏 + 截断）只为调试用。
改成：debug 级别才保留完整脱敏报文，平时只存摘要字段。

## 八、配置归属错乱（2026-10-23 二次自查）

起因是「再次检查文档和代码漏洞」。这次不只看新功能，把配置的读写链路整个走了一遍。

### 1. 面板改「监听地址 / 端口 / 访问密钥」完全不生效（已修）

现象：表单里改端口 → 提示「已保存」→ 实际什么都没变，重启也没用。

三层原因叠在一起：

1. `GET /api/config` 只返回机器人 `cfg`，而 `webui` 在**全局配置** `config/bot.json`
   → 面板永远显示默认值 `127.0.0.1:15207`，用户看不出当前是什么
2. `PUT /api/config` 里 `cfg.webui = {...}` 写进了**机器人配置**
3. `saveBotConfig` 是白名单式保存，**不保存 `webui`** → 连磁盘都进不去

同一个坑第三次踩（前两次是 `groupManage` 和更早的插件存档路径）。
根因是**字段归属没分清**：哪些是全局的、哪些是 per-bot 的，全靠记忆，没有强制。

**修法**：`webui` 和 `logLevel` 统一走 `globalCfg` + `saveGlobalConfig`，
GET 时把这两个字段补进响应。自检新增「配置归属」6 项断言，
故意把 `webui`/`logLevel` 塞进 cfg 再保存，断言它们不会落进机器人配置。

### 2. 日志级别下拉框不同步（已修）

`logLevel` 确实改了也生效了（写全局配置 + `setLevel`），但 GET 不返回它，
面板刷新后下拉框永远回到 `info`。用户改完看不出自己当前是什么级别。
随上面一起修好了。

### 3. 五处旧路径注释（已修）

`config/plugins/<id>.json`、`data/plugins.json`、`data/plugins/<id>.json`
这些**单机器人时代的旧路径**还有 5 处残留在注释和文档里：

- `src/main.js` 启动横幅
- `src/plugin/config.js` 头部注释
- `src/plugin/context.js` 注释
- `src/plugin/loader.js` 注释
- `docs/插件开发规范.md` 存档路径表

实际路径是 `config/bots/<机器人id>/plugins/<id>.json` 和
`data/bots/<机器人id>/plugins/<id>.json`。已全部改正。

### 遗留

`webui.enabled` 字段前端没有暴露（只能手改配置文件）。如果面板要能「临时关面板」，
得单独加。目前不算 bug，只是功能缺口。

## 九、插件更新 + bot_state 预检（2026-10-23）

### 插件更新：参考 BetterGI 后重做

最初版本每个插件单独 `git clone` 一次仓库——N 个插件就是 N 次完整 clone。
看了 [BetterGI](https://github.com/babalae/better-genshin-impact) 的
`ScriptRepoUpdater` 后重做：**先拉一次中央仓库，再从里面逐个检出**。

借鉴的设计：
- 一次 clone 服务所有待更新插件
- 每个插件独立失败，互不影响；成功/跳过/失败分类汇报
- 「先备份再替换，失败还原」，不会出现更到一半的中间状态
- 备份放系统临时目录，不放 `plugins/` 旁边（否则被 loader 扫成幽灵插件）

接口：`GET /api/plugins/updates`（检测，5 分钟缓存）、
`POST /api/market/update`（单个）、`POST /api/market/update-all`（批量）。
检测是启动后 30 秒 + 每小时自动跑，**安装永远要用户点**——会覆盖本地目录。

### 踩到的坑

**1. `localVersions` 读内存不读磁盘**
最初优先用 `loaded` 里的 `meta.version`，导致用户手动换过 `plugins/` 下的文件后
检测不到更新。改成**磁盘优先**，内存只做兜底。

**2. 端口被旧进程占着，测出新代码没生效**
改完 `localVersions` 后测试，接口还返回旧版本号，一度以为是代码没生效。
实际是 `Get-CimInstance` 发现有**两个 mock serve 进程**，12:21 启动的那个
跑的是旧代码，一直占着 15207。杀掉重启才对。

> 教训：测试面板改动的效果前，先确认只有一个服务进程在跑。

**3. `localVersions` 拼写错误**
`update-all` 里把 `localVers` 写成 `localVersions`，运行时才炸。
已补「28 个源文件全部可导入」的自检——它能在启动前抓住这类导出/引用不同步。

### bot_state 预检（用户指出我之前说错了）

我此前在文档和回复里说「框架无法判断机器人是不是群管理员」。
用户指出 `GET /v2/groups/{group_openid}/bot_state` 就能查——**我说错了**。

该接口返回 `member_role`（`member`/`owner`/`admin`）。已封装成 `canManageGroup()`：

```js
const st = await ctx.api.canManageGroup(groupId);
// { ok: true, role: 'admin', reason: '机器人是群管理员' }
// { ok: false, role: 'member', reason: '机器人只是普通成员，没有群管权限' }
// { ok: false, role: null, reason: '查不到机器人角色：...' }
```

禁言、踢人、入群审批**默认自动预检**：确认只是普通成员就直接抛友好错误，
不用插件自己 try/catch `40062003`。传 `{ precheck: false }` 可跳过。

两个限制（文档里已写明）：
1. `bot_state` 本身是**内邀**接口（`11253`），没申请白名单查不了。
   这时返回 `role: null`，框架**不拦截**，照样发请求让服务端判。
2. 它只有 30 QPM，框架带 60 秒缓存，批量操作不会每次都查。

顺带修正：早期文档把 `bot_state` 归类成「公开接口」也是错的，已改为内邀。

自检 122 → 123 项。

## 十、对标 ElainaBot 补 Webhook 与新接口（2026-10-23）

用户拿 [ElainaBot_v2](https://github.com/ElainaCore/ElainaBot_v2) 来问「要不要放弃本项目」。
调研结论：同为 QQ 官方接口路线，Python / MIT / 70 星，插件生态 66 个（我们 4 个示例）。
决定**保留项目、对标补齐**。

### 补了什么

**1. Webhook 模式（架构级缺口）**

官方支持 WebSocket 和 Webhook 两种收事件方式，我们之前只有前者。
Serverless / 容器 / 公网部署场景下 Webhook 更合适。

- `src/sign.js` —— Ed25519 回调签名。算法：AppSecret 循环填充到 32 字节作私钥种子，
  签 `event_ts + plain_token`，输出 hex。**用公钥验签验证过**，seed 推导与 Python 实现一致
- `src/webhook.js` —— WebhookServer。多机器人共用一个端口，按 `X-Bot-Appid` 分流；
  `op=13` 走签名校验；`INTERACTION_CREATE` 回 `{op:12,code}` ACK；端口被占自动顺延
- 配置：`connection.mode`（机器人级）+ `webhook.*`（全局级）
- 面板配置页加了「收事件方式」下拉

**2. 流式消息（AI 玩法基础）**

`POST /v2/users/{openid}/stream_messages`，**仅单聊**，50 QPS。
封装成 `ctx.api.sendStreamMessage()` + `msg.replyStream()`，

## 十一、用户实机反馈的四个问题（2026-10-23 晚）

### 1. 输了 AppID/AppSecret，还是报「缺少凭证」★

日志：`21:22:06 ERROR [bot:main] 缺少 AppID / AppSecret`，
但用户明明在启动提示里输了。

根因：`ensureBotCredentials()` 的**返回值被丢弃**了。

```js
if (!MOCK && (!cfg.appId || !cfg.appSecret)) {
  await ensureBotCredentials(cfg.id);   // 它返回重新读出来的配置
}
const rt = new BotRuntime({ cfg, ... });  // 用的还是旧的空 cfg
```

`ensureBotCredentials` 内部 `loadBotConfig` 返回的是**新对象**，
写盘了但内存里的 `cfg` 没更新，`BotRuntime` 拿到的还是空凭证。

修法：`Object.assign(cfg, await ensureBotCredentials(cfg.id))`。

### 2. 第一次连接一直「上线中」，第二次才正常 ★

日志：
```
21:23:04 WARN  [gateway] WebSocket 错误: Received network error or non-101 status code.
（之后没有任何日志，卡死）
```

根因：`#connect()` 里 `this.connecting = true` 只在 **open 事件**里复位。
握手失败时 Node 的 WebSocket **只发 error 不发 close**，于是：

1. `connecting` 永远停在 `true`
2. 后续每次 `#connect()` 都被开头 `if (this.connecting) return` 挡掉
3. 重连永远不执行，状态卡在「上线中」

修法：
- 新增 `#failAndRetry(ws)`：统一收尾（复位 connecting、丢弃 ws、安排重连），
  用 `retryScheduledFor` 保证 error + close 双触发时只安排一次
- `error` 事件里调它
- 加 **20 秒连接超时**兜底，防 open/error/close 全都不来的极端情况
- `#scheduleReconnect` 加幂等：已有重连排队就跳过

### 3. 保存配置按钮容易找不到

配置页很长（凭证、intents、白名单、限流、面板设置），保存按钮在最底部，
用户要滚到底才能看到。

修法：
- 保存按钮挪到**连接凭证区块正下方**（用户填完凭证立刻能点）
- 底部 `sticky-actions` 强化：加 `z-index`、实色背景、上边框、阴影
- 新增 `.cred-actions` 样式

### 4. 新增：框架自身检测更新

`src/updater.js`：

- `checkUpdate()` —— 查最新 release。**不用 GitHub API**：未认证每小时只有 60 次，
  按 IP 算，家用宽带很容易被限成 403。改用 `releases/latest` 的 302 重定向取
  版本号，不消耗配额
- `applyUpdate()` —— 下载 tarball（公开直链）、解包、备份、替换
- 面板「概览 → 框架版本」：检查更新 / 立即更新，更新后提示重启

## 十二、补后台服务层（对标 ElainaBot，2026-10-23）

再次对比 ElainaBot_v2（它今天 12:30 还在推），结论变了：

**上次的架构差距已经补平**（Webhook / 流式 / 全局菜单 / Docker / 自更新），
**新的差距在「运行时服务能力」**——它的 `core/services/`（347 行）有五个后台服务，
`core/storage/` 有完整 SQLite 统计体系，`core/plugin/` 有文件监听热重载和

用户选「先补运维五项」，做了：

### 新增 `src/services/`

| 文件 | 服务 | 干什么 |
|---|---|---|
| `base.js` | BaseService | 定时器、异常隔离、状态 |
| `index.js` | Services | 统一启停 + 面板状态 |
| `health.js` | 健康巡检 | 每分钟采样 RSS/积压/重连/会话，5 分钟一条摘要，超阈值 WARNING |

### 几个设计决定

**配置热加载用轮询不用 fs.watch**
Windows 上编辑器「先写临时文件再改名」经常漏事件，网络盘更不可靠。
3 秒比一次 mtime 开销可以忽略，行为稳定得多。

**定时重启 = 拉起新进程再退出**
裸机跑（没 systemd / 没 docker）也能自愈，不依赖外部守护。
新进程启动时旧进程已释放端口和实例锁，不会撞车。

**自动更新默认只检查不安装**
自动装代码风险高——万一新版有 bug，用户是在「不知道发生了什么」的情况下被升级的。

**清理服务的硬约束**
只清 `data/.update-*`、超份数备份、过期 `.log`。
`config/` `data/bots/` `plugins/` 无论配置怎么写都不许动，代码里做了双保险
（FORBIDDEN 列表 + 路径包含检查）。误删存档是最不可接受的 bug。

`index.js` 导入各服务，各服务又 `import { BaseService } from './index.js'`，

```
ReferenceError: Cannot access 'BaseService' before initialization
```

把 `BaseService` 抽到独立的 `base.js` 才解决。index.js 保留一行
`export { BaseService } from './base.js'` 兼容旧引用。

## 十四、用户实机反馈的两个问题（2026-10-24 凌晨）

用户升到 0.5.4 后报了两个问题，日志在 `Desktop/qq-bot-roost/logs/bot.log`。

### 1. 面板打开后机器人自动上线，但下拉菜单要手动刷新才显示 ★

`openBotMenu()` 只重渲染，不重新拉数据：

```js
function openBotMenu() {
  $('#botMenu').hidden = false;
  renderBotMenu(...);   // 用 BOTS 里的旧数据
}
```

`BOTS` 是初始化时拉的快照，那时机器人还没连上网关（启动要 1~2 秒），
所以菜单里永远显示「离线」，得手动点刷新。

修法：
- `openBotMenu()` 改成 async，**每次打开都 `await loadBots()`**
- 先用旧数据立刻渲染（菜单要马上出来，不能等网络），拉到新的再重渲染
- 新增 `syncBotListState()`：`pollStatus` 每 5 秒拿到最新状态后同步回 `BOTS`，
  菜单开着时只改状态点和那一行文字（不整体重渲染，避免搜索框丢焦点）

### 2. 市场装了插件，程序识别不到，提示「没有新插件」★★

日志里这行是关键：

```
00:17:57 INFO [plugins] 本机器人未启用: kun
00:22:28 INFO [plugins] 本机器人未启用: kun
```

**根因是默认配置写错了**：

```js
plugins: { mode: 'include', list: [] }   // 只启用名单内的，而名单是空的
```

字面意思是「一个插件都不启用」。用户从市场装了插件 → 不在名单里 → 不加载。
而面板只列已加载的插件 → 用户看不到它 → 也没法启用。**死循环。**

注释里写的初衷是「避免误触发」，但实际后果是「装了永远不生效」。

修了四处：

**a. 默认值改成 `all`**（装了就用）

**b. 旧配置自动纠正**：`include` + 空 list 在 `loadBotConfig` 里按 `all` 处理，
只改内存不改用户文件，控制台提示一句。

**c. 面板开关和配置过滤器统一**。原来是两套独立机制：
- `isEnabled(id)` 只看 state（面板开关）
- `pluginFilterOf()` 只看 cfg.plugins（配置过滤器）

结果「面板显示已启用，实际没加载」。现在：
- `isEnabled` 同时看 filter
- 启停操作走 `setPluginEnabled()`，同时改配置和 state：
  | 模式 | 启用 | 禁用 |
  |---|---|---|
  | all | 不动 | 转 exclude 并加入名单 |
  | include | 加入名单 | 移出名单 |
  | exclude | 移出名单 | 加入名单 |

**d. 未启用的插件也要列出来**。`list()` 原来只列 `loaded` + `meta`，
现在加上 `diskIds`（scan 时记下的磁盘目录），面板能看到「已禁用」并点启用。

**e. 加载失败不再被吞**。`rescan` 原来只返回 `added/removed`，
加载失败也返回空 `added`，前端只能提示「没有发现新插件」——
「没发现」和「发现了但加载失败」是两回事，却给同一句话。
现在返回 `errors`，前端显示具体原因。

### 验证
- 用旧配置（include + 空 list）启动 → 自动纠正，4 个插件全加载
- 设为 `include:['dice']` → 面板显示 kun/echo/hello-py 为「已禁用」而非隐藏
- 点「启用 kun」→ 配置变成 `include:['dice','kun']`，插件加载
- 点「禁用 dice」→ 配置变成 `include:['kun']`，插件卸载
- 下拉菜单打开即显示「在线」
- 单测 154 → **159**（补 5 项过滤器语义），e2e 95 全过

## 十五、安装提示误报 + 指标不刷新 + 卸载功能（2026-10-24 凌晨）

用户报了两个问题，又要求加卸载功能。

### 1. 提示「插件已安装，但没能自动加载」，其实加载成功了 ★

**根因是我上一版自己埋的**。安装流程是：

```js
await setPluginEnabled(rt, r.id, true);   // ← 这里内部调了 load()
const scanned = await plugins.rescan();    // ← rescan 看到「已加载」就跳过
```

`setPluginEnabled` 会改配置 **并且** 加载插件。等 `rescan` 跑的时候，
插件已经在 `loaded` 里了，`rescan` 的循环第一行 `if (this.loaded.has(id)) continue`
直接跳过，`added` 就是空的。前端拿到空 `added`，只能提示「没能自动加载」。

修法：把「改配置」和「加载」拆成两个函数——
`ensurePluginInList`（只改配置，不 load）+ `setPluginEnabled`（改配置 + load）。
安装流程改用前者，把加载留给 `rescan`，这样 `added` 才有值。

### 2. 插件指标（回声的收发数）不实时刷新

`/api/plugins/dashboard` 只在 `loadPlugins()` 里调一次，**没有任何轮询**。
插件在跑，数字不动。

修法：
- 新增 `refreshPluginDashboards()`，每 5 秒拉一次 dashboard
- **只更新 `.plugin-metrics` 的 innerHTML，不重建卡片**——整块重绘会丢滚动位置、
  正在点的按钮消失，用户会以为界面在抽风
- 指标从无到有时补一个容器（首次渲染时可能还没有指标）
- 只在插件页轮询，切走就 `stopPluginDashPolling()`

### 3. 新增：卸载插件

之前只有安装没有卸载，装错了只能手动删目录。

后端 `POST /api/plugins/:id/remove`：
- id 校验和安装时一致（`^[a-z0-9][a-z0-9_-]{0,31}$`）
- 路径必须严格是 `plugins/` 下的一级子目录（防穿越）
- **先卸运行时再删文件**——顺序反了会出现进程还在读已删除的代码
- 从启用名单移除
- `plugins.forget(id)` 清掉 state 里的残留，否则重装会被旧的 `false` 挡住
- **数据目录保留**（`data/bots/<机器人>/plugins/<id>`），重装还能接着用

前端：卡片加「卸载」按钮（danger 样式），确认弹窗写清「代码删掉、数据保留」。

顺带给 `.plugin` 加了 `flex-wrap: wrap` —— 4 个按钮在窄屏会挤。

### 验证

- 安装 kun → `added:["kun"]`（不再误报）
- 卸载 kun → 目录删除、列表更新、`{"ok":true}`
- 路径穿越 `..%2f..%2fsrc` → 被路由拦掉（404）
- 非法 id `KUN` → 400「插件 id 不合法」
- 不存在的插件 → 404「插件 nosuch 没装」
- 被拒的卸载没动到任何示例插件
- e2e 95 → **100**（补 5 项卸载安全边界 + dashboard）

## 十六、对标补齐六项（2026-10-24 上午，v0.5.7）

第三轮对标 ElainaBot 后列了六项差距，这次一次做完。

### 1. 插件文件变更自动热重载

`src/services/plugin-watch.js`，默认 2 秒轮询一次 `plugins/`。

**用轮询不用 `fs.watch`**：和 `config-watch.js` 同一个理由——Windows 上编辑器
保存走「写临时文件再改名」，`fs.watch` 会漏事件，网络盘更不可靠。
对方（ElainaBot `plugin/_watcher.py`）也是 mtime 轮询，这条路验证过。

**为什么是「文件安静够久」而不是「变了就重载」**：
编辑器保存大文件会分几次写，`fs.cp` 安装插件更是逐个文件复制。
签名里带了最大 mtime，只有「最后修改距今 ≥ 500ms」才动手，
否则会读到半个 `index.js`，报一个莫名其妙的语法错误。

跳过 `node_modules` / `__pycache__` / `.venv` / `data` / `*.log` / `*.pyc`——
这些是运行时产物，变了不代表代码变了。

**安装/卸载要挂起**：`fs.cp` 期间目录里逐个出现文件，那不算「用户改代码」。
`suspendPluginWatch(ms)` 给面板用，装完再收窄窗口。

顺带修了一个老 bug：插件目录被删后，`meta` 里还留着它的记录，
`list()` 会继续列出一个「已禁用 · v0.0.0」的幽灵条目。
现在 `rescan` 卸载时同时 `forget(id)`。

### 2. 插件元数据与版本兼容校验

新增 `src/semver.js`：`compareVersion` + `satisfies`。
顺手把 **三份重复实现合成一份**（market.js、updater.js 各有一份）。

支持 `>=0.5.0`、`>=0.5.0 <1.0.0`、`^0.5.0`、`~0.5.0`、`0.5.x`、`||`。
预发行版按 npm 规则简化：范围里没写 `-` 就一律不满足，
免得 `0.6.0-beta` 被 `>=0.5.0` 判过，作者以为测的是正式版。

`plugin.json` / 默认导出新增：`shortDesc` / `icon` / `repo` /
`frameworkVersion` / `supportPlatforms`。面板卡片显示图标和「需框架 x」。

**兼容性在加载前拦**，不是在运行时炸：插件调一个不存在的 ctx 方法，
报错会指向插件内部，作者和用户都看不出真正原因是「框架太旧」。
作者本地调试可用 `plugins.ignoreFrameworkVersion: true` 硬跑。

### 3. SQLite 统计

`src/storage/`（db / schema / index），用 **Node 22 内置的 `node:sqlite`**，
不引第三方包——零依赖是底线，不能因为要统计就破掉。

四张表：`messages`（明细）/ `daily`（按天汇总）/ `members`（人）/ `commands`（命令）。

**只记数量与时间，不存消息正文。** 这是隐私底线，表结构里根本没有 content 字段，
单测直接断言了这一点。

写入走缓冲：`record()` 只往数组里塞一条，1 秒一次批量事务提交。
收消息是热路径，不能每条都等磁盘。

`open()` 失败（Node < 22.5）只 warn 不抛，`available=false`，
所有查询返回空结构，面板显示「统计不可用」，其它功能不受影响。

面板新增「统计」页：6 个指标卡 + 纯 CSS 柱状图 + 命令/会话排行。
不引图表库——多一个库就破了零依赖。

### 4. 插件注册面板页面

`src/plugin/pages.js` + `ctx.registerPage({key, label, html})`。

- key 统一加 `<插件id>:` 前缀，插件之间不会撞
- 卸载/重载时自动清掉，不留打不开的死标签
- 渲染在 iframe 里：**样式隔离**，CSS 不会漏到面板上
- HTML 上限 512 KB（存在内存里）
- 前端 `loadPluginPages()` 动态加标签，第一次点开才去拉 html

示例：`dice` 插件注册了「骰子战绩」页，从 `/api/plugins/dice/panel` 拿存档渲染。

### 5. 素材缓存 / 模板消息 / 图片 Buffer

- `api.uploadMedia` 加缓存：同一个 url 两天内只上传一次。
  键里带 scene + target——`file_info` 是跟着上传时的会话走的，换群必须重传。
  base64 上传不缓存（做键要算哈希，不值当）。
- `msg.replyCard({markdown, keyboard, ark})`：三样一次带出去。
  分三次发会变成三条独立消息，用户看到三块碎片。
- `msg.replyImageBuffer(buf)`：渲染类插件画完直接发，不用先落盘。

### 6. 图床与渲染示例插件

- `plugins/imgbed`：零依赖，支持 base64 / multipart 两种上传，`resultPath`
  配置从响应里取链接。实测用本地 mock 图床跑通（转存成功 1 张）。
- `plugins/render`：**可选依赖** `@napi-rs/canvas`。没装时命令明确告诉用户
  怎么装，不静默失败。框架不替用户装——渲染是重功能，
  不用的人不该多下几十兆原生模块。

### 踩的坑（这次差点漏过去）

**`export { x } from './y.js'` 不会在本模块内绑定名字。**

把 `compareVersion` 从 market.js 挪到 semver.js 时，写成了 re-export，
结果 `detectUpdates` 里调用它直接 `ReferenceError`。
**模块导入测试照样通过**——它只 import，不执行函数体。

是 e2e 的市场测试报出来的（`/api/market` 500）。补了一条单测真的调一遍
`detectUpdates`，以后这类「引用断了」能被抓住。

教训：**re-export 只对导出方有效，模块内部要另写 import。**
同理，导入测试只能证明「语法和顶层依赖没问题」，证明不了「函数能跑」。

### 验证

- 单测 159 → **220**（+61：热重载 10、semver 18、兼容 5、统计 18、素材模板 10）
- e2e 95 → **115**（+20：统计 6、页面 4、其余为计数修正）
- 热重载实测：改 `echo` 2 秒后重载、新建目录自动加载、删目录自动卸载
- 统计实测：注入 4 条消息（含 1 个 `/roll`）→ total 4、命令榜 dice、成员 3
- 插件页面实测：`#page:dice:rank` 渲染出排行榜，4 个玩家的最高值与次数正确
- 图床实测：本地 mock 服务收到上传，插件指标「转存成功 1 张」

## 十七、v0.5.7 发布后的自查与修复（2026-10-24 上午，v0.5.8）

v0.5.7 发完做了一轮自查，13 项全部修掉。这里记判断依据，不记过程。

### 三个真 bug

**1. scope 标签写错**
`web/app.js` 判 `x.scope === 'channel'`，但 `msg.kind` 只有
`group` / `c2c` / `guild` / `dm`（`src/events.js` 的 `message` 字段）。
`'channel'` 是不存在的值，永远走 else 分支，频道消息全被标成「私聊」。
→ 抽了个 `scopeName()`，顺手把映射写进注释，免得下次又猜。

**2+3. 切机器人不刷新**
`selectBot()` 逐个 if 重拉各页数据，漏一个就错一个。这次漏了两个：stats 和插件页面。

更隐蔽的是**插件页面的 iframe 地址里没有 `bot`**：页面里的
`fetch('/api/plugins/dice/panel')` 不带机器人，服务端按「没传就第一个」处理，
所以多机器人下插件页面永远显示第一个机器人的数据——单机器人测不出来。

→ 改成「地址在点开时才算」（`pluginPageUrl(key)` 读当前 `CURRENT_BOT`），
切机器人后 `src` 变了会自动重载；`dice` 示例把 `bot` 参数原样转发给接口。

教训：**「按机器人隔离」这件事，凡是前端自己发请求的地方都要检查一遍**。
面板的 `api()` 会自动加 `bot`，但 iframe 里跑的页面用的是原生 `fetch`，绕过了这一层。

### 文档与实现不一致

**4. `replyCard` 注释和实现相反**
注释写「ark 和 markdown 同时给时以 markdown 为准」，但 `#payload` 是
先 markdown（msg_type=2）后 ark（msg_type=3），ark 赢，而且两个字段都在 payload 里。
→ 在 `replyCard` 里就丢掉 ark 并 warn。**注释描述的行为要么实现它，要么改注释，
不能放着两边打架**——下一个人会按注释写代码。

**5. 协议文档漏了 frameworkVersion**
loader 对 `plugin.json` 也做校验，但 `docs/插件协议.md` 零处提及。
→ 补「plugin.json 里还能写什么」一节。

**6. 规范示例版本号不可用**
示例写 `>=0.6.0`，当前 0.5.8。抄的人立刻被自己的示例挡住。
→ 改 `>=0.5.0`，并加一句「别写当前还没有的版本号」。

**7. release notes 数字错**
写「e2e 95 → 115（+20）」，实际基线 100（v0.5.6 notes 自己写的），应为 +15。
根因：拿 README 里过期的「95 项」当基线，没去查上一版 notes。
→ 文件改了，GitHub 上 v0.5.7 的正文也用 API 改了。
**以后报数字只认上一版 release notes 或实跑输出，不认 README 里的旧值。**

### 体验与风险

**8. 统计页不轮询** → 打开时 10 秒一轮，切走停（和插件指标同一套思路）。

**9. 热重载死循环**
插件往自己目录写文件 → 签名变 → 重载 → setup 又写 → 2 秒一轮。
不是热重载的 bug，但不设防线会烧 CPU 且用户看不出原因。
→ 加了熔断：30 秒内 3 次就暂停该插件 60 秒 + 明确提示；
文档里在 `ctx.storage` 那节加了醒目提示。

**10. `.deps.json` 被当成代码变更** → 按文件名忽略（后缀判断不了，`SKIP_FILES`）。

**11. 统计口径**
原来在 pipeline 之前记录，去重/白名单拦下的消息也算，数字虚高。
→ 挪到 pipeline 之后，统计「实际处理量」。概览页的「收到消息」仍是 pipeline 前计数，
两个口径各有用途，注释里写清区别。

**12. README 文档索引漏 `对标ElainaBot.md`** → 补。顺手发现自己差点加重复的「架构说明」行。

**13. mock 注入接口没兜错** → 插件抛错返回 `{ok:false, error}`，不再 500。

- e2e 115 → **115**（无新增，全过）
