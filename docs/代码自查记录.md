# 代码自查记录

对全部源码（`src/` 15 个文件、`web/` 3 个文件、`plugins/` 2 个插件）做了一遍通读，
按「安全 → 正确性 → 健壮性 → 性能」的顺序排查。下面是发现的问题与处理结果。

---

## 一、安全

### 1. 事件报文里的 `auth_token` 会被暴露（已修）

群消息报文长这样：

```json
"message_scene": { "ext": ["msg_idx=REFIDX_xxx", "auth_token=laoT7IKvYcoc2yLgruyZ-..."] }
```

原来 `runtime.lastRaw` 直接存原始 JSON，而 `/api/status` 会把它返回给面板。
虽然面板默认只听 `127.0.0.1`，但这属于凭证泄露面。

**修复**：新增 `sanitizePayload()`，递归脱敏：
- `auth_token` / `token` / `secret` / `cookie` 等键名 → `***`
- `ext` 字段整体隐藏
- 字符串里的 `auth_token=xxx`、`msg_idx=xxx` 用正则抹掉

日志里打印未知事件时也走同一个函数。

### 2. 静态文件路径校验可被前缀绕过（已修）

```js
const abs = path.join(WEB_ROOT, filePath);
if (!abs.startsWith(WEB_ROOT)) 403;   // ← 问题在这
```

`startsWith` 是按字符串比较的：如果存在 `web-evil/` 这种同前缀的兄弟目录，
`/../web-evil/x` 解析后仍以 `web` 开头，检查会通过。

**修复**：改用 `path.relative()`，结果以 `..` 开头或为绝对路径就拒绝。

> 补充：WHATWG `URL` 本身会规范化 `..`，所以裸 `..` 走不到这里；
> 真正有风险的是 `%2f` 编码变体，实测已返回 403。

### 3. 面板写接口存在 CSRF 风险（已修）

`/api/config` 这类接口只看访问密钥，不看请求来源。如果没设 `accessKey`，
恶意网页可以用简单表单 POST 打到本地面板端口改配置。

**修复**：所有非 GET 请求强制要求 `Content-Type: application/json`。
跨站表单设不了这个头（设了会触发预检并被拦），实测返回 415。

### 4. 面板输出未转义（已修）

`renderGroups` / `renderRoles` / `renderPlugins` 用模板字符串直接拼服务端数据，
`adminOpenid` 是用户在面板里手填的，理论上可以注入 `<img onerror=...>`。

**修复**：统一用 `escapeHtml()` 包一层。

## 二、正确性

### 5. `gateway.restart()` 完全无效（已修）★

```js
async restart() {
  this.stop();          // ← 这里把 stopped 置成 true
  this.stopped = false; // ← 立刻改回来了
  ...
  await this.#connect(); // ← #connect 第一行 if (this.stopped) return
}
```

面板上点「重连网关」没有任何效果。更糟的是：`stop()` 关闭旧连接后，
close 事件在 300ms 内触发，此时 `stopped` 已经是 `false`，
于是 close 回调又安排了一次重连 → **两条连接同时存在**。

两条连接共用同一个 `sessionId`，后连上的那条发 Resume 会被服务端拒绝：

```
WebSocket 关闭 code=4902 reason=reset by resume
```

然后各自重连、互相踢，形成重连风暴（实测 20 秒内重连 5 次）。

**修复**：
1. `restart()` 里等旧连接真正 `close` 之后再放开 `stopped`
2. `#connect()` 增加守卫：已有 `readyState` 为 0/1 的连接时直接返回
3. 收到 `4902` 时清空 `sessionId`，下次走全新 Identify 而不是 Resume

实测修复后手动重连一次，连接保持在线，`reconnectCount` 不再增长。

### 6. 权限迁移会误伤插件等级（已修）★

旧格式用 `100/80/60/40`，新格式用 `0/1/2/3`，读取时做迁移：

```js
if (lv >= 40 && LEGACY_MAP[lv] !== undefined) { ... }
```

问题：插件号段从 10 开始、每插件 10 个号位，第 4 个插件的等级就是 **40**，
第 6 个是 **60**，第 8 个是 **80**。这些合法值会被当成旧数据转成 3/2/1，
权限直接错乱。

**修复**：加 `__version` 标记，迁移只做一次；并且**跳过 `feature:` 开头的
作用域**——旧版本根本没有插件权限，出现在 feature 作用域的一定是新数据。

实测：`global:80 → 1`、`group:60 → 2` 正确迁移，`feature:60` 和 `feature:40` 原样保留。

### 7. `level: 0` 被当成「缺少参数」（已修）

```js
if (!scope || !openid || !level)   // 0 是 falsy
```

**修复**：改用 `!Number.isInteger(level)`。

### 8. `Math.min` 混入 Promise 得 NaN（已修）

```js
const chat = roles.effective(...);      // 漏了 await
const feature = roles.effective(...);
return Math.min(chat, feature);         // NaN，且不报错
```

后果是所有插件级权限判定静默失败。

**修复**：补 `await`，并改成 `Promise.all` 并行。

## 三、健壮性

### 9. 所有 HTTP 请求没有超时（已修）

`fetch` 默认无限等待。网络卡住时命令会一直挂着，用户看到的是「机器人没反应」。

**修复**：`AbortSignal.timeout(15000)`，凭证接口和开放平台接口都加了。

### 10. 退出时权限数据会丢（已修）

`roles` 的写入有 300ms 防抖，但 `shutdown` 只 flush 了 `groups`，漏了 `roles`。
Ctrl+C 前 300ms 内改的权限会消失。

**修复**：退出、mock 结束时都 `await roles.flush()`。

### 11. 配置文件可能写坏（已修）

`fs.writeFile` 直接覆盖，写到一半断电会留下半个 JSON，下次启动直接崩。

**修复**：写临时文件再 `rename`（原子操作）。

### 12. 心跳假死检测（已加）

原来只发心跳、不检查回执。连接假死（TCP 还在但没有数据）时会一直挂着。

**修复**：记录 `lastAckAt`，连续 2.5 个周期没有 ACK 就主动断开触发重连。

## 四、性能

### 13. 权限查询重复计算（已优化）

每条消息可能查 3~4 次权限，每次都要遍历作用域取 min。

**优化**：
- `RoleStore.effective` 加结果缓存（key = `scope\0openid`），写操作时清空
- `ctx.levelOf` 按消息缓存（`msg.__lvl_<pluginId>`）
- 两个作用域查询改 `Promise.all` 并行
- 命令鉴权合并成一次计算

实测 3 次鉴权 = 1 次未命中 + 2 次命中（67%），`/stats` 里能看到命中率。

> 主人判断放在缓存**之前**——`owners` 会在 `/claim` 时变化，不能缓存。

### 14. 限流表无界增长（已修）

`rate` 按会话存，群多了会一直涨。加了「超过 500 条时清理过期窗口」。

### 15. `lastRaw` 深拷贝开销（已优化）

每条消息都 `JSON.stringify` 整个报文（脱敏 + 截断）只为调试用。
改成：debug 级别才保留完整脱敏报文，平时只存摘要字段。

## 八、配置归属错乱（2026-10-23 二次自查）

起因是「再次检查文档和代码漏洞」。这次不只看新功能，把配置的读写链路整个走了一遍。

### 1. 面板改「监听地址 / 端口 / 访问密钥」完全不生效（已修）

现象：表单里改端口 → 提示「已保存」→ 实际什么都没变，重启也没用。

三层原因叠在一起：

1. `GET /api/config` 只返回机器人 `cfg`，而 `webui` 在**全局配置** `config/bot.json`
   → 面板永远显示默认值 `127.0.0.1:15207`，用户看不出当前是什么
2. `PUT /api/config` 里 `cfg.webui = {...}` 写进了**机器人配置**
3. `saveBotConfig` 是白名单式保存，**不保存 `webui`** → 连磁盘都进不去

同一个坑第三次踩（前两次是 `groupManage` 和更早的插件存档路径）。
根因是**字段归属没分清**：哪些是全局的、哪些是 per-bot 的，全靠记忆，没有强制。

**修法**：`webui` 和 `logLevel` 统一走 `globalCfg` + `saveGlobalConfig`，
GET 时把这两个字段补进响应。自检新增「配置归属」6 项断言，
故意把 `webui`/`logLevel` 塞进 cfg 再保存，断言它们不会落进机器人配置。

### 2. 日志级别下拉框不同步（已修）

`logLevel` 确实改了也生效了（写全局配置 + `setLevel`），但 GET 不返回它，
面板刷新后下拉框永远回到 `info`。用户改完看不出自己当前是什么级别。
随上面一起修好了。

### 3. 五处旧路径注释（已修）

`config/plugins/<id>.json`、`data/plugins.json`、`data/plugins/<id>.json`
这些**单机器人时代的旧路径**还有 5 处残留在注释和文档里：

- `src/main.js` 启动横幅
- `src/plugin/config.js` 头部注释
- `src/plugin/context.js` 注释
- `src/plugin/loader.js` 注释
- `docs/插件开发规范.md` 存档路径表

实际路径是 `config/bots/<机器人id>/plugins/<id>.json` 和
`data/bots/<机器人id>/plugins/<id>.json`。已全部改正。

### 遗留

`webui.enabled` 字段前端没有暴露（只能手改配置文件）。如果面板要能「临时关面板」，
得单独加。目前不算 bug，只是功能缺口。

## 九、插件更新 + bot_state 预检（2026-10-23）

### 插件更新：参考 BetterGI 后重做

最初版本每个插件单独 `git clone` 一次仓库——N 个插件就是 N 次完整 clone。
看了 [BetterGI](https://github.com/babalae/better-genshin-impact) 的
`ScriptRepoUpdater` 后重做：**先拉一次中央仓库，再从里面逐个检出**。

借鉴的设计：
- 一次 clone 服务所有待更新插件
- 每个插件独立失败，互不影响；成功/跳过/失败分类汇报
- 「先备份再替换，失败还原」，不会出现更到一半的中间状态
- 备份放系统临时目录，不放 `plugins/` 旁边（否则被 loader 扫成幽灵插件）

接口：`GET /api/plugins/updates`（检测，5 分钟缓存）、
`POST /api/market/update`（单个）、`POST /api/market/update-all`（批量）。
检测是启动后 30 秒 + 每小时自动跑，**安装永远要用户点**——会覆盖本地目录。

### 踩到的坑

**1. `localVersions` 读内存不读磁盘**
最初优先用 `loaded` 里的 `meta.version`，导致用户手动换过 `plugins/` 下的文件后
检测不到更新。改成**磁盘优先**，内存只做兜底。

**2. 端口被旧进程占着，测出新代码没生效**
改完 `localVersions` 后测试，接口还返回旧版本号，一度以为是代码没生效。
实际是 `Get-CimInstance` 发现有**两个 mock serve 进程**，12:21 启动的那个
跑的是旧代码，一直占着 15207。杀掉重启才对。

> 教训：测试面板改动的效果前，先确认只有一个服务进程在跑。

**3. `localVersions` 拼写错误**
`update-all` 里把 `localVers` 写成 `localVersions`，运行时才炸。
已补「28 个源文件全部可导入」的自检——它能在启动前抓住这类导出/引用不同步。

### bot_state 预检（用户指出我之前说错了）

我此前在文档和回复里说「框架无法判断机器人是不是群管理员」。
用户指出 `GET /v2/groups/{group_openid}/bot_state` 就能查——**我说错了**。

该接口返回 `member_role`（`member`/`owner`/`admin`）。已封装成 `canManageGroup()`：

```js
const st = await ctx.api.canManageGroup(groupId);
// { ok: true, role: 'admin', reason: '机器人是群管理员' }
// { ok: false, role: 'member', reason: '机器人只是普通成员，没有群管权限' }
// { ok: false, role: null, reason: '查不到机器人角色：...' }
```

禁言、踢人、入群审批**默认自动预检**：确认只是普通成员就直接抛友好错误，
不用插件自己 try/catch `40062003`。传 `{ precheck: false }` 可跳过。

两个限制（文档里已写明）：
1. `bot_state` 本身是**内邀**接口（`11253`），没申请白名单查不了。
   这时返回 `role: null`，框架**不拦截**，照样发请求让服务端判。
2. 它只有 30 QPM，框架带 60 秒缓存，批量操作不会每次都查。

顺带修正：早期文档把 `bot_state` 归类成「公开接口」也是错的，已改为内邀。

自检 122 → 123 项。

## 十、对标 ElainaBot 补 Webhook 与新接口（2026-10-23）

用户拿 [ElainaBot_v2](https://github.com/ElainaCore/ElainaBot_v2) 来问「要不要放弃本项目」。
调研结论：同为 QQ 官方接口路线，Python / MIT / 70 星，插件生态 66 个（我们 4 个示例）。
决定**保留项目、对标补齐**。

### 补了什么

**1. Webhook 模式（架构级缺口）**

官方支持 WebSocket 和 Webhook 两种收事件方式，我们之前只有前者。
Serverless / 容器 / 公网部署场景下 Webhook 更合适。

- `src/sign.js` —— Ed25519 回调签名。算法：AppSecret 循环填充到 32 字节作私钥种子，
  签 `event_ts + plain_token`，输出 hex。**用公钥验签验证过**，seed 推导与 Python 实现一致
- `src/webhook.js` —— WebhookServer。多机器人共用一个端口，按 `X-Bot-Appid` 分流；
  `op=13` 走签名校验；`INTERACTION_CREATE` 回 `{op:12,code}` ACK；端口被占自动顺延
- 配置：`connection.mode`（机器人级）+ `webhook.*`（全局级）
- 面板配置页加了「收事件方式」下拉

**2. 流式消息（AI 玩法基础）**

`POST /v2/users/{openid}/stream_messages`，**仅单聊**，50 QPS。
封装成 `ctx.api.sendStreamMessage()` + `msg.replyStream()`，
自动维护 `index` 和 `stream_msg_id`，群聊自动降级成普通 markdown。

顺带发现官方字段 `is_wakeup`：置 true 时**不校验 msg_id 有效期**，
是绕开被动回复 5 分钟窗口的官方口子。ElainaBot 的 `send_wakeup` 就是靠它。

**3. 全局自定义菜单**

`GET/PUT /v2/menu`，仅 C2C 场景，最多 10 项。封装成 `getGlobalMenu()` / `setGlobalMenu()`。

> 注：ElainaBot 的 `get_share_link`、`force_wakeup` 在官方 sitemap 里**找不到对应接口**，
> 是它自己封装的，没有照抄。

**4. Docker 部署**

`Dockerfile` + `docker-compose.yml`。镜像不装任何 npm 包（项目零依赖），
用 `node:22-alpine`，非 root 运行。
配套加了 `ROOST_*` 环境变量覆盖（`loadGlobalConfig` 里），
容器里不用改配置文件就能调端口 / 密钥 / Webhook。

### 踩到的坑

**1. `saveBotConfig` 白名单第四次**
加 `connection` 字段时又忘了加进保存白名单。这次是因为自检的「配置归属」断言
只覆盖了 `webui`/`logLevel`，新字段没覆盖到。

**2. 并发请求 GitHub 被限流**
e2e 里 `/api/market` 偶发失败，但 `/api/plugins/updates` 成功。
排查发现是启动 30 秒后的**自动更新检查**和市场测试**并发**打 GitHub，
两个请求互相拖累一起超时。

修法：
- `fetchIndex` 加 **in-flight 去重**——同一时刻多个调用只发一个请求
- 自动检查从启动后 30 秒延到 60 秒
- 超时 15s → 20s，失败重试一次（4xx 不重试）

**3. 测试断言写错两次**
- op=13 验证请求忘了带 `X-Bot-Appid` 头（服务端行为是对的，没 appid 一律 400）
- `/api/groups` 返回的是裸数组，不是 `{groups:[]}`

## 十一、用户实机反馈的四个问题（2026-10-23 晚）

用户用 `.bat` 启动 0.5.1 实测，报了四个问题。日志在
`Desktop/qq-bot-roost-0.5.1/logs/bot.log`。

### 1. 输了 AppID/AppSecret，还是报「缺少凭证」★

日志：`21:22:06 ERROR [bot:main] 缺少 AppID / AppSecret`，
但用户明明在启动提示里输了。

根因：`ensureBotCredentials()` 的**返回值被丢弃**了。

```js
if (!MOCK && (!cfg.appId || !cfg.appSecret)) {
  await ensureBotCredentials(cfg.id);   // 它返回重新读出来的配置
}
const rt = new BotRuntime({ cfg, ... });  // 用的还是旧的空 cfg
```

`ensureBotCredentials` 内部 `loadBotConfig` 返回的是**新对象**，
写盘了但内存里的 `cfg` 没更新，`BotRuntime` 拿到的还是空凭证。

修法：`Object.assign(cfg, await ensureBotCredentials(cfg.id))`。

### 2. 第一次连接一直「上线中」，第二次才正常 ★

日志：
```
21:23:04 WARN  [gateway] WebSocket 错误: Received network error or non-101 status code.
（之后没有任何日志，卡死）
```

根因：`#connect()` 里 `this.connecting = true` 只在 **open 事件**里复位。
握手失败时 Node 的 WebSocket **只发 error 不发 close**，于是：

1. `connecting` 永远停在 `true`
2. 后续每次 `#connect()` 都被开头 `if (this.connecting) return` 挡掉
3. 重连永远不执行，状态卡在「上线中」

修法：
- 新增 `#failAndRetry(ws)`：统一收尾（复位 connecting、丢弃 ws、安排重连），
  用 `retryScheduledFor` 保证 error + close 双触发时只安排一次
- `error` 事件里调它
- 加 **20 秒连接超时**兜底，防 open/error/close 全都不来的极端情况
- `#scheduleReconnect` 加幂等：已有重连排队就跳过

### 3. 保存配置按钮容易找不到

配置页很长（凭证、intents、白名单、限流、面板设置），保存按钮在最底部，
用户要滚到底才能看到。

修法：
- 保存按钮挪到**连接凭证区块正下方**（用户填完凭证立刻能点）
- 底部 `sticky-actions` 强化：加 `z-index`、实色背景、上边框、阴影
- 新增 `.cred-actions` 样式

### 4. 新增：框架自身检测更新

`src/updater.js`：

- `checkUpdate()` —— 查最新 release。**不用 GitHub API**：未认证每小时只有 60 次，
  按 IP 算，家用宽带很容易被限成 403。改用 `releases/latest` 的 302 重定向取
  版本号，不消耗配额
- `applyUpdate()` —— 下载 tarball（公开直链）、解包、备份、替换
- 面板「概览 → 框架版本」：检查更新 / 立即更新，更新后提示重启

**安全设计**：
- 只替换 `CODE_ENTRIES`（src / web / test / docs / package.json 等），
  **绝不碰** config / data / logs / plugins
- 替换前整个代码目录备份到 `data/backups/<旧版本>-<时间>/`，失败自动还原
- 校验新包里必须有 `src/main.js`，否则拒绝
- 不自动重启，让用户自己重启看日志

### 更新功能的两个坑

**1. tar 顶层目录剥离写错**

最初用 `entries[0].name.split('/')[0]` 当顶层目录。GitHub 的包第一条是
`qq-bot-roost-0.5.1/`，没问题；但用 `tar czf` 自己打的包第一条是 `./`，
算出来 `first = '.'`，所有路径都剥不掉，校验直接失败。

改成：先去掉 `./` 前缀，再看所有条目的**公共顶层段**，只有一个才剥。
扁平结构的包不剥。

**2. GitHub API 403**

最初用 `api.github.com/repos/.../releases/latest`，实测返回 403
（未认证 60 次/小时，按 IP 算）。改成 302 重定向方案后稳定。
