# 代码自查记录

对全部源码（`src/` 15 个文件、`web/` 3 个文件、`plugins/` 2 个插件）做了一遍通读，
按「安全 → 正确性 → 健壮性 → 性能」的顺序排查。下面是发现的问题与处理结果。

---

## 一、安全

### 1. 事件报文里的 `auth_token` 会被暴露（已修）

群消息报文长这样：

```json
"message_scene": { "ext": ["msg_idx=REFIDX_xxx", "auth_token=laoT7IKvYcoc2yLgruyZ-..."] }
```

原来 `runtime.lastRaw` 直接存原始 JSON，而 `/api/status` 会把它返回给面板。
虽然面板默认只听 `127.0.0.1`，但这属于凭证泄露面。

**修复**：新增 `sanitizePayload()`，递归脱敏：
- `auth_token` / `token` / `secret` / `cookie` 等键名 → `***`
- `ext` 字段整体隐藏
- 字符串里的 `auth_token=xxx`、`msg_idx=xxx` 用正则抹掉

日志里打印未知事件时也走同一个函数。

### 2. 静态文件路径校验可被前缀绕过（已修）

```js
const abs = path.join(WEB_ROOT, filePath);
if (!abs.startsWith(WEB_ROOT)) 403;   // ← 问题在这
```

`startsWith` 是按字符串比较的：如果存在 `web-evil/` 这种同前缀的兄弟目录，
`/../web-evil/x` 解析后仍以 `web` 开头，检查会通过。

**修复**：改用 `path.relative()`，结果以 `..` 开头或为绝对路径就拒绝。

> 补充：WHATWG `URL` 本身会规范化 `..`，所以裸 `..` 走不到这里；
> 真正有风险的是 `%2f` 编码变体，实测已返回 403。

### 3. 面板写接口存在 CSRF 风险（已修）

`/api/config` 这类接口只看访问密钥，不看请求来源。如果没设 `accessKey`，
恶意网页可以用简单表单 POST 打到本地面板端口改配置。

**修复**：所有非 GET 请求强制要求 `Content-Type: application/json`。
跨站表单设不了这个头（设了会触发预检并被拦），实测返回 415。

### 4. 面板输出未转义（已修）

`renderGroups` / `renderRoles` / `renderPlugins` 用模板字符串直接拼服务端数据，
`adminOpenid` 是用户在面板里手填的，理论上可以注入 `<img onerror=...>`。

**修复**：统一用 `escapeHtml()` 包一层。

## 二、正确性

### 5. `gateway.restart()` 完全无效（已修）★

```js
async restart() {
  this.stop();          // ← 这里把 stopped 置成 true
  this.stopped = false; // ← 立刻改回来了
  ...
  await this.#connect(); // ← #connect 第一行 if (this.stopped) return
}
```

面板上点「重连网关」没有任何效果。更糟的是：`stop()` 关闭旧连接后，
close 事件在 300ms 内触发，此时 `stopped` 已经是 `false`，
于是 close 回调又安排了一次重连 → **两条连接同时存在**。

两条连接共用同一个 `sessionId`，后连上的那条发 Resume 会被服务端拒绝：

```
WebSocket 关闭 code=4902 reason=reset by resume
```

然后各自重连、互相踢，形成重连风暴（实测 20 秒内重连 5 次）。

**修复**：
1. `restart()` 里等旧连接真正 `close` 之后再放开 `stopped`
2. `#connect()` 增加守卫：已有 `readyState` 为 0/1 的连接时直接返回
3. 收到 `4902` 时清空 `sessionId`，下次走全新 Identify 而不是 Resume

实测修复后手动重连一次，连接保持在线，`reconnectCount` 不再增长。

### 6. 权限迁移会误伤插件等级（已修）★

旧格式用 `100/80/60/40`，新格式用 `0/1/2/3`，读取时做迁移：

```js
if (lv >= 40 && LEGACY_MAP[lv] !== undefined) { ... }
```

问题：插件号段从 10 开始、每插件 10 个号位，第 4 个插件的等级就是 **40**，
第 6 个是 **60**，第 8 个是 **80**。这些合法值会被当成旧数据转成 3/2/1，
权限直接错乱。

**修复**：加 `__version` 标记，迁移只做一次；并且**跳过 `feature:` 开头的
作用域**——旧版本根本没有插件权限，出现在 feature 作用域的一定是新数据。

实测：`global:80 → 1`、`group:60 → 2` 正确迁移，`feature:60` 和 `feature:40` 原样保留。

### 7. `level: 0` 被当成「缺少参数」（已修）

```js
if (!scope || !openid || !level)   // 0 是 falsy
```

**修复**：改用 `!Number.isInteger(level)`。

### 8. `Math.min` 混入 Promise 得 NaN（已修）

```js
const chat = roles.effective(...);      // 漏了 await
const feature = roles.effective(...);
return Math.min(chat, feature);         // NaN，且不报错
```

后果是所有插件级权限判定静默失败。

**修复**：补 `await`，并改成 `Promise.all` 并行。

## 三、健壮性

### 9. 所有 HTTP 请求没有超时（已修）

`fetch` 默认无限等待。网络卡住时命令会一直挂着，用户看到的是「机器人没反应」。

**修复**：`AbortSignal.timeout(15000)`，凭证接口和开放平台接口都加了。

### 10. 退出时权限数据会丢（已修）

`roles` 的写入有 300ms 防抖，但 `shutdown` 只 flush 了 `groups`，漏了 `roles`。
Ctrl+C 前 300ms 内改的权限会消失。

**修复**：退出、mock 结束时都 `await roles.flush()`。

### 11. 配置文件可能写坏（已修）

`fs.writeFile` 直接覆盖，写到一半断电会留下半个 JSON，下次启动直接崩。

**修复**：写临时文件再 `rename`（原子操作）。

### 12. 心跳假死检测（已加）

原来只发心跳、不检查回执。连接假死（TCP 还在但没有数据）时会一直挂着。

**修复**：记录 `lastAckAt`，连续 2.5 个周期没有 ACK 就主动断开触发重连。

## 四、性能

### 13. 权限查询重复计算（已优化）

每条消息可能查 3~4 次权限，每次都要遍历作用域取 min。

**优化**：
- `RoleStore.effective` 加结果缓存（key = `scope\0openid`），写操作时清空
- `ctx.levelOf` 按消息缓存（`msg.__lvl_<pluginId>`）
- 两个作用域查询改 `Promise.all` 并行
- 命令鉴权合并成一次计算

实测 3 次鉴权 = 1 次未命中 + 2 次命中（67%），`/stats` 里能看到命中率。

> 主人判断放在缓存**之前**——`owners` 会在 `/claim` 时变化，不能缓存。

### 14. 限流表无界增长（已修）

`rate` 按会话存，群多了会一直涨。加了「超过 500 条时清理过期窗口」。

### 15. `lastRaw` 深拷贝开销（已优化）

每条消息都 `JSON.stringify` 整个报文（脱敏 + 截断）只为调试用。
改成：debug 级别才保留完整脱敏报文，平时只存摘要字段。

## 五、已确认但暂不处理

| 问题 | 原因 |
|------|------|
| 插件与内核同进程 | 一个插件死循环会拖垮整个机器人。改 `worker_threads` 是架构级改动，等有实际需求再做 |
| 新增插件可能导致号段漂移 | 按 id 排序分配，新插件插到前面会让后面的整体后移。已加 WARN 日志提示重启，彻底解决要持久化分配表 |
| 频道消息只收不发 | v2 的频道发送接口没接，当前场景用不到 |
| 未做分片（shard） | 单连接够用，几千个群再说 |
| 面板无登录态 | 只有访问密钥，没有会话。别直接暴露公网 |

## 七、文档与官方接口核对（2026-10-23）

起因：记得官方开放了群管接口，但文档写「没提供」。逐条核对后**文档错得不止一处**。

### 核对方法

官方 wiki 是 SPA，`WebFetch` 只能拿到导航壳。两条可行路径：

1. **`bot.q.qq.com/wiki/sitemap.xml`** —— 拿到全部 47 个 autogen 接口的 URL 清单
2. **接口详情在 HTML 正文里**，`curl` 拿页面后剥标签即可（内容不在 JS chunk 中）

另外 `github.com/tencent-connect/bot-docs` 是官方文档仓库，但它**落后于 wiki**：
群成员接口整段被 HTML 注释包着、标注「内邀开放」，wiki 的 autogen 才是最新。
只信仓库会漏掉 2026-08 之后新增的禁言/踢人。

### 发现的问题

| 文档原话 | 实际 |
|----------|------|
| 群成员列表「没有接口」 | 有 `GET /v2/groups/{group_openid}/members`，但**内邀中**（返回 `11253`） |
| 踢人「明确未开放」 | `POST /v2/groups/{group_openid}/batch_remove_members`，**内邀中** |
| 禁言「明确未开放」 | `GET/POST /v2/groups/{group_openid}/restrict_chat_setting`，**已开放** |
| 撤回他人消息「做不到」 | `DELETE /v2/groups/{group_openid}/messages/{message_id}`，**已开放** |

「群列表没有查询接口」和「用户 QQ 号不可读」这两条**是对的**，21 个群接口里确实没有。

### 官方群管理接口的真实状态（21 个）

- **已开放**：群基本信息、机器人群内状态、群禁言（查/设）、撤回群消息、
  入群申请列表/审批、入群自动审批策略（6 个）
- **内邀中**：群成员列表、群成员信息、群成员批量移除、群黑名单（查/操作）

禁言的硬约束（文档里已补）：机器人**必须是群管理员**，最长 30 天，
单次最多 20 人，`op` 为 `add`/`update`/`del`，**只能操作普通成员**。
撤回的硬约束：2 分钟内，群管理员可撤普通成员的消息。

### 顺带发现代码注释也是错的

`src/api.js` 的 `retractGroupMessage` 注释写「只能撤回机器人自己发的」——
官方明确群管理员可以撤普通成员的消息。已改为准确描述，
并说明框架**不做预检**（2 分钟时限和权限都是服务端判，失败看错误码）。

### 改动范围

只改文档和注释，**没有动任何逻辑**：

- `docs/官方接口限制.md`：重写第二节，新增「二·补、群管理接口现状」，
  含完整接口表、禁言/撤回的约束、错误码
- `docs/插件开发规范.md`：「做不到的事」改为准确表述
- `README.md`：两处「已知限制」同步修正
- `src/api.js`：`retractGroupMessage` 注释

### 还没做的

`src/api.js` 只封装了撤回，禁言 / 群信息 / 入群审批都没包。
`QQApi` 的 `#request` 是私有的，插件**无法自己发请求**——
要支持群管玩法得先在 api.js 补公开方法。这属于新增能力，等确认再做。
