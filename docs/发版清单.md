# 发版清单（PR 驱动 · CI 自动发版）

发版从「本地手工七步」改成「**改版本 → 开 PR → 合并 → CI 自动发**」。
人只决定版本号和 notes，剩下的 tag / Release / npm 由 `release.yml` 串起来做。
**每一步后面都写了漏掉的后果**，因为这些都是真踩过的。

## 0. 总流程（先看这个）

1. 从 master 拉分支，改代码 + bump 版本 + 写 notes + 重生成指纹（下面 1–3 步）
2. 开 PR → CI 全绿（框架仓 8 项必需检查）→ 合并进 master
3. 合并触发 `release.yml`，两个 job：
   - **发版前校验**：版本必须递增、notes 顶部段版本 = package.json、指纹与内容一致
   - **建 tag / 验签 / Release / 发 npm / 发后自检**：**停下等你点 Approve**（`Release` environment），
     批准后自动做：CI 代签 → 验签门禁 → 建 tag → 建 Release → 上传 `SHA256SUMS`+`.sig` 附件
     → 发 npm → 发后自检 → `beta` 对齐
4. 核对两端（第 6 步）——CI 已经自动核对过的项目，这里只是二次确认

关键变化：**不再手动推 tag、不再本地签名、不再本地发 npm、不再本地对 beta**。
人只决定版本号和 notes，其余由 CI 串起来。
分支保护已开（require PR + CI 检查），直接 push master/main 会被拒（管理员可绕过，但日常别用）。

## 1. 改完代码、跑测试

- [ ] `npm test`（单元 + 依赖）、`npm run test:e2e`
- [ ] `node scripts/check-secrets.mjs`

> 指纹**不要在这一步跑**，见第 2 步。

## 2. 改版本号与文档（必须先 bump，再生成指纹）

- [ ] `package.json` 的 `version` —— **先改这个**
- [ ] `RELEASE_NOTES.md`：新版本段落写在**最上面**
- [ ] **`README.md` 里会过期的数字都要对一遍**：
  - 版本徽章（`badge/version-x.y.z`）——**这是硬门禁**：`ci.yml` 的 `版本徽章` job
    已进必需检查，徽章和 `package.json` 不一致，PR 直接过不了
  - 测试数量徽章（`431/431` 这种，改了测试就会变）
  - 官方接口数量、插件数量、文档里写死的行号/文件名
  - 这些是硬编码的，代码改了不跟着改就会挂一个错的数字在上面
- [ ] 其他提到版本号的文档（`docs/*.md` 里的「当前版本」段）

## 3. 生成内容指纹（bump 之后才跑）

- [ ] **先 `git add`，再跑 `npm run sums`**
  - ⚠️ **`npm run sums` 会改写 `SHA256SUMS`，改完必须再 `git add SHA256SUMS` 一次**
  - 漏了会怎样：`git add -A` 是在 sums **之前**做的，sums 之后文件又变了，
    不带 `-a` 的 `git commit` 只提交已暂存的内容 → **提交里是旧指纹**，
    package.json 已是新版本而 SHA256SUMS 没有那一行 → CI 的「当前版本必须已有内容指纹」
    直接红，tag 上的「指纹必须与当前代码一致」也红
  - 2026-10-29 的 0.9.0 就栽在这：npm 包不含 SHA256SUMS 所以 npm 没事，
    但 GitHub 的 tarball 里是旧指纹，用户的自动更新会校验失败；
    只能补一个提交 + `git tag -f` 移动 tag 补救（tag 一推不可撤回，验证窗口只在推之前）
  - 漏了会怎样：`build-sums.mjs` 用 `git ls-files` 拿文件清单，**未跟踪的新文件不在清单里**。
    先跑 sums 再 `git add -A` → 文件集多了几个 → 指纹对不上 → tag 上的「发布指纹校验」直接红。
    2026-10-29 的 0.8.14 就栽在这（`src/reach.js` 和一份新文档还是未跟踪），只能移动 tag 补救
  - 正确的顺序是：改完 → `git add -A` → bump → `npm run sums` → `sums:verify` → commit
- [ ] `npm run sums` —— 重新生成当前版本的内容指纹
  - 漏了会怎样：`updater.js` 是严格模式，用户的自动更新会因为「拿不到指纹」被拒绝
  - 什么时候必须重跑：动了 `src/` `web/` `test/` `docs/` `package.json` `README.md` `LICENSE` `start.bat` 里任何一个
- [ ] `npm run sums:verify` 应该通过（指纹与工作区一致）
- [ ] **`git diff -- SHA256SUMS` 只应看到新增一行，旧版本的条目一个都不能变**
  - 顺序错了会怎样：`build-sums.mjs` 按 `package.json` 里的**当前**版本写入。bump 之前跑 → 新代码的指纹被写进**上一个已发布版本**的条目 → 那个 tag 的 tarball 就和指纹对不上 → 所有用户的自动更新被校验拒绝，而且报的是「你的代码有改动」这种误导性错误
  - 已经写错了怎么救：`git checkout <旧tag> -- SHA256SUMS` 把旧条目找回来，然后 bump 一个新版本重跑
  - 铁律：**版本一旦发布，它那条指纹就冻结了**，它对应的是那个 tag 的 tarball，不是 master

## 3.5 签名（供应链）

> 私钥在发版机的 `keys/trust-private.pem`（`keys/` 已 gitignore），**永远不进仓库**。
> 公钥内嵌在 `src/trust.js` 的 `EMBEDDED_PUBKEY`，是公开的。

### 框架仓：已全自动，本地不用签（2026-11-19 起）

- [ ] **什么都不用做**。`SIGN_IN_CI=true` 已开，发版 job 会自己签：
  - 私钥来自 `Release` environment 的 secret `TRUST_PRIVATE_PEM`，
    只有人工批准 environment 之后才注入，用完立即从 runner 删除
  - `SHA256SUMS` 变了就重签，签名仍有效则跳过（重跑幂等）
  - 签完用内嵌公钥验一遍（**验签门禁**），私钥公钥不配对直接红，不发版
  - 最后把 `SHA256SUMS` 和 `.sig` **成对挂到 Release 附件**——
    updater 优先从 `releases/download/v<版本>/` 拉这一对
- 只提交 `SHA256SUMS`，`.sig` 不必再跟着改
- **仓库里不再有 `SHA256SUMS.sig`**（2026-11-19 删除，并已加进 `.gitignore`）：
  签名只存在于 Release 附件里，每次发版都是新的。以前留一份在仓库会随版本过期，
  走 master / Gitee 的用户拿到 `bad`（"内容和签名对不上"，看着像被篡改）；
  现在这条路拿到 `unsigned`（"没有签名文件"），诚实且不误导
- 代价：Gitee 镜像和很老的 updater 拿不到签名（`enforce` 没开，只影响日志）。
  等迁到组织仓（能用 bypass 直推 master）时再闭环
- 想临时退回本地签：把仓库变量 `SIGN_IN_CI` 改成 `false`，然后
  `node scripts/sign.mjs SHA256SUMS --key keys/trust-private.pem --key-id roost-<年>-<月>`，
  再把产物 `git add -f SHA256SUMS.sig`（它已在 `.gitignore` 里，必须 `-f`）一起提交，
  否则验签门禁会因为「没有签名文件」直接红。
  产出与 CI 签的字节完全相同（Ed25519 是确定性签名），只是换谁执行

### 插件仓：仍需本地签

- [ ] **插件仓**：`ROOST_TRUST_KEY=<私钥路径> node scripts/build-index.mjs`
  - 生成索引时顺手签名，产出 `index.json.sig`
  - 只补签：`node scripts/sign-index.mjs --key <私钥>`
  - 校验：`node scripts/sign-index.mjs --verify`
- [ ] 确认 `.sig` 已进提交（`git status` 里能看到）
- 漏了会怎样：等面板「插件来源校验」开关打开后，**用户装不了插件、也更新不了框架**
  （`bad` 直接拒，`unsigned` 不在白名单也拒）。开关默认关，所以漏了不会立刻出事，
  但下一版打开时就是全体事故

## 4. 开 PR 并合并（不再手动推 tag）

- [ ] `git add -A && git commit`（确认 `SHA256SUMS` 进了提交；框架仓 `.sig` 由 CI 生成，不必带）
- [ ] `git push` 推分支 → 开 PR → 等 CI 全绿 → 合并进 master
  - **不要手动 `git tag` / `git push origin v<版本>`**——tag 由 CI 建，手动推会造成「tag 存在 but 内容没校验」的坏状态
- [ ] 合并后看 `发版`（release.yml）这个 workflow：
  - `发版前校验` job：指纹与内容一致、notes 顶部段版本 = package.json 版本，任一不过就红且不发版
  - `建 tag / 验签 / Release / 发 npm / 发后自检` job：**会停在等待 `Release` environment 批准**——这是设计的闸门（把「提交前先问」变成系统强制），你去 Actions 页点 Approve 才继续

- [ ] 点批准后，确认该 job 依次完成：验签门禁 → 建 tag `v<版本>` → 建 GitHub Release
      → 上传 `SHA256SUMS` + `.sig` 附件 → 发 npm → 发后自检
  （只看「有没有触发」不算数，要看每一步都绿；发后自检会核对
  `releases/latest`、npm 版本、以及两个附件是否真的挂上去了）

### ⚠️ GitHub Release 由 CI 自动建（但要核对）

PR 合并后 `release.yml` 的 `建 tag / 验签 / Release / 发 npm / 发后自检` job 会**自动建 Release**，不用再手工建。
前提：notes 顶部段版本 = 版本号、指纹校验都通过、且你批准了 `Release` environment；
不通过 CI 会红且**不建**，这时要先修 notes/指纹再重发 PR，别手工硬建绕过校验。

只推 tag **不建 Release** 的话，框架的检查更新就失效了：

- 检查更新读的是 `https://github.com/<owner>/<repo>/releases/latest`，
  它 302 到「最新的 Release」。没有 Release 时会 302 到**上一个版本的 Release**，
  于是解析出「最新 = 旧版本」→ 对已升到新版的用户 `hasUpdate=false`，
  **永远显示「已是最新」**，检查更新彻底失效。
- 2026-10-28 就栽在这：0.8.8 和 0.8.9 只推了 tag 没建 Release，
  `releases/latest` 停在 0.8.7。

CI 自动建的内容：标题 = `v<版本> — <一句话主题>`（由 notes 顶部段 `## v<版本>：<主题>` 转换），
正文 = `RELEASE_NOTES.md` 顶部段。已存在同 tag 的 Release 会**跳过、不覆盖人工内容**，
所以重跑 CI 不会重复建、也不会冲掉手工编辑。

- [ ] 去 Release 页确认 CI 建的标题、正文正确（`https://github.com/<owner>/<repo>/releases`）
- [ ] 第 6 步核对 `releases/latest` 的 `tag_name` 指向新版本

手工兜底（仅 CI 没建成时用，比如首次跑 CI 权限没配好）：本机 git 凭据管理器里
存着 `tdcq9594` 的令牌，可以取出来用 API 建 Release：

```bash
T=$(printf "protocol=https\nhost=github.com\n\n" \
    | GIT_TERMINAL_PROMPT=0 GCM_INTERACTIVE=never git credential fill \
    | sed -n 's/^password=//p')
curl -s -X POST -H "Authorization: Bearer $T" \
     -H "Accept: application/vnd.github+json" \
     https://api.github.com/repos/<owner>/<repo>/releases \
     -d '{"tag_name":"v<版本>","name":"v<版本> — <主题>","body":"<RELEASE_NOTES 对应段落>"}'
unset T
```

纪律：令牌**不 echo、不落文件**，只在 shell 变量里过一遍；`api.github.com` 偶发返回空，重试即可。

## 5. 发布 npm（CI 自动，本地不再发）

`release.yml` 的 `发 npm` step 用 **OIDC trusted publishing** 发布，不再用长期令牌
（`network.npmToken` 已作废，本地那套 token 发布已下架）。
前提：npm 后台登记了 trusted publisher，绑本仓 + `release.yml` + `Release` environment，
且勾了 **Allow npm publish**（默认是 staged publish，不勾会失败）和 **Allow npm dist-tag**
（5.5 节的 beta 对齐要用）。这三项必须**逐字匹配**，OIDC 校验不通过时 `npm publish` 直接 403。

- [ ] 确认 `发 npm` step 绿；`npm view <包名> version` 是新版本（registry 传播要几分钟）
- 这一步**幂等**：发布前先查 `npm view <包名>@<版本>`，已存在就跳过。
  所以 resume / 手动重跑不会因为 `403 previously published` 而红
- CI 真失败要人工排查，别在 workflow 里改版本号重发

手工兜底（仅 OIDC 配错、CI 没发成时用）：npm 后台临时加 personal token，本地
`npm publish --access public`，用删掉临时 token 后立刻撤销——不到万不得已不用。

## 5.5 `beta` 标签对齐（CI 自动，无需操作）

规则（2026-11-17 主人定）：**正式版版本号比 beta 高，就把 beta 指到最新版**。
否则 `npm i <包名>@beta` 一直装着旧的预发布版。beta 比 latest 新时**不动**——
那是真正的测试通道。

- [ ] **什么都不用做**。`release job` 最后一步用 OIDC 的 dist-tag 权限自动对齐
  （npm 后台需勾 **Allow npm dist-tag**），幂等：
  - 包没有 `beta` 标签 → 跳过
  - `beta == latest` → 跳过
  - `beta` 比 `latest` 新（真测试通道）→ 保留不动
- [ ] 想确认结果：`npm view <包名> dist-tags`，`beta` 应指向新版本

本地兜底（CI 没对齐时用，需要 `config/bot.json` 里的长期 token，已属淘汰路径）：

```bash
# 本机系统代理经常是坏的，显式指定：
ROOST_NPM_PROXY=http://127.0.0.1:7892 node scripts/sync-beta-tag.mjs --dry-run
ROOST_NPM_PROXY=http://127.0.0.1:7892 node scripts/sync-beta-tag.mjs
```

- 默认检查 `qq-bot-roost` 与 `dsh-roost`，也可以只传一个包名
- 输出 `beta=X 不低于 latest=Y，不动` 就是正常

## 已知的坑

**Gitee 镜像**：2026-11-17 起不再手动推 Gitee，由 Gitee 侧原生 Pull 镜像自动同步 GitHub。
旧的手工补推 / 同树提交 / tag 补推过程细节见 `D:\WorkBuddy\_archive\2026-11-18-分册瘦身\MEMORY-release-Gitee外迁.md`，正常发版不用做。

**发完版之后再动 `CODE_ENTRIES` 里的文件，`sums:verify` 会红 —— 这是正常的，别去「修」它。**
`sums:verify` 拿工作区内容去比对 `package.json` 当前版本那条指纹。发完 0.8.10 又补了个
README 徽章，它就会红，因为 `SHA256SUMS` 里 0.8.10 那条必须等于 **tag v0.8.10 的 tarball**，
不能跟着工作区走（改了就等于让所有已装 0.8.10 的用户校验失败）。
正确做法是等下次 bump 版本再一起重跑。CI 跑的是 `sums:check`（只查条目在不在），不会被这个搞红。

**npm 包不含 `SHA256SUMS`**：更新走 GitHub 的 tarball，那边有；`npm run sums` 是开发期工具，用户不需要。
