# 发版清单

每次发版照着走。**每一步后面都写了漏掉的后果**，因为这些都是真踩过的。

## 1. 改完代码、跑测试

- [ ] `npm test`（单元 + 依赖）、`npm run test:e2e`
- [ ] `node scripts/check-secrets.mjs`

> 指纹**不要在这一步跑**，见第 2 步。

## 2. 改版本号与文档（必须先 bump，再生成指纹）

- [ ] `package.json` 的 `version` —— **先改这个**
- [ ] `RELEASE_NOTES.md`：新版本段落写在**最上面**
- [ ] **`README.md` 里会过期的数字都要对一遍**：
  - 版本徽章（`badge/version-x.y.z`）
  - 测试数量徽章（`431/431` 这种，改了测试就会变）
  - 官方接口数量、插件数量、文档里写死的行号/文件名
  - 这些是硬编码的，代码改了不跟着改就会挂一个错的数字在上面
- [ ] 其他提到版本号的文档（`docs/*.md` 里的「当前版本」段）

## 3. 生成内容指纹（bump 之后才跑）

- [ ] `npm run sums` —— 重新生成当前版本的内容指纹
  - 漏了会怎样：`updater.js` 是严格模式，用户的自动更新会因为「拿不到指纹」被拒绝
  - 什么时候必须重跑：动了 `src/` `web/` `test/` `docs/` `package.json` `README.md` `LICENSE` `start.bat` 里任何一个
- [ ] `npm run sums:verify` 应该通过（指纹与工作区一致）
- [ ] **`git diff -- SHA256SUMS` 只应看到新增一行，旧版本的条目一个都不能变**
  - 顺序错了会怎样：`build-sums.mjs` 按 `package.json` 里的**当前**版本写入。bump 之前跑 → 新代码的指纹被写进**上一个已发布版本**的条目 → 那个 tag 的 tarball 就和指纹对不上 → 所有用户的自动更新被校验拒绝，而且报的是「你的代码有改动」这种误导性错误
  - 已经写错了怎么救：`git checkout <旧tag> -- SHA256SUMS` 把旧条目找回来，然后 bump 一个新版本重跑
  - 铁律：**版本一旦发布，它那条指纹就冻结了**，它对应的是那个 tag 的 tarball，不是 master

## 4. 提交与打标

- [ ] `git add -A && git commit`
- [ ] `git push`
- [ ] `git tag -a v<版本> -m "<一句话主题>"`
- [ ] `git push origin v<版本>`

推了 tag 会触发两个 CI：
- `release-check.yml`：校验指纹与 tag 内容一致、tag 名与 package.json 版本一致
- `gitee-sync.yml`：把内容推到 Gitee 并校验

- [ ] 去 Actions 页确认这三条 workflow 都是绿的：`CI` / `发布指纹校验` / `Gitee 镜像同步`
  （只看「有没有触发」不算数，`gitee-sync` 曾经红灯过但没人发现）

### ⚠️ 必须建 GitHub Release（tag 和 Release 是两回事）

只推 tag **不建 Release** 的话，框架的检查更新就失效了：

- 检查更新读的是 `https://github.com/<owner>/<repo>/releases/latest`，
  它 302 到「最新的 Release」。没有 Release 时会 302 到**上一个版本的 Release**，
  于是解析出「最新 = 旧版本」→ 对已升到新版的用户 `hasUpdate=false`，
  **永远显示「已是最新」**，只有 GitHub 完全连不上、回退 Gitee 时才能发现新版本。
- 2026-10-28 就栽在这：0.8.8 和 0.8.9 只推了 tag 没建 Release，
  `releases/latest` 停在 0.8.7。

做法（网页，不需要 token）：
1. 打开 `https://github.com/<owner>/<repo>/releases/new`
2. Choose a tag 选刚推的 `v<版本>`
3. 标题填 `v<版本> — <一句话主题>`，正文贴 `RELEASE_NOTES.md` 里对应那段
4. Publish release

网页手动是最省事的做法，但不是唯一做法——本机 git 的凭据管理器里存着 `tdcq9594` 的令牌，
可以取出来用 API 建 Release：

```bash
T=$(printf "protocol=https\nhost=github.com\n\n" \
    | GIT_TERMINAL_PROMPT=0 GCM_INTERACTIVE=never git credential fill \
    | sed -n 's/^password=//p')
curl -s -X POST -H "Authorization: Bearer $T" \
     -H "Accept: application/vnd.github+json" \
     https://api.github.com/repos/<owner>/<repo>/releases \
     -d '{"tag_name":"v<版本>","name":"v<版本> — <主题>","body":"<RELEASE_NOTES 对应段落>"}'
unset T
```

纪律：令牌**不 echo、不落文件**，只在 shell 变量里过一遍；`api.github.com` 偶发返回空，重试即可。

## 5. 发布 npm

```bash
# token 在 config/bot.json 的 network.npmToken，不要写进仓库
python - <<'PY'
import json, os
tok = json.load(open('config/bot.json', encoding='utf-8'))['network']['npmToken']
open(os.path.join(os.environ['TEMP'], '.npmrc-pub'), 'w').write(
    f'//registry.npmjs.org/:_authToken={tok}\n')
PY
npm publish --userconfig "$TEMP/.npmrc-pub" --access public
# 记得删掉临时文件（含令牌）
```

- [ ] 等 registry 传播（通常几分钟）：`npm view <包名> version`
- 重发同版本会报 `403 previously published` —— **那说明已经写进去了**，别换版本号重发

## 6. 三端核对

- [ ] GitHub：`git ls-remote origin refs/tags/v<版本>`
- [ ] Gitee：`git ls-remote https://gitee.com/<owner>/<repo>.git master`
- [ ] npm：`npm view <包名> version`、`npm view <包名> dist-tags`
- [ ] Gitee 上的 `package.json` 版本与 `SHA256SUMS` 存在（**用 API 查，别信 raw**）
- [ ] **README 徽章显示新版本**（这条最容易漏，0.8.10 就漏过）
- [ ] **`releases/latest` 指向新版本** —— 整个 0.8.8/0.8.9 事故的根因就是它停在旧版，
      而核对环节原来没查它：
      ```bash
      curl -s https://api.github.com/repos/<owner>/<repo>/releases/latest | grep '"tag_name"'
      # 期望 "tag_name": "v<版本>"
      ```

## 已知的坑

**Gitee raw 有 CDN 缓存**：push 成功后几分钟内 `raw/master/...` 读到的还是旧内容。
核对要走 API：`https://gitee.com/api/v5/repos/<owner>/<repo>/contents/package.json?ref=master`

**Gitee 与 GitHub 历史不同源**：不能快进也不能强推（强推会冲掉 Gitee 的历史）。
做法是造一个「同树提交」——树等于 GitHub HEAD 的树，父提交指向 Gitee 当前 HEAD：

```bash
TREE=$(git rev-parse HEAD^{tree})
PARENT=$(git ls-remote https://gitee.com/<owner>/<repo>.git master | cut -f1)
NEW=$(git log -1 --format=%s HEAD | git commit-tree "$TREE" -p "$PARENT")
git -c http.extraHeader="Authorization: Basic $(printf '<用户>:<token>' | base64 -w0)" \
    push https://gitee.com/<owner>/<repo>.git "$NEW:master"
```

**gitee-sync 没配 GITEE_TOKEN 就不会自动推**，只做校验（滞后就报红）。
配好之后这一步可以省掉。

**发完版之后再动 `CODE_ENTRIES` 里的文件，`sums:verify` 会红 —— 这是正常的，别去「修」它。**
`sums:verify` 拿工作区内容去比对 `package.json` 当前版本那条指纹。发完 0.8.10 又补了个
README 徽章，它就会红，因为 `SHA256SUMS` 里 0.8.10 那条必须等于 **tag v0.8.10 的 tarball**，
不能跟着工作区走（改了就等于让所有已装 0.8.10 的用户校验失败）。
正确做法是等下次 bump 版本再一起重跑。CI 跑的是 `sums:check`（只查条目在不在），不会被这个搞红。

**npm 包不含 `SHA256SUMS`**：更新走 GitHub/Gitee 的 tarball，那边有；`npm run sums` 是开发期工具，用户不需要。
